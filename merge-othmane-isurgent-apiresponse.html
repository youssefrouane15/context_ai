2Étape 1 — Scripts Flyway V1 (retail) et V2 (corpo) édités en place

Dans chaque script, la colonne de la table cash_operation change de type. Cherche la ligne is_urgent et remplace :

db\migration\V1__… (schéma retail) ET V2__… (schéma corpo) — table cash_operationMODIFIER
-- AVANT (à supprimer) :
is_urgent VARCHAR(3) NOT NULL DEFAULT 'NO',
CONSTRAINT chk_is_urgent CHECK (is_urgent IN ('YES', 'NO')),

-- APRÈS :
is_urgent BOOLEAN NOT NULL DEFAULT FALSE,

Vérifie qu'aucun INSERT de seed n'alimente is_urgent avec 'YES'/'NO' (les seeds portent normalement sur currency/denomination/establishment/user_profile, pas sur des opérations — mais un Ctrl+F sur is_urgent dans les deux fichiers coûte 10 secondes).

Pourquoi supprimer la contrainte CHECK : elle n'a plus de sens sur un booléen — le type garantit déjà les deux seules valeurs possibles. La laisser ferait échouer le script.

3Étape 2 — Entités JPA

Retail et corpo ont chacun leur entité opération. Même modification dans les deux :

dataaccess\…\CashOperationEntity.java (retail) ET l'entité opération corpoMODIFIER
// AVANT :

private String isUrgent = "NO";

// APRÈS :
@Column(name = "is_urgent", nullable = false)

Boolean (objet) et non boolean (primitif) : volontaire, pour rester cohérent avec les autres champs wrapper de l'entité et éviter le piège du getter Lombok isUrgent() sur un primitif qui perturbe MapStruct et Jackson (avec un primitif boolean isUrgent, Lombok génère isUrgent() et non getIsUrgent() — les mappings par nom se cassent). Avec Boolean, Lombok génère getIsUrgent() et tout reste aligné.

7Étape 6 — ApiResponse : la classe + les controllers

a) La classe, format socle exact (success / message / data / error)

Placée dans application-service (module partagé par retail et corpo, comme ResponseDTO qui y vit déjà) :

application-service\…\service\domain\dto\ApiResponse.javaCRÉER
package com.bmci.workflow.fund.management.service.domain.dto;

import com.fasterxml.jackson.annotation.JsonInclude;
import lombok.AllArgsConstructor;
import lombok.Getter;
import lombok.NoArgsConstructor;

/**
 * Enveloppe standard de toute réponse HTTP du microservice,
 * alignée sur le format du socle QlickFlow : { success, message, data, error }.
 * Les champs null ne sont pas sérialisés (data absent en erreur, error absent en succès).
 */
@Getter
@NoArgsConstructor
@AllArgsConstructor
@JsonInclude(JsonInclude.Include.NON_NULL)
public class ApiResponse<T> {

    private Boolean success;
    private String message;
    private T data;
    private String error;

    public static <T> ApiResponse<T> success(T data) {
        return new ApiResponse<>(true, null, data, null);
    }

    public static <T> ApiResponse<T> success(T data, String message) {
        return new ApiResponse<>(true, message, data, null);
    }

    public static <T> ApiResponse<T> failure(String message, String error) {
        return new ApiResponse<>(false, message, null, error);
    }
}
Et le ResponseDTO<D,C> existant ? Il exprimait le même besoin (message + data). Vérifie ses usages (Alt+F7) : s'il n'est utilisé nulle part, supprime-le pour ne pas garder deux enveloppes concurrentes. S'il est utilisé, remplace par ApiResponse.

8Étape 7 — ApiResponse : les handlers d'exceptions

C'est ce qui garantit une seule forme de réponse pour le front, succès comme erreur. Le principe : le corps d'erreur devient ApiResponse.failure(message, error), les statuts HTTP ne changent pas. Sur le modèle de RetailDemandExceptionHandler :

RetailDemandExceptionHandler.java ET le handler corpo — chaque @ExceptionHandlerMODIFIER
// Le type de retour de chaque méthode devient ResponseEntity<ApiResponse<Void>>.
// Exemples (adapte aux noms de tes exceptions typées et de tes clés messages) :

@ExceptionHandler(RetailNotFoundException.class)
public ResponseEntity<ApiResponse<Void>> handleNotFound(RetailNotFoundException ex) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(ApiResponse.failure(message("retail.error.notfound", ex.getMessage()), "NOT_FOUND"));
}

@ExceptionHandler(RetailConflictException.class)
public ResponseEntity<ApiResponse<Void>> handleConflict(RetailConflictException ex) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(ApiResponse.failure(message("retail.error.conflict", ex.getMessage()), "CONFLICT"));
}

@ExceptionHandler(RetailValidationException.class)
public ResponseEntity<ApiResponse<Void>> handleValidation(RetailValidationException ex) {
    return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY)
            .body(ApiResponse.failure(message("retail.error.validation", ex.getMessage()), "VALIDATION_ERROR"));
}

@ExceptionHandler(MethodArgumentNotValidException.class)   // @Valid → 400
public ResponseEntity<ApiResponse<Void>> handleBadRequest(MethodArgumentNotValidException ex) {
    String detail = ex.getBindingResult().getFieldErrors().stream()
            .map(e -> e.getField() + " : " + e.getDefaultMessage())
            .collect(Collectors.joining("; "));
    return ResponseEntity.badRequest()
            .body(ApiResponse.failure(message("retail.error.badrequest", detail), "BAD_REQUEST"));
}

@ExceptionHandler(Exception.class)   // filet de sécurité
public ResponseEntity<ApiResponse<Void>> handleTechnical(Exception ex) {
    log.error("Erreur technique non gérée", ex);
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(ApiResponse.failure(message("retail.error.technical"), "TECHNICAL_ERROR"));
}
Le champ error = un code stable, le champ message = le texte lisible. Le front pourra brancher sa logique sur error (ex. afficher un formulaire de correction sur VALIDATION_ERROR) sans dépendre du texte. Si tu avais un ErrorDTO maison comme corps d'erreur, il devient inutile — supprime-le après avoir vérifié ses usages, sinon tu gardes deux formats d'erreur.

9Étape 8 — Les tests qui cassent et leur correction

Trois familles de tests vont rougir. Voici exactement quoi et pourquoi.

a) Tests controller (MockMvc) — le JSON a changé de forme

Toute assertion du type jsonPath("$.id") ou jsonPath("$.requestStatus") échoue : ces champs sont maintenant sous data. Les status().isOk()/isCreated() restent vrais.

Tests controller retail + corpo — pattern de correctionMODIFIER
// AVANT :
.andExpect(jsonPath("$.id").value(id.toString()))
.andExpect(jsonPath("$.requestStatus").value("INITIATED"))

// APRÈS :
.andExpect(jsonPath("$.success").value(true))
.andExpect(jsonPath("$.data.id").value(id.toString()))
.andExpect(jsonPath("$.data.requestStatus").value("INITIATED"))

// Pour les tests d'erreur (handler) :
.andExpect(status().isNotFound())
.andExpect(jsonPath("$.success").value(false))
.andExpect(jsonPath("$.error").value("NOT_FOUND"))
.andExpect(jsonPath("$.data").doesNotExist())

Les tests qui se contentent de status().isOk() + verify(useCase).create(any()) (comme CashDemandControllerTest d'origine) passent sans modification. Astuce : Ctrl+Shift+F sur jsonPath("$. dans src/test te donne la liste exhaustive à corriger.

b) Tests avec des payloads isUrgent — le type a changé

Tout builder ou setter de test qui fait .isUrgent("YES"), .isUrgent(UrgencyFlag.NO) ou setIsUrgent("NO") ne compile plus. Idem pour les fixtures JSON.

Tests use case / mapper / domaine — pattern de correctionMODIFIER
.isUrgent("YES")            →   .isUrgent(true)
.isUrgent(UrgencyFlag.NO)   →   .isUrgent(false)
assertEquals("NO", op.getIsUrgent())   →   assertEquals(Boolean.FALSE, op.getIsUrgent())
"isUrgent": "YES"  (JSON)   →   "isUrgent": true

Le test de défaut serveur (celui qui vérifie qu'une opération sans urgence reçoit NO) devient : « reçoit Boolean.FALSE ». Même intention, nouvelle valeur.

c) Tests de handler — le corps d'erreur a changé

Si tes tests de handler asserent sur les champs de l'ancien ErrorDTO (ex. $.code, $.detail), ils passent sur $.success/$.error/$.message — cf. le bloc du (a).

Mockito strict (MockitoExtension) — rappel : en corrigeant les tests, ne rajoute pas de stubs « au cas où » dans un @BeforeEach. Chaque test déclare exactement ce qu'il consomme, sinon UnnecessaryStubbingException te fera rougir le build pour une mauvaise raison.
