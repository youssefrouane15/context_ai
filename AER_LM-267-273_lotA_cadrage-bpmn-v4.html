0. Réponse courte aux deux questions de la note VS Code

Q1 — Modification / annulation agence vs traitement Caisse Centrale. Oui, c'est exactement un cas « boundary » : dans la v3 la modification est un sous-processus événementiel non interruptif, donc la tâche « Traiter la demande » reste active pendant que le DA modifie — la Caisse Centrale garde la main, ce qui est le bug fonctionnel que tu décris. En v4, l'instruction et le traitement sont encapsulés dans SubProcess_Traitement ; la modification est un boundary message interruptif sur ce sous-processus qui détruit la tâche Caisse Centrale et la remplace par une user task « Modifier la demande » détenue par l'agent (verrou). Quand l'agent enregistre ou abandonne (ou au bout de dureeVerrouModification s'il ferme son écran), le jeton revient dans le sous-processus et la tâche Caisse Centrale est recréée. L'annulation reste un sous-processus événementiel interruptif (il couvre brouillon, soumise et en modification).

Q2 — Chaque action humaine doit être une user task. Oui : le workflow démarre désormais à la création du brouillon (POST /cash) sur une user task Task_SaisirDemande, complétée par la soumission (PATCH /submit). Je n'ai pas modélisé deux tâches distinctes « Saisir » puis « Soumettre » : on ne peut pas démarrer une instance avant d'avoir un id (businessKey), donc « Saisir » commence forcément au premier enregistrement, et le clic Soumettre complète cette tâche. Deux tâches seraient complétées par le même appel, ce qui n'aurait aucun sens dans Cockpit. La tâche s'appelle « Saisir et soumettre la demande ».

« Rejetée » par la Caisse Centrale. Le back n'a pas de REJECTED (décision antérieure : pas de REJECTED) et le front du collègue ne connaît que ANNULEE_CAISSE_CENTRALE. Je traite « rejetée » = ANNULEE par la Caisse Centrale avec motif. À confirmer PO si un troisième état est attendu.

8. Sécurité fund-management — hypothèse à confirmer avant le lot B

Rien dans le code reçu ne montre de sécurité dans fund-management (aucun SecurityConfig, aucun @PreAuthorize, aucune lecture de l'appelant). Le contexte de la 261 dit que la gateway relaie le JWT aux microservices et que utilisateurs-ci expose GET /api/v1/internal/users/{uid} pour résoudre uid → profil, permissions, agence.

Plan lot B (déjà esquissé en 261, jamais implémenté) : filtre QfJwtAuthenticationFilter (lecture du sub du Bearer, sans re-validation de signature en mode mock, validation JWK en mode oauth), UserContextPort + adapter REST vers utilisateurs-ci avec cache 5 min, ContexteAppelant (uid, branchCode, permissions) injecté dans les use cases, gardes 403 dans CashDemandUseCaseImpl.

Avant de coder : confirme-moi (1) qu'il n'y a effectivement aucune sécurité dans fund-management, (2) le nom du header relayé par la gateway (Authorization: Bearer ?), (3) le mode local (auth-mode: mock comme utilisateurs-ci ?). Trois réponses courtes suffisent, pas de captures.
