1Le fonctionnel : ce que demande la Jira AER_LM-257

Le périmètre « Demandes Corpo » permet à un client entreprise (corporate) de demander à la Caisse Centrale soit une ALIMENTATION (livraison d'espèces, avec une ventilation précise par coupures : tant de billets de 200, tant de pièces de 10…), soit un RAMASSAGE (collecte d'espèces, sans ventilation préalable). Contrairement au retail — où le demandeur est une agence identifiée par son user/établissement — le corpo est identifié par son identité client : référence client, ville, complément d'adresse, numéro de compte (les « zones libres » de la Jira).

Donnée JiraTraduction dans le système
Type de demande (Alimentation/Ramassage)operationSens de l'opération — l'équivalent exact du SUPPLY/COLLECTION retail
MontanttotalAmount de l'opération, toujours calculé serveur (Σ quantité × valeur faciale) ; un montant fourni est contrôlé (422 si incohérent)
Urgence, statut, datesChamps retail existants (YES/NO ; INITIATED→VALIDATED/CANCELLED ; timestamps auto)
Réf demandeuniqueRequestRef lisible CO-AAAA-NNNNNN, générée par séquence PostgreSQL, unique et immuable
Identité client (4 zones libres)Colonnes additionnelles sur l'entête corpo — n'existent nulle part chez retail
Ventilation par coupuresArbre opération → détail devise (MAD) → lignes coupure/quantité, résolues par un code stable (BILLET_200…) contre le référentiel

3Le parcours d'une demande — le fil rouge à raconter en démo

POST /corpo/cash (payload arborescent aligné retail) │ ▼ CorpoDemandController (@Valid) │ 400 FieldErrorsDTO si contrat violé : user @NotBlank, operations @NotEmpty, │ operationSens @NotNull, quantity @Min(0), denominationCode @NotBlank (cascade @Valid) ▼ CorpoCashRequestWebMapper (MapStruct) DTO → domaine │ champs SERVEUR ignorés en entrée : id, uniqueRequestRef, requestStatus, dates ▼ CorpoDemandUseCaseImpl (sans try/catch — les exceptions typées filent au handler) │ charge le référentiel {code → valeur faciale} via le port CorpoDenominationRepository ▼ CorpoCashRequest.validateAndCompute() ← LES RÈGLES MÉTIER (domaine pur) │ ≥1 opération · défauts serveur · calcul du montant · cohérence montant fourni │ coupure inconnue → CorpoValidationException → 422 ▼ CorpoDemandRepositoryImpl (adapter @Transactional) │ réf CO-2026-NNNNNN (séquence) · charge coupures par code + devises par ISO │ + establishment par code + user par uid (nullables) ▼ CorpoCashRequestPersistenceMapper (MapStruct hybride) │ structure de l'arbre GÉNÉRÉE · résolutions en default+@Context │ liens parents & références en @AfterMapping ▼ save() → cascade JPA sur les 4 tables du schéma corpo ▼ toDomain → toResponseDTO → 201 Created (réf, statut, montants, labels)

Chaque flèche = une responsabilité unique, remplaçable et testée isolément — c'est la définition de l'architecture hexagonale : le domaine au centre ne connaît ni HTTP ni JPA ; les ports (interfaces) sont implémentés par les adaptateurs aux bords.

La règle de placement (à réciter) : utilisé par les deux modèles → common · nominal → sous-paquet retail de sa couche · corpo → sous-paquet corpo · indépendant des modèles → transverse. La racine des paquets est le MODÈLE, les couches dedans (dataaccess.corpo.entity, pas entity.corpo) — conséquence assumée : les scans de la main class élargis à la racine dataaccess (seule modification jamais faite à cette classe).

Factorisation actée dans common : les 6 VOs d'identité (CashRequestId…) et les DTOs référentiels (CurrencyDTO, DenominationDTO au format corpo) sont en UN exemplaire, noms métier sans préfixe de modèle. Justification : concepts identiques, schémas de stockage séparés — la séparation des modèles porte sur le métier et les contrats, pas sur des types d'identité triviaux. DenominationDTO unifié = le contrat retail gagne denominationCode/faceValue nullables (additif, non cassant, signalé).

5La base de données & Flyway

Le schéma corpo : 8 tables miroir de retail (cash_request, cash_operation, operation_currency — typo total_amount_by_curerency conservée volontairement, alignement oblige —, operation_denomination, currency, denomination, establishment, user_profile) + la séquence corpo_request_ref_seq + le seed (MAD, 11 coupures avec codes stables). Colonnes additionnelles : identité client + unique_request_ref sur l'entête, denomination_code sur le référentiel coupures. Contraintes ajoutées : CHECK sur operation_sens (ALIMENTATION/RAMASSAGE) et request_status, unicité (détail, coupure).

Flyway, le mécanisme à savoir expliquer : sa mémoire est la table public.flyway_schema_history (dans public car premier de schemas: public, corpo — convention du schéma socle, partagée avec le futur V1 retail). Au premier démarrage sur base non vide, baseline-on-migrate la marque V1 sans rien exécuter → tout script ≤ V1 est ignoré à jamais (le V1 du collègue ne s'appliquera pas ici — c'est voulu), seul V2+ s'exécute. Un script appliqué ne se modifie JAMAIS (checksum) ; évolution = V3, V4… ddl-auto reste à update pour ne pas changer le comportement retail (compromis transitoire acté ; cible none = décision d'équipe).

6Les choix techniques : alternatives, décision, lien fonctionnel

La méthode à retenir (et à énoncer en soutenance) : aucun choix technique n'est un goût personnel — chacun remonte soit à un besoin fonctionnel de la Jira, soit à une directive du tech lead, soit à une contrainte vécue (incident du journal). Pour chaque décision : le besoin, les options réellement sur la table, le verdict, et le prix payé — car un bon choix assume toujours son coût.

D-01 · La référence de demande par séquence PostgreSQL

Besoin fonctionnelLa Jira exige une « réf demande » : un identifiant que le métier peut lire, dicter au téléphone, retrouver dans un litige — un UUID ne remplit pas ce rôle. Elle doit être unique et ne jamais changer.
Options envisagées(a) UUID seul — illisible pour le métier, rejeté. (b) SELECT max(ref)+1 — race condition : deux créations simultanées lisent le même max et produisent un doublon ; il faudrait verrouiller la table. (c) Table de compteurs maison — réinventer la séquence, avec les mêmes locks à gérer. (d) Séquence PostgreSQL native — nextval() est atomique par conception : deux transactions concurrentes reçoivent deux valeurs distinctes, garanti par le moteur, zéro code de synchronisation.
Verdict & prix payé(d), formatée CO-AAAA-NNNNNN côté adapter. On garde deux identités : l'UUID reste la clé technique (PK, FKs, URLs) ; la référence est l'identité métier (unique, affichée, immuable — le PUT l'ignore). Prix : des « trous » possibles dans la numérotation (une transaction rollbackée consomme son numéro) — acceptable, la référence identifie, elle ne compte pas.

D-02 · Handler d'erreurs SCOPÉ (assignableTypes) et non global

BesoinLe corpo doit avoir un contrat d'erreur propre (400/404/409/422 typés) SANS modifier le comportement du retail, qui est en recette et appartient à un autre développeur.
Options(a) @RestControllerAdvice global — élégant sur le papier, mais il intercepterait aussi les exceptions retail : or le retail fonctionne aujourd'hui en try/catch → SessionServiceException → 500 ; un advice global changerait ses réponses HTTP du jour au lendemain, sans que son développeur l'ait décidé — régression de contrat imposée à autrui. (b) Advice scopé par assignableTypes — rayon d'impact strictement limité aux controllers listés.
Verdict & prix payé(b) : chaque périmètre possède son advice et migre à son rythme (le guide retail livré au collègue suit exactement ce chemin). Le prix : deux advices à maintenir transitoirement, et une cible avouée — quand le retail aura migré, fusionner en un advice global sera un refactoring trivial (les deux partagent déjà ErrorDTO et messages.properties). Le scoping n'est pas une fin, c'est un sas de migration.

D-03 · Packages : la racine est le MODÈLE, pas la couche

BesoinNote 3 du TL (« séparer les deux modèles et couches ») + réalité d'équipe : deux périmètres métier, deux développeurs, deux cycles de livraison.
Options(a) Couche-d'abord (entity.corpo, entity.retail…) — ma première version : les classes d'un même périmètre sont éparpillées dans N paquets de couche. (b) Modèle-d'abord (dataaccess.corpo.entity, dataaccess.retail.entity) : TOUT le corpo d'un module vit sous une seule racine.
Verdict & prix payé(b) — recadré par toi, à raison. Trois bénéfices : la cohésion (revoir/livrer un périmètre = ouvrir un dossier) ; les imports révélateurs (un import ...retail... dans une classe corpo saute aux yeux en review — la frontière entre modèles devient visible dans le code) ; la symétrie avec domain-core et application-service qui étaient déjà modèle-d'abord. Le prix, assumé et documenté : les paquets corpo/retail ne sont plus des sous-paquets de dataaccess.entity → l'unique modification de la classe main (scans élargis à la racine dataaccess).

D-04 · Schéma PostgreSQL séparé (et non des colonnes discriminantes)

BesoinNote 1 du TL + fonctionnel : deux populations de demandes aux identités différentes (agence interne vs client externe), aux référentiels différents (le corpo a des centimes), aux cycles d'évolution indépendants.
Options(a) Colonnes discriminantes dans les tables retail (un flag request_type + colonnes nullables client) — chaque requête retail devrait filtrer le flag, chaque évolution corpo toucherait les tables du collègue, les contraintes NOT NULL deviendraient toutes conditionnelles. (b) Base séparée — surdimensionné : double connexion, transactions distribuées pour rien. (c) Schéma dédié dans la même base.
Verdict & prix payé(c) : isolation complète (contraintes propres, CHECK ALIMENTATION/RAMASSAGE impossibles dans une table partagée avec SUPPLY/COLLECTION), migrations Flyway indépendantes, zéro risque de régression croisée — dans une seule base (une connexion, un backup). Prix : les référentiels devise/coupure existent en double ; si le métier exige un jour un référentiel unique, c'est une décision d'équipe (Q&A).

D-05 · Module Maven common (et pas des copies, ni des imports croisés)

BesoinNote 4 du TL : les deux modèles partagent un socle (identité, timestamps, contrats génériques) sans se coupler entre eux.
Options(a) Copier les classes socle dans chaque périmètre — dérive garantie (deux BaseEntity qui divergent silencieusement). (b) Le corpo importe depuis les paquets retail — couplage direct, la pire option : une évolution retail casserait le corpo. (c) Module Maven dédié dont les deux dépendent.
Verdict & prix payé(c) : la règle « retail et corpo ne s'importent JAMAIS » devient vérifiable par le build — la flèche de dépendance ne va que vers common. Critère d'admission strict : une classe entre dans common si elle est réellement importée par les deux (les VOs et DTOs référentiels y sont passés sur ta décision — concepts identiques, stockages séparés) ; le métier homonyme reste chez lui. Prix : un module de plus dans le reactor, négligeable.

D-06 · Codes stables de coupures (vs la résolution par label du retail)

BesoinLe front envoie une ventilation : il faut désigner chaque coupure de façon fiable dans le contrat d'API. Chez retail, la résolution se fait par denomination_label — « Billet de 200 DH » : corriger une majuscule ou un espace dans le libellé casse l'API.
Options(a) Reproduire la résolution par label (alignement littéral) — reproduire une fragilité connue. (b) Résoudre par UUID — fiable mais illisible et pénible côté front. (c) Code métier stable (BILLET_200, CENTIME_50) : colonne additionnelle UNIQUE sur le référentiel corpo.
Verdict & prix payé(c) — l'exemple parfait de la ligne du projet : l'alignement porte sur le modèle, pas sur les à-peu-près (même logique que le 201). Le label redevient ce qu'il doit être : de l'affichage. Prix : une colonne hors duplication stricte, tracée dans le tableau des écarts ; et le retail pourra adopter le même code (la colonne DTO existe déjà, nullable chez lui).

D-07 · Le montant : calculé serveur, jamais cru

BesoinFonctionnel pur : une demande d'espèces engage un transport de cash réel. Le montant doit être exact par construction — pas « probablement juste ».
Options(a) Faire confiance au montant du front — erreur de saisie ou fraude passent en base. (b) Calculer ET ignorer silencieusement le montant fourni — le front ne saura jamais qu'il se trompe. (c) Calculer, et si un montant est fourni, le CONTRÔLER : différent du calculé → 422.
Verdict & prix payé(c), implémenté dans le domaine PUR (validateAndComputeTotal) et pas dans le use case ni le mapper : la règle est testable sans Spring, et elle s'applique quel que soit le chemin d'entrée (create, update, demain un batch). C'est LE principe hexagonal rendu concret : la ventilation est la source de vérité, le montant en est une projection.

8Application-service : DTOs, mapper web, use case

DTOs arborescents miroir retail (breaking change assumé de l'API corpo v1, signalé au front) + Bean Validation en cascade (@Valid sur chaque liste imbriquée — sans lui, seuls les champs d'entête seraient contrôlés). Web mapper MapStruct (interface, Impl générée au build dans target/generated-sources) : les champs pilotés serveur sont @Mapping(ignore) en entrée — un client qui envoie sa propre réf ou son statut est ignoré. 9Data-access : la mécanique de persistance

La même mécanique que le save() retail, en version outillée : l'adapter (@Transactional) charge les référentiels en maps (coupures par code, devises par ISO) et résout establishment/user (nullables) ; le mapper MapStruct hybride construit l'arbre — structure générée ; résolutions par référentiels en méthodes default + @Context (les maps voyagent dans le contexte de mapping) ; liens parents bidirectionnels et références en @AfterMapping ; VO↔UUID en 12 méthodes default. Un save() unique cascade les 4 tables.

  • Lecture : fetch join sur le 1er niveau seulement (operations) — les niveaux profonds se chargent en lazy DANS la transaction (leçon du MultipleBagFetchException, cf. journal). Comme retail.
  • Update : updateHeader (@MappingTarget, réf/statut/opérations ignorés) + remplacement de l'arbre en clear() → flush() → addAll() — le flush force les DELETE avant les INSERT (contrainte d'unicité).
  • Référence : nextval('corpo.corpo_request_ref_seq') en nativeQuery → CO-2026-000042 — atomique et sans collision, contrairement à un max()+1.

10REST : controller & handler pattern BFF

Controller /corpo/cash, même media type versionné que retail, 5 endpoints. Le create renvoie 201 Created — divergence assumée avec retail (200), documentée dans le code : contrat explicite conforme à la sémantique HTTP, harmonisation retail proposée en amélioration.

Handler aligné BFF : contrat ErrorDTO {code, message} (copie conforme, dans common), registre CorpoHttpStatus (code↔statut↔clé), libellés dans messages.properties préfixés [code] (compatibles avec la regex du BFF quand il propage nos erreurs). Adaptations au contexte producteur : résolution par TYPE d'exception, FieldErrorsDTO additif sur les 400, filet Exception.class → 500 + log.error systématique (jamais de bug silencieux, jamais de 999).

12Exploitation : nettoyer la base avant une campagne

L'option A est celle des campagnes de tests (elle préserve schéma, seed et historique Flyway) ; l'option B ne sert QUE si la V2 a été modifiée (règle du checksum). Première vérification gratuite après un reset A : CN-01 doit redonner exactement CO-2026-000001.

OPTION A — Purge des données de test (l'outil du quotidien)
-- ============================================================
-- OPTION A — Purge des donnees de test (avant une campagne)
-- Garde : schema, seed devises/coupures, establishment/user,
-- historique Flyway. Pret a rejouer CN-01 immediatement.
-- ============================================================
TRUNCATE TABLE corpo.operation_denomination,
               corpo.operation_currency,
               corpo.cash_operation,
               corpo.cash_request;

-- La numerotation des references repart a CO-2026-000001
ALTER SEQUENCE corpo.corpo_request_ref_seq RESTART WITH 1;

-- Controle : transactionnel a zero, referentiels intacts
SELECT (SELECT count(*) FROM corpo.cash_request)           AS demandes,   -- 0
       (SELECT count(*) FROM corpo.cash_operation)         AS operations, -- 0
       (SELECT count(*) FROM corpo.operation_currency)     AS details,    -- 0
       (SELECT count(*) FROM corpo.operation_denomination) AS lignes,     -- 0
       (SELECT count(*) FROM corpo.currency)               AS devises,    -- 1
       (SELECT count(*) FROM corpo.denomination)           AS coupures;   -- 11
OPTION B — Reset complet du schéma (uniquement si V2 modifiée)
-- ============================================================
-- OPTION B — Reset COMPLET du schema (uniquement si la V2 a
-- ete modifiee et doit etre rejouee — regle du checksum)
-- ============================================================
DELETE FROM public.flyway_schema_history WHERE version = '2';
DROP SCHEMA corpo CASCADE;
-- Puis REDEMARRER l'application : Flyway recree le schema,

14Q&A de défense

QuestionRéponse
Pourquoi un schéma séparé plutôt que des colonnes discriminantes dans les tables retail ?Note 1+3 du TL : modèles séparés, cycle de vie et évolutions indépendants, aucun risque de régression croisée ; et Flyway isole proprement les migrations corpo.
Pourquoi dupliquer les référentiels devise/coupure au lieu de les mutualiser ?Séparation stricte des modèles (note 3) : chaque périmètre gère son référentiel (le corpo a d'ailleurs des centimes et des codes que retail n'a pas). Mutualiser = re-coupler ; possible plus tard si le métier l'exige, décision d'équipe.
Pourquoi le DTO arborescent (breaking change) ?Alignement 100% : même contrat que retail. Le front écrit UN seul modèle mental d'intégration pour les deux périmètres. Ancien contrat plat = mon prototype, remplacé avant tout branchement front.
Pourquoi le montant est-il recalculé serveur ?Le montant engage des espèces réelles : la ventilation est LA source de vérité ; un montant client n'est jamais cru, seulement contrôlé (anti-erreur de saisie, anti-fraude).
Pourquoi une séquence pour la référence ?Atomique, sans collision en concurrence (contrairement à max()+1), lisible pour le métier (CO-2026-000042), et l'UUID reste la clé technique.
Pourquoi MapStruct « hybride » et pas tout manuel / tout généré ?Le générable est généré (structure, listes, enums, VOs — zéro code d'écriture de champ à maintenir) ; l'impossible à générer (résolutions contre référentiels, liens parents) est isolé en default/@AfterMapping. Cohérent avec le web mapper.
Pourquoi les FKs user/establishment nullables ?Duplication de structure respectée, adaptation au métier : une demande corpo est identifiée par le CLIENT. Colonnes prêtes pour le jour où le workflow associera un agent.
Pourquoi le handler ne reprend pas la regex du BFF ?La regex résout un problème de CONSOMMATEUR d'erreurs (le BFF repêche les codes des services aval). Nous PRODUISONS nos erreurs : le type est la source fiable. Et nos messages [code] alimentent sa regex — compatibilité totale.
Le V1 Flyway du collègue va-t-il s'exécuter chez nous ?Non : la base est baselinée V1 → tout ≤ V1 est ignoré à jamais ici ; V2 seul s'est exécuté, et flyway_schema_history en est la preuve auditable.
Qu'est-ce qui reste ouvert ?Backlog assumé : coupure en double dans une ventilation (500 propre aujourd'hui → dédupliquer ou 422, à trancher), pagination du GET all, Testcontainers pour l'intégration, migration retail vers le handler (guide fourni au collègue), ddl-auto none (décision d'équipe), endpoint VALIDATED (attend le workflow Camunda).
Le récit en 60 secondes (à savoir par cœur) : « J'ai implémenté les demandes corpo en miroir exact du modèle retail — mêmes couches hexagonales, même agrégat, même mécanique de persistance — avec uniquement les ajouts de la Jira : identité client sur l'entête et code stable sur les coupures. Le schéma corpo est la duplication du schéma retail, livrée par Flyway en V2 versionnée. Le partagé est factorisé dans un module common. Les règles métier — montant calculé et contrôlé, défauts serveur, référence séquencée immuable, annulation propagée — vivent dans le domaine pur et sont couvertes par une pyramide de 7 classes de tests plus un cahier API de 21 cas avec attendus en base. Les erreurs suivent le contrat du socle BFF, adapté au contexte producteur, et le guide de migration retail est prêt pour mon collègue. »
