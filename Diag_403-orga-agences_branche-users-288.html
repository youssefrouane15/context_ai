0. Diagnostic — pourquoi un 403 ici et seulement ici

Capture du 01/10 12:52 : me, kpi et cash?page=0… passent, seul GET /api/v1/public/users/orga/agences renvoie 403. Les en-têtes Access-Control-Allow-* sont présents et le corps est en JSON : ce n'est pas du CORS, c'est Spring Security côté utilisateurs-ci qui refuse l'appel après authentification.

Front 4201→ gateway 9090→ utilisateurs-ci→ AgenceController.getAllAgences()@PreAuthorize → 403
Ce que fait la sécurité sur ce contrôleurConséquence
AgenceController porte un @PreAuthorize de classe (CONSOLE_ADMIN_EDIT / CREATE_USER) : réservé à la console admin.Un profil GDF (Caisse Centrale, Support, Agence) n'a aucune de ces permissions → 403 sur toutes les méthodes de la classe.
Le lot 266 a ajouté un @PreAuthorize de méthode sur getAllAgences() incluant GDF_CONSULTER_DEMANDE. En Spring Security, l'annotation de méthode prime sur celle de la classe.Avec ce commit : le GET liste est ouvert aux profils GDF, le reste de la classe reste admin. Sans ce commit : retour au 403.

Hypothèse principale : « ça marchait » quand utilisateurs-ci tournait sur la branche du lot 266 ; « ça ne marche plus » depuis qu'il tourne sur feature/AER_LM-288, créée depuis develop avant que le commit 266 n'y soit mergé. Tu n'as rien changé dans users ni dans la gateway : c'est le point de départ de la branche qui n'a pas le commit. Les quatre contrôles ci-dessous confirment ou infirment, dans l'ordre : Git (§1) → code à HEAD (§2) → processus qui tourne (§3) → données (§4). On s'arrête au premier qui explique le 403.

Le front n'est pas en cause : AgencesReferentielService tolère ce 403 par construction (lot 266), c'est pour ça que l'écran s'affiche avec une liste déroulante « Agences » vide au lieu d'une erreur.

  2. pgAdmin : la requête de contrôle du doc 288, qui liste les permissions GDF par profil.
REQUÊTEPermissions GDF par profil
pgAdmin — base utilisateurs-ci, schéma qf_admin
set search_path to qf_admin;
SELECT p.code AS profil, r.id AS role_id, r.name AS role,
       string_agg(rp.permission, ', ' ORDER BY rp.permission) AS permissions
FROM hab_profiles p
JOIN hab_profile_role pr ON pr.profile_id = p.id
JOIN hab_roles r         ON r.id = pr.role_id
LEFT JOIN hab_role_permission rp ON rp.role_id = r.id
WHERE r.platform = 'GESTION_FONDS'
GROUP BY p.code, r.id, r.name
ORDER BY p.code, r.id;

-- État des migrations (V18 doit être en success = true s'il a été joué)
SELECT version, description, success, installed_on
FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 5;
