La simulation du processus en Java
Camunda, Outbox et Saga — expliqués simplement

Une simulation complète et pédagogique du futur processus Gestion des Espèces, avec les deux patterns qu'on utilisera partout : l'Outbox (pour ne jamais perdre un message entre notre base et l'engine) et la Saga (pour défaire proprement quand une étape échoue). Chaque concept suit le même chemin : LE PROBLÈME raconté comme une panne réelle → L'IDÉE en une image → LE CODE → À RETENIR. Les noms de classes sont ceux de la simulation — les définitifs viendront de l'archi QlickFlow.

1La grande image : qui fait quoi

Trois acteurs, à ne plus jamais confondre :

ActeurSon rôleImage simple
L'engine Camunda (repo séparé)Il connaît LE PARCOURS : quelle étape vient après laquelle, qui doit valider quoi. Il ne connaît RIEN au métier des espèces.Le GPS : il dit « tourne à droite », il ne conduit pas.
Notre microserviceIl connaît LE MÉTIER : les demandes, les montants, les statuts en base. Il exécute les étapes que l'engine lui confie.Le conducteur : il tient le volant.
La businessKeyNotre référence RT-/CO-, donnée à l'instance au démarrage.Le fil rouge qui relie la demande (chez nous) et son parcours (chez l'engine), pour toujours.

Et le BPMN se lit comme une bande dessinée — chaque balise est une case :

<!-- EXTRAIT simplifie du BPMN (le fichier complet vivra dans le repo engine).
     Lis-le comme une bande dessinee : chaque balise = une case du diagramme. -->
<bpmn:process id="gestion-especes" name="Gestion des Especes" isExecutable="true">

  <!-- La demande est SOUMISE : le processus demarre ici -->
  <bpmn:startEvent id="demande-soumise" name="Demande soumise"/>

  <!-- Aiguillage : le profil qui a saisi est-il auto-validant ? -->
  <bpmn:exclusiveGateway id="gw-auto-validant" name="Profil auto-validant ?"/>

  <!-- NON -> un humain doit approuver : c'est une USER TASK.
       candidateGroups = "qui a le droit de la prendre" (vient du ms users) -->
  <bpmn:userTask id="task-validation-da" name="Valider la demande"
                 camunda:candidateGroups="DA,CHEF_CAISSE"/>

  <!-- OUI ou approuvee -> notre microservice doit poser le statut en base :
       c'est une EXTERNAL TASK : l'engine "affiche une annonce" (topic) et
       NOTRE worker vient la chercher -->
  <bpmn:serviceTask id="task-marquer-a-traiter" name="Marquer A TRAITER"
                    camunda:type="external" camunda:topic="marquer-a-traiter"/>

  <!-- La Caisse Centrale traite ou annule : user tasks CC, puis fin -->
  <bpmn:userTask id="task-traitement-cc" name="Traiter (Caisse Centrale)"
                 camunda:candidateGroups="CAISSE_CENTRALE"/>
  <bpmn:endEvent id="demande-traitee" name="Traitee"/>

</bpmn:process>

Deux types de cases à retenir : la user task (« un humain doit agir » — le DA valide, la Caisse Centrale traite ; l'engine attend, la tâche apparaît dans une corbeille de tâches) et l'external task (« un logiciel doit agir » — l'engine poste une annonce sur un topic, et NOTRE worker vient la chercher). Ce sens-là est important : l'engine ne nous appelle jamais, c'est nous qui venons chercher le travail — donc si notre service est en panne, le travail attend sagement au lieu de se perdre.

CRÉER...\\process\\DemandeProcessClient.java — le pont REST vers l'engine
package com.bmci.workflow.fund.management.process;

import org.springframework.stereotype.Component;
import org.springframework.web.client.RestTemplate;

import java.util.Map;

/**
 * Le PONT vers l'engine (repo separe) : de simples appels REST.
 * On ne demarre JAMAIS l'instance directement d'ici (voir Outbox) —
 * cette classe est appelee par le relais, pas par le service metier.
 */
@Component
public class DemandeProcessClient {

    private final RestTemplate rest = new RestTemplate();
    private static final String ENGINE = "http://localhost:8080/engine-rest";

    /** Demarre l'instance : businessKey = NOTRE reference RT-/CO-.
     *  C'est le fil qui relie pour toujours la demande et son processus. */
    public void demarrerInstance(String businessKey, String entite) {
        rest.postForObject(ENGINE + "/process-definition/key/gestion-especes/start",
                Map.of(
                    "businessKey", businessKey,                 // ex : RT-2026-000042
                    "variables", Map.of(
                        "entite", Map.of("value", entite))),    // PANIER_AGENCE / CORPORATE
                Map.class);
    }

    /** Termine une user task (ex : le DA a clique "Approuver" chez nous). */
    public void completerTache(String taskId, Map<String, Object> variables) {
        rest.postForObject(ENGINE + "/task/" + taskId + "/complete",
                Map.of("variables", variables), Map.class);
    }
}

2Le pattern OUTBOX — ne jamais perdre un message

Le problème, raconté comme une panne
Un caissier soumet sa demande à 9h58. Notre code naïf fait : ① UPDATE du statut en base → ② appel REST à l'engine pour démarrer le processus. Entre ① et ②, le serveur crashe (ou l'engine est en maintenance). Résultat au réveil : la demande est SOUMISE en base... mais aucun processus n'existe. Personne ne la validera jamais. Elle est orpheline, et personne ne le sait. L'inverse est possible aussi (processus démarré, statut pas posé). C'est LE problème des « deux systèmes » : on ne peut pas écrire dans notre base ET chez l'engine d'un seul geste atomique.
L'idée, en une image
Le serveur de restaurant n'apporte pas ta commande en cuisine en criant : il l'écrit d'abord sur son carnet. Si la cuisine est débordée, la commande est sur le carnet — rien n'est perdu, elle partira plus tard. L'Outbox, c'est le carnet : au lieu d'appeler l'engine, on écrit le message dans notre propre base, dans LA MÊME transaction que le changement de statut. Une transaction = tout ou rien : soit statut+message existent tous les deux, soit aucun. Puis un « facteur » (un scheduler) livre les messages du carnet à l'engine, et réessaie tant que ça échoue.
CRÉERdb/migration — la table outbox (V suivant)
-- La table OUTBOX : la "boite d'envoi" qui vit DANS NOTRE base metier.
-- Un message a envoyer a l'engine = une ligne ici, ecrite dans la MEME
-- transaction que le changement metier. C'est tout le secret du pattern.
CREATE TABLE retail.outbox_event (
    id             uuid PRIMARY KEY,
    aggregate_ref  varchar(20)  NOT NULL,   -- RT-2026-000042 : de quelle demande on parle
    event_type     varchar(50)  NOT NULL,   -- DEMANDE_SOUMISE, DEMANDE_VALIDEE...
    payload        text         NOT NULL,   -- le contenu du message (JSON)
    created_at     timestamp    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    sent_at        timestamp    NULL        -- NULL = pas encore livre a l'engine
);

-- L'index du relais : "donne-moi les messages pas encore partis, dans l'ordre"
CREATE INDEX idx_outbox_pending ON retail.outbox_event (created_at) WHERE sent_at IS NULL;
CRÉER...\\service\\domain\\retail\\SoumissionService.java — LE cœur : une seule transaction
package com.bmci.workflow.fund.management.service.domain.retail;

import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * LE COEUR DU PATTERN OUTBOX, en une methode.
 * Regle d'or : le statut metier ET le message pour l'engine sont ecrits
 * dans LA MEME transaction. Soit les deux existent, soit aucun.
 * Aucun appel reseau ici — le reseau, c'est le probleme du relais.
 */
@Service
@RequiredArgsConstructor
public class SoumissionService {

    private final CashDemandRepository cashDemandRepository;
    private final OutboxRepository outboxRepository;

    @Transactional   // <-- UNE transaction pour les DEUX ecritures
    public void soumettre(String requestRef) {
        // 1. Le changement METIER : la demande passe SOUMISE
        CashRequest demande = cashDemandRepository.getByRef(requestRef);
        demande.soumettre();                          // regle du domaine (garde cutoff 10h ici)
        cashDemandRepository.save(demande);

        // 2. Le MESSAGE pour l'engine : juste une ligne en base, pas un appel reseau
        outboxRepository.save(OutboxEvent.of(
                requestRef,
                "DEMANDE_SOUMISE",
                "{\"entite\": \"PANIER_AGENCE\"}"));

        // Si un crash arrive ICI : la transaction annule TOUT.
        // Pas de statut sans message, pas de message sans statut. Jamais.
    }
}
CRÉER...\\process\\OutboxRelay.java — le facteur (scheduler)
package com.bmci.workflow.fund.management.process;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.List;

/**
 * LE FACTEUR : toutes les 2 secondes, il regarde la boite d'envoi et livre
 * ce qui n'est pas encore parti. Si l'engine est en panne -> il n'efface
 * rien, il REESSAIERA au prochain tour. C'est ca, la garantie de livraison.
 */
@Component
@RequiredArgsConstructor
@Slf4j
public class OutboxRelay {

    private final OutboxRepository outboxRepository;
    private final DemandeProcessClient processClient;

    @Scheduled(fixedDelay = 2000)
    public void livrerLesMessagesEnAttente() {
        List<OutboxEvent> enAttente = outboxRepository.findBySentAtIsNullOrderByCreatedAt();

        for (OutboxEvent event : enAttente) {
            try {
                if ("DEMANDE_SOUMISE".equals(event.getEventType())) {
                    processClient.demarrerInstance(event.getAggregateRef(), "PANIER_AGENCE");
                }
                event.setSentAt(LocalDateTime.now());     // livre -> on le marque
                outboxRepository.save(event);
            } catch (Exception e) {
                // Engine injoignable ? On LOG et on s'arrete la pour ce tour.
                // Le message reste sent_at = NULL -> reessaye dans 2 secondes.
                log.warn("Engine injoignable, nouvelle tentative au prochain tour : {}", e.getMessage());
                return;
            }
        }
    }
}
À retenir
① Le service métier n'appelle JAMAIS l'engine directement — il écrit dans la table outbox, dans la même transaction que le métier. ② Le relais livre et réessaie : un message peut donc arriver deux fois (livré, crash avant le marquage sent_at, relivré) — c'est le prix de « au moins une fois ». ③ D'où la règle jumelle : tout destinataire doit être idempotent — recevoir deux fois le même message = le traiter une seule fois. Tu verras ce mot partout maintenant.

3Les workers — notre microservice exécute les étapes

Quand le processus arrive sur une external task, l'engine poste l'annonce sur le topic, et notre worker la prend. Regarde comme l'idempotence du point ② se retrouve ici :

CRÉER...\\process\\MarquerATraiterWorker.java — un worker simple et idempotent
package com.bmci.workflow.fund.management.process;

import org.camunda.bpm.client.spring.annotation.ExternalTaskSubscription;
import org.camunda.bpm.client.task.ExternalTask;
import org.camunda.bpm.client.task.ExternalTaskHandler;
import org.camunda.bpm.client.task.ExternalTaskService;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;

/**
 * UN WORKER = notre microservice qui "prend une annonce" postee par l'engine.
 * L'engine ne nous appelle pas : c'est NOUS qui venons chercher le travail
 * (long polling). Avantage : si on est en panne, le travail attend sagement.
 */
@Component
@RequiredArgsConstructor
@ExternalTaskSubscription(topicName = "marquer-a-traiter")   // l'annonce qu'on guette
public class MarquerATraiterWorker implements ExternalTaskHandler {

    private final CashDemandRepository cashDemandRepository;

    @Override
    public void execute(ExternalTask task, ExternalTaskService taskService) {
        String requestRef = task.getBusinessKey();            // RT-2026-000042 : notre fil

        // IDEMPOTENT : si le statut est DEJA pose (retry apres un crash au
        // mauvais moment), on ne refait rien — on confirme juste.
        CashRequest demande = cashDemandRepository.getByRef(requestRef);
        if (!demande.estDejaATraiter()) {
            demande.marquerATraiter();
            cashDemandRepository.save(demande);
        }

        taskService.complete(task);      // on rend le travail : l'engine avance
    }
}

4Le pattern SAGA — défaire proprement quand une étape échoue

Le problème, raconté comme une panne
La Caisse Centrale traite une urgence : ① geler la demande → ② réserver les fonds → ③ notifier le prestataire de transport. Trois étapes, trois systèmes — donc pas de transaction globale possible : chaque étape a déjà commité quand la suivante démarre. Et à l'étape ③, le prestataire répond « refusé ». Nous voilà avec des fonds réservés pour rien et une demande gelée pour rien. Qui les libère ? Quand ? Si c'est « un dev y pensera », c'est un incident de prod en devenir.
L'idée, en une image
La réservation de voyage : tu réserves le vol, puis l'hôtel, puis la voiture. La voiture est indisponible ? Tu ne laisses pas le vol et l'hôtel payés dans le vide : tu annules l'hôtel, puis le vol — dans l'ordre inverse. La Saga, c'est exactement ça : chaque étape déclare son action inverse (sa compensation), et si une étape échoue définitivement, on remonte le fil en compensant tout ce qui avait réussi. Et la beauté de notre archi : Camunda est déjà l'orchestrateur de la saga — le BPMN décrit les étapes ET leurs compensations, l'engine gère la marche arrière tout seul.
CRÉER(repo engine) — la saga « traiter une urgence », extrait commenté
<!-- LA SAGA en BPMN : "Traiter une demande urgente" = 3 etapes qui doivent
     reussir ENSEMBLE... sans transaction globale possible (3 systemes !).
     Chaque etape declare sa COMPENSATION : son annulation, au cas ou. -->

<bpmn:serviceTask id="geler-demande" name="1. Geler la demande"
                  camunda:type="external" camunda:topic="geler-demande"/>
<!-- compensation de 1 : degeler -->

<bpmn:serviceTask id="reserver-fonds" name="2. Reserver les fonds"
                  camunda:type="external" camunda:topic="reserver-fonds"/>
<!-- compensation de 2 : liberer les fonds -->

<bpmn:serviceTask id="notifier-prestataire" name="3. Notifier le prestataire"
                  camunda:type="external" camunda:topic="notifier-prestataire"/>
<!-- PAS de compensation : c'est la DERNIERE etape. Si elle reussit, la saga
     est finie. Si elle echoue -> l'engine remonte le fil et compense 2 puis 1,
     DANS L'ORDRE INVERSE. Comme on defait une valise. -->

Le point le plus important de toute la page est dans le worker de l'étape 3 : la différence entre les deux sortes d'échec. Un échec TECHNIQUE (réseau, timeout) est temporaire → on réessaie. Un échec MÉTIER (« refusé ») est définitif → réessayer ne changera rien, il faut compenser. Confondre les deux, c'est soit spammer le prestataire de retries inutiles, soit abandonner pour une micro-coupure réseau :

CRÉER...\\process\\NotifierPrestataireWorker.java — LE test des deux échecs
package com.bmci.workflow.fund.management.process;

import org.camunda.bpm.client.spring.annotation.ExternalTaskSubscription;
import org.camunda.bpm.client.task.ExternalTask;
import org.camunda.bpm.client.task.ExternalTaskHandler;
import org.camunda.bpm.client.task.ExternalTaskService;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;

/**
 * L'etape 3 de la saga — celle qui peut echouer pour de vrai (systeme externe).
 * Deux sortes d'echec, deux reactions differentes. C'est LE point a comprendre.
 */
@Component
@RequiredArgsConstructor
@ExternalTaskSubscription(topicName = "notifier-prestataire")
public class NotifierPrestataireWorker implements ExternalTaskHandler {

    private final PrestataireClient prestataireClient;

    @Override
    public void execute(ExternalTask task, ExternalTaskService taskService) {
        try {
            prestataireClient.notifier(task.getBusinessKey());
            taskService.complete(task);                       // etape 3 OK -> saga finie

        } catch (PrestataireIndisponibleException e) {
            // Echec TECHNIQUE (reseau, timeout) : ca vaut le coup de REESSAYER.
            // 3 tentatives espacees de 30s, PUIS incident visible dans Cockpit.
            taskService.handleFailure(task, "Prestataire injoignable", e.getMessage(),
                    task.getRetries() == null ? 3 : task.getRetries() - 1, 30_000L);

        } catch (DemandeRefuseeParPrestataireException e) {
            // Echec METIER (refus definitif) : reessayer ne changera RIEN.
            // On leve une ERREUR BPMN -> l'engine declenche les COMPENSATIONS :
            // liberer les fonds (2), puis degeler la demande (1). Ordre inverse.
            taskService.handleBpmnError(task, "PRESTATAIRE_REFUS", e.getMessage());
        }
    }
}
CRÉER...\\process\\LibererFondsCompensationWorker.java — une compensation = un worker inverse
package com.bmci.workflow.fund.management.process;

import org.camunda.bpm.client.spring.annotation.ExternalTaskSubscription;
import org.camunda.bpm.client.task.ExternalTask;
import org.camunda.bpm.client.task.ExternalTaskService;
import org.camunda.bpm.client.task.ExternalTaskHandler;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;

/**
 * UNE COMPENSATION = un worker comme un autre, qui fait l'action INVERSE.
 * "Reserver les fonds" a son miroir : "liberer les fonds".
 * L'engine l'appelle automatiquement quand la saga part en arriere.
 */
@Component
@RequiredArgsConstructor
@ExternalTaskSubscription(topicName = "liberer-fonds")
public class LibererFondsCompensationWorker implements ExternalTaskHandler {

    private final FondsService fondsService;

    @Override
    public void execute(ExternalTask task, ExternalTaskService taskService) {
        // Idempotent, encore et toujours : liberer des fonds deja liberes = ne rien faire
        fondsService.libererSiReserves(task.getBusinessKey());
        taskService.complete(task);
    }
}
À retenir
① Une saga = des étapes qui commitent chacune localement + une compensation par étape (sauf la dernière). ② L'échec TECHNIQUE se réessaie (handleFailure, retries, puis incident visible dans Cockpit) ; l'échec MÉTIER déclenche la marche arrière (handleBpmnError → compensations en ordre inverse). ③ Une compensation est un worker ordinaire qui fait l'inverse — et lui aussi idempotent (libérer des fonds déjà libérés = ne rien faire). ④ Nos statuts suivent : GELÉ posé à l'étape 1, retiré par sa compensation — le « verrou applicatif » du ticket trouve ici sa place naturelle.

5Tout relier : la carte mentale finale

Question que tu te poserasLa réponse-réflexe
« Je dois changer un statut ET prévenir l'engine »→ Outbox : les deux écritures dans une transaction, le relais livre.
« Mon message peut-il arriver deux fois ? »→ Oui, toujours. Donc idempotence partout (le fameux « si déjà fait, ne rien refaire »).
« Plusieurs étapes sur plusieurs systèmes, et si l'une échoue ? »→ Saga : une compensation par étape, Camunda orchestre la marche arrière.
« Réessayer ou abandonner ? »→ Échec technique = réessayer (handleFailure). Échec métier = compenser (handleBpmnError).
« Comment je retrouve le processus d'une demande ? »→ Par la businessKey = la réf RT-/CO-. Une requête, zéro jointure exotique.
« Où vit quoi ? »→ BPMN + déploiement : repo engine. Workers + outbox + statuts : chez nous.
Et maintenant : cette simulation est volontairement épurée pour l'apprentissage — quand tu m'envoies les diagrammes QlickFlow et le pattern réel de l'engine (workers ou delegates ?), on la transforme en implémentation réelle : mêmes concepts, vrais noms, vraies conventions du socle.
