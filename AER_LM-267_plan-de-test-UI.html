1. Préparation

1.1 Back et moteur

  1. Flyway : le script V3 (colonnes locked_by, cancellation_origin, cancellation_reason, submitted_at, request_comment + CHECK avec IN_MODIFICATION) est appliqué — vérifié par la requête 1.3.
  2. gestion-des-fonds_v4.1.bpmn déployé sur le moteur, même clé gestion-des-fonds, même tenant. Dans Cockpit, la définition doit afficher la version 4.1 (versionTag) comme dernière version.
  3. Purge des instances antérieures en local : une demande dont l'instance est en v3 ne sait pas recevoir msgModifierDemande au bon endroit. Supprime les instances en cours dans Cockpit (ou via la requête DELETE ci-dessous) et repars de demandes créées après le déploiement.
  4. Worker actif : camunda.worker.enabled: true dans le yaml principal du container. Au démarrage, les logs listent les abonnements aux topics gdf-*, dont gdf-appliquer-modification.
  5. Pour le scénario S08 uniquement : gdf.verrou-modification-duree: PT2M (au lieu de PT30M), à remettre ensuite.

3. Se connecter et changer d'utilisateur

Le front autonome n'a pas de page de login (c'est le shell qui la porte). En mode mock, on pose le cookie directement sur la gateway :

  1. Ouvre http://localhost:9090/api/v1/public/users/me dans un onglet (un 401 est normal à ce stade).
  2. Dans la console DevTools de cet onglet, exécute la ligne ci-dessous avec l'uid voulu.
  3. Recharge l'onglet : le JSON de /me doit montrer le bon uid, orgaUnit.code = agence attendue, et des permissions GDF_* sous un rôle de plateforme GESTION_FONDS.
  4. Recharge le front (F5) : le contexte utilisateur est relu à chaque chargement de l'application.
fetch('/mock-auth/login?uid=j43709', { method: 'POST', credentials: 'include' }).then(r => console.log(r.status));

Changer d'utilisateur = relancer la ligne avec un autre uid, puis F5 sur le front. Pour tenir deux utilisateurs en même temps (S07), utilise une fenêtre de navigation privée pour B : les cookies y sont séparés.

Contrôle réseau à faire une fois

DevTools > Réseau, sur n'importe quel appel …/fund-management/cash… : en-têtes de requête X-Uid et X-Branch-Code présents, cookie QF_MOCK_SESSION envoyé. Côté fund-management, aucun log WARN « Contexte appelant transitoire » ne doit apparaître pendant les tests UI : s'il apparaît, l'intercepteur n'envoie pas l'identité.
