1Les concepts, expliqués simplement

Commit et rollback — le vocabulaire de base

Quand ton code écrit en base de données, il travaille dans une transaction : une bulle de travail temporaire. Commit = « je valide, écris tout définitivement ». Rollback = « annule tout, comme si rien ne s'était passé ». La base sait faire ça toute seule tant que tout se passe chez elle.

Le problème : Camunda n'est pas dans notre base

Souviens-toi de l'architecture du socle : le moteur Camunda est une application séparée, qu'on appelle par HTTP (du réseau). Or une transaction de base de données ne peut pas englober un appel réseau. Scénario catastrophe : j'enregistre la demande en base (commit ✓), puis j'appelle Camunda pour démarrer le workflow… et l'appel échoue (moteur éteint, réseau coupé). Résultat : une demande « soumise » en base sans workflow démarré. La base ne peut pas faire de rollback : elle a déjà commité, et de toute façon elle ne connaît pas Camunda. C'est le problème du double-écrit (dual-write) qu'on avait identifié dans le décorticage du socle.

La Saga : la solution choisie par Yassin

En clairUne Saga, c'est une recette de cuisine où chaque étape sait se défaire elle-même. Étape 1 : casser les œufs (annulation : jeter le bol). Étape 2 : allumer le four (annulation : l'éteindre). Si l'étape 3 échoue, on ne peut pas « rollbacker » magiquement — à la place, on exécute les annulations des étapes déjà faites, en ordre inverse : éteindre le four, jeter le bol. On revient à un état propre, sans transaction magique. Chaque annulation s'appelle une compensation.

Appliqué à nous : Étape 1 = passer la demande au statut SOUMIS en base (compensation : remettre l'ancien statut). Étape 2 = démarrer le processus Camunda (compensation : supprimer l'instance de processus). Si l'étape 2 échoue → on compense l'étape 1 → la demande revient à son statut d'avant, aucune incohérence. Un orchestrateur (une petite classe qu'on va écrire) enchaîne les étapes et déclenche les compensations automatiquement en cas d'échec — c'est le « presque automatisé » dont parlait Yassin : toi tu écris des étapes, lui gère l'aiguillage succès/échec.

Saga vs Outbox — pourquoi ce choix

Outbox (la dérog tarifaire)Saga (notre choix)
PrincipeOn pose l'événement dans une table, un job l'envoie plus tardOn fait tout tout de suite, avec des annulations si ça casse
Réponse à l'utilisateur« C'est noté, ça partira » (asynchrone)« C'est fait — ou rien n'est fait » (synchrone)
InfrastructureTable outbox + job planifié + ShedLock + recoveryAucune table, aucun job : juste du code
ComplexitéÉlevée (toute la tuyauterie du facteur)Faible et lisible (des étapes + compensations)
Honnêteté technique (1 phrase) : la saga synchrone a une limite théorique — si l'application crashe pile entre une étape et sa compensation, il faut détecter l'incohérence à la main. C'est un compromis assumé (simplicité contre garantie absolue), c'est le choix de Yassin et il est raisonnable pour notre volumétrie. On le note, on n'en fait pas un débat.

Port et adapter — le réflexe hexagonal (rappel express)

Le domaine (nos use cases) ne doit jamais savoir que Camunda existe. Il connaît seulement un port : une interface Java qui dit « je sais démarrer un workflow ». Le module external-services fournit l'adapter : la classe qui implémente cette interface en parlant HTTP à Camunda. Demain Camunda est remplacé ? On réécrit l'adapter, le domaine ne bouge pas d'une ligne. C'est exactement le rôle de CashDemandRepository (port) / CashDemandRepositoryImpl (adapter) pour la base — on refait pareil pour le workflow.

Trois mots Camunda à connaître

  • process-definition-key : le nom de la « recette » BPMN déployée chez le moteur (l'attribut id du process, cf. notre décorticage). On le mettra en yaml, configurable.
  • process instance : UNE exécution de la recette. Notre demande n°42 = une instance ; la demande n°43 = une autre. Chaque instance a un id technique que Camunda nous rend au démarrage — on le garde précieusement, c'est lui qu'il faut pour supprimer/piloter l'instance.
  • businessKey : une étiquette métier qu'on colle sur l'instance au démarrage — chez nous, l'UUID de la demande. Ça permet de retrouver « l'instance de LA demande 42 » dans Camunda Cockpit sans connaître l'id technique.

package com.bmci.workflow.fund.management.service.domain.ports.output.workflow;

import java.util.Map;

/**
 * PORT de sortie vers le moteur de workflow.
 * Le domaine ne sait pas QUI est derrière (Camunda aujourd'hui, autre chose demain).
 * L'implémentation vit dans le module fund-management-external-services.
 */
public interface ProcessusWorkflowPort {

    /**
     * Démarre une exécution du processus métier pour une demande donnée.
     * @param referenceMetier l'identifiant métier de la demande (notre UUID)
     *                        — deviendra la businessKey côté moteur
     * @param variables       les données à transmettre au processus (profil, montants…)
     * @return l'identifiant technique de l'instance créée (à retenir pour compenser)
     */
    String demarrerProcessus(String referenceMetier, Map<String, Object> variables);

    /**
     * COMPENSATION : supprime une instance de processus démarrée par erreur.
     * @param processInstanceId l'id rendu par demarrerProcessus
     * @param raison            motif tracé côté moteur (ex. "Compensation saga")
     */
    void supprimerProcessus(String processInstanceId, String raison);

    /**
     * Signale un événement métier à un processus déjà en cours
     * (ex. plus tard : "la demande a été validée par le DA").
     * @param nomMessage       le nom du message tel que défini dans le BPMN
     * @param referenceMetier  la businessKey pour cibler la bonne instance
     * @param variables        données jointes à l'événement
     */
    void correlerMessage(String nomMessage, String referenceMetier, Map<String, Object> variables);
}

c) Le client : les appels REST Camunda, un par un

…external\camunda\client\CamundaEngineClient.javaCRÉER
package com.bmci.workflow.fund.management.external.camunda.client;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;
import org.springframework.web.client.RestClient;

import java.util.HashMap;
import java.util.Map;

/**
 * Compose les appels HTTP vers l'API REST de Camunda 7.
 * Chaque méthode = un endpoint officiel du moteur.
 * Cette classe est la SEULE du projet qui connaît les URLs Camunda.
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class CamundaEngineClient {

    private final RestClient camundaRestClient;

    /** POST /process-definition/key/{key}/start
        → démarre une instance, renvoie son id technique. */
    public String demarrerParKey(String processKey, String businessKey,
                                 Map<String, Object> variables) {
        Map<String, Object> corps = new HashMap<>();
        corps.put("businessKey", businessKey);
        corps.put("variables", versFormatCamunda(variables));

        log.info("Camunda > démarrage processus key={} businessKey={}", processKey, businessKey);

        DemarrageReponse reponse = camundaRestClient.post()
                .uri("/process-definition/key/{key}/start", processKey)
                .body(corps)
                .retrieve()
                .body(DemarrageReponse.class);

        log.info("Camunda > instance démarrée id={}", reponse.id());
        return reponse.id();
    }

    /** DELETE /process-instance/{id} → supprime une instance (compensation). */
    public void supprimerInstance(String processInstanceId, String raison) {
        log.warn("Camunda > suppression instance id={} raison={}", processInstanceId, raison);
        camundaRestClient.delete()
                .uri("/process-instance/{id}?deleteReason={raison}", processInstanceId, raison)
                .retrieve()
                .toBodilessEntity();
    }

    /** POST /message → transmet un événement métier à l'instance
        identifiée par sa businessKey. */
    public void correlerMessage(String nomMessage, String businessKey,
                                Map<String, Object> variables) {
        Map<String, Object> corps = new HashMap<>();
        corps.put("messageName", nomMessage);
        corps.put("businessKey", businessKey);
        corps.put("processVariables", versFormatCamunda(variables));

        log.info("Camunda > corrélation message={} businessKey={}", nomMessage, businessKey);
        camundaRestClient.post()
                .uri("/message")
                .body(corps)
                .retrieve()
                .toBodilessEntity();
    }

    /** Camunda attend chaque variable sous la forme {"value": …}.
        Ex : {"montant": {"value": 5000}} — cette méthode fait l'emballage. */
    private Map<String, Object> versFormatCamunda(Map<String, Object> variables) {
        Map<String, Object> enveloppees = new HashMap<>();
        if (variables != null) {
            variables.forEach((nom, valeur) -> enveloppees.put(nom, Map.of("value", valeur)));
        }
        return enveloppees;
    }

    /** Le petit morceau de la réponse JSON de Camunda qui nous intéresse :
        un "record" = une mini-classe qui ne porte que des données. */
    public record DemarrageReponse(String id) {}
}

6Étape 4 — Le moteur de Saga (générique et réutilisable)

Trois petites classes, dans le domaine (c'est de la logique d'orchestration métier, pas de la technique HTTP). D'abord la forme d'une étape :

…application-service\…\service\domain\saga\SagaStep.javaCRÉER
package com.bmci.workflow.fund.management.service.domain.saga;

/**
 * Une étape de saga : elle sait FAIRE (execute) et DÉFAIRE (compensate).
 * <C> est le "contexte" : le sac à dos partagé entre les étapes,
 * où chacune range ce dont les suivantes (ou sa compensation) auront besoin.
 */
public interface SagaStep<C> {

    /** Le nom de l'étape, pour des logs lisibles. */
    String nom();

    /** L'action. Si elle lance une exception, la saga déclenche les compensations. */
    void execute(C contexte);

    /** L'annulation de l'action. Ne doit JAMAIS supposer que tout va bien :
        elle s'exécute précisément quand quelque chose a mal tourné. */
    void compensate(C contexte);
}

Puis l'orchestrateur — le chef de chantier qui enchaîne et qui, en cas de pépin, fait marche arrière tout seul (le côté « automatisé ») :

…service\domain\saga\SagaOrchestrator.javaCRÉER
package com.bmci.workflow.fund.management.service.domain.saga;

import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;

import java.util.ArrayDeque;
import java.util.Deque;
import java.util.List;

/**
 * Exécute les étapes dans l'ordre. Si l'une échoue :
 * compense les étapes DÉJÀ RÉUSSIES, en ordre inverse, puis relance l'erreur.
 *
 *   execute:    Étape1 ✓ → Étape2 ✓ → Étape3 ✗
 *   compensate:                Étape2 ↩ → Étape1 ↩   puis exception
 */
@Slf4j
@Component
public class SagaOrchestrator {

    public <C> void executer(String nomSaga, List<SagaStep<C>> etapes, C contexte) {
        // Une pile (dernier entré, premier sorti) : parfaite pour "défaire à l'envers"
        Deque<SagaStep<C>> etapesReussies = new ArrayDeque<>();

        for (SagaStep<C> etape : etapes) {
            try {
                log.info("Saga [{}] > exécution de : {}", nomSaga, etape.nom());
                etape.execute(contexte);
                etapesReussies.push(etape);
            } catch (Exception erreur) {
                log.error("Saga [{}] > ÉCHEC de : {} — démarrage des compensations",
                        nomSaga, etape.nom(), erreur);
                compenser(nomSaga, etapesReussies, contexte);
                throw new SagaExecutionException(
                        "Saga '" + nomSaga + "' échouée à l'étape '" + etape.nom() + "'", erreur);
            }
        }
        log.info("Saga [{}] > terminée avec succès ({} étapes)", nomSaga, etapes.size());
    }

    private <C> void compenser(String nomSaga, Deque<SagaStep<C>> etapesReussies, C contexte) {
        while (!etapesReussies.isEmpty()) {
            SagaStep<C> etape = etapesReussies.pop();
            try {
                log.warn("Saga [{}] > compensation de : {}", nomSaga, etape.nom());
                etape.compensate(contexte);
            } catch (Exception erreurCompensation) {
                // On log et on CONTINUE : une compensation ratée ne doit pas
                // empêcher les autres. C'est le seul cas d'incohérence possible
                // → le log ERROR est le signal d'alerte à surveiller.
                log.error("Saga [{}] > COMPENSATION ÉCHOUÉE pour : {} — intervention manuelle requise",
                        nomSaga, etape.nom(), erreurCompensation);
            }
        }
    }
}

package com.bmci.workflow.fund.management.service.domain.saga.soumission;

import com.bmci.q360.domain.entity.CashRequest;
import com.bmci.workflow.fund.management.service.domain.ports.output.repository.CashDemandRepository;
import com.bmci.workflow.fund.management.service.domain.saga.SagaStep;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;

/** ÉTAPE 1 — FAIRE : statut → SUBMITTED en base.
    DÉFAIRE : remettre le statut d'origine. */
@Component
@RequiredArgsConstructor
public class ChangerStatutDemandeStep implements SagaStep<SoumissionDemandeSagaContext> {

    private final CashDemandRepository repository;

    @Override
    public String nom() { return "Passage du statut à SUBMITTED"; }

    @Override
    public void execute(SoumissionDemandeSagaContext ctx) {
        CashRequest demande = ctx.getDemande();
        ctx.setStatutPrecedent(demande.getRequestStatus());  // mémoriser AVANT
        demande.setRequestStatus("SUBMITTED");
        ctx.setDemande(repository.update(demande.getId().getValue(), demande));
    }

    @Override
    public void compensate(SoumissionDemandeSagaContext ctx) {
        CashRequest demande = ctx.getDemande();
        demande.setRequestStatus(ctx.getStatutPrecedent());  // marche arrière
        repository.update(demande.getId().getValue(), demande);
    }
}

/** ÉTAPE 2 — FAIRE : démarrer l'instance de processus chez le moteur.
    DÉFAIRE : la supprimer. */
@Component
@RequiredArgsConstructor
public class DemarrerProcessusStep implements SagaStep<SoumissionDemandeSagaContext> {

    private final ProcessusWorkflowPort workflow;

    @Override
    public String nom() { return "Démarrage du processus workflow"; }

    @Override
    public void execute(SoumissionDemandeSagaContext ctx) {
        String referenceMetier = ctx.getDemande().getId().getValue().toString();

        // Variables transmises au processus : uniquement des champs PROUVÉS
        // du modèle. La liste s'enrichira quand le BPMN final sera connu.
        Map<String, Object> variables = Map.of(
                "establishment", ctx.getDemande().getEstablishment(),
                "branchCode",    ctx.getDemande().getBranchCode(),
                "uidUser",       ctx.getDemande().getUidUser()
        );

        ctx.setProcessInstanceId(workflow.demarrerProcessus(referenceMetier, variables));
    }

    @Override
    public void compensate(SoumissionDemandeSagaContext ctx) {
        if (ctx.getProcessInstanceId() != null) {
            workflow.supprimerProcessus(ctx.getProcessInstanceId(),
                    "Compensation saga soumission demande");
        }
    }
}
En clairRegarde la symétrie : chaque étape range dans le sac à dos exactement ce dont sa marche arrière aura besoin (l'ancien statut, l'id d'instance). C'est LA discipline du pattern. Et si demain le PO ajoute une étape (ex. réserver un montant), tu écris une classe de 30 lignes avec son execute/compensate et tu l'insères dans la liste — l'orchestrateur ne change jamais.

// 2) La nouvelle opération
@Override
public CashRequestDTO soumettre(UUID id) {
    CashRequest demande = cashDemandRepository.getCashRequestById(id);
    if (demande == null) {
        throw new SessionServiceException("Cash demand not found : " + id);
    }
    if ("CANCELLED".equals(demande.getRequestStatus())) {
        throw new IllegalStateException("Cannot submit a cancelled request");
    }

    SoumissionDemandeSagaContext ctx = new SoumissionDemandeSagaContext();
    ctx.setDemande(demande);

    sagaOrchestrator.executer("soumission-demande",
            List.of(changerStatutStep, demarrerProcessusStep), ctx);

    return mapperTamp.toResponseDTO(ctx.getDemande());
}
Point important — pas de @Transactional sur soumettre() : c'est volontaire et il faut le comprendre. Si on mettait une transaction autour du tout, le commit du statut n'aurait lieu qu'À LA FIN — après l'appel Camunda. Un crash entre les deux laisserait un processus démarré pour une demande jamais soumise, et notre compensation base serait annulée par le rollback lui-même : la saga et la grande transaction se marchent dessus. La règle : chaque étape commit son propre travail (le update() du repository est déjà @Transactional), et c'est la saga qui joue le rôle de « rollback » global via les compensations.

10Étape 8 — Tester de bout en bout

  • 1. Compiler : mvn clean install à la racine — le nouveau module doit apparaître dans le réacteur Maven entre les autres.
  • 2. Démarrer le moteur : lance qlickflow-camunda-engine (il écoute sur 3030). Pour ce test de plomberie, déploie depuis le Modeler n'importe quel BPMN minimal dont l'id du process = la key du yaml (un start → user task → end suffit) — on ne teste pas les règles métier, on teste la chaîne.
  • 3. Démarrer fund-management (port 8300, ton yaml local habituel).
  • 4. Créer puis soumettre : POST /cash (comme d'habitude), puis PATCH /cash/{id}/submit. Réponse attendue : la demande avec requestStatus = SUBMITTED.
  • 5. Vérifier chez Camunda : Cockpit (http://localhost:3030, selon la config de l'engine) → ton processus → une instance en cours, avec la businessKey = l'UUID de ta demande. C'est la preuve visuelle que tout est branché.
  • 6. Tester la COMPENSATION (le test qui compte) : éteins le moteur Camunda, refais un submit sur une autre demande. Attendu : erreur côté API, et dans les logs la séquence Saga [soumission-demande] > ÉCHEC … → compensation de : Passage du statut à SUBMITTED. Vérifie en base : le statut est revenu à sa valeur d'avant. C'est ça, la saga qui fait son travail.
