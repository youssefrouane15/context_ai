CORRECTIF · 04/08/2026

1La règle Mockito qui a tout fait tomber (et pourquoi elle a raison)

MockitoExtension tourne en strictness STRICT_STUBS par défaut : un stub déclaré mais non consommé dans UN test = UnnecessaryStubbingException. Mon @BeforeEach d'origine stubbait denominationRepository et webMapper.toDomain pour TOUS les tests, alors que getById/getAll/cancel n'appellent jamais ces méthodes → 5 rouges. La sévérité est une garde utile : elle interdit les tests aux dépendances floues. La correction propre : zéro stub global — chaque test déclare exactement ce qu'il consomme (les helpers construisent, ils ne stubbent pas ; stubReferential() n'est appelé que par les 4 tests qui passent par create/update). L'anti-pattern écarté : @MockitoSettings(strictness = LENIENT), qui aurait masqué le problème au lieu de le résoudre.

2Côté corpo : les ports portent les MÊMES noms que retail

Ton arborescence tranche ce que j'avais supposé de travers : dans le package corpo, les ports s'appellent CashDemandUseCase, CashDemandRepository, DenominationRepository — mêmes noms qu'en retail, seul le package change. Donc dans CorpoDemandUseCaseImplTest :

  • Les champs @Mock doivent être typés sur les ports du package corpo : ...service.domain.corpo.ports.outputs.repository.CashDemandRepository (vérifie l'import — s'il pointe vers le package retail ou vers un type « CorpoDemandRepository » inexistant, c'est l'erreur).
  • Les méthodes appelées doivent être celles de l'interface RÉELLE : Ctrl+B sur le type du champ → tu vois la liste exacte (probablement getCashRequestById / save / update / findAll / cancelById en miroir du retail — mais c'est l'interface qui fait foi, pas ma supposition).
Pour un fichier exact plutôt qu'adapté : colle-moi (1) l'interface du port corpo CashDemandRepository et (2) l'en-tête de ton CorpoDemandUseCaseImplTest existant (imports + champs @Mock) — je te régénère le fichier corpo complet au caractère près, restructuré selon la même règle zéro-stub-global.

3La leçon à encaisser (pour moi comme pour toi)

Un bloc « AJOUTER » doit être conçu en fonction du fichier d'accueil — ses stubs globaux, sa strictness, ses helpers. J'ai fourni des ajouts pensés isolément : le compilateur ne pouvait rien dire, c'est Mockito à l'exécution qui a attrapé l'incohérence. Le réflexe que ça t'installe pour tes futurs tests : un @BeforeEach ne devrait stubber que ce que TOUS les tests de la classe consomment ; sinon, le stub descend dans les tests concernés.
