Agent vs workflow : la distinction à connaître par cœur

Un workflow enchaîne des appels LLM dans un ordre codé à l'avance (comme un process BPMN). Un agent décide lui-même de la prochaine action : il observe, raisonne, appelle un outil, lit le résultat et recommence jusqu'à atteindre l'objectif. Règle d'or (Anthropic, « Building effective agents ») : utilise le système le plus simple qui fait le travail. Un agent coûte plus cher, est plus lent et moins prévisible ; il se justifie quand le chemin ne peut pas être connu à l'avance.

La boucle agentique

loop:
  pensée   ← LLM(system_prompt + historique + observations)
  action   ← choisir un outil + ses arguments   (tool use / function calling)
  résultat ← exécuter l'outil (API, SQL, shell, navigateur, autre agent)
  si objectif atteint ou budget épuisé → réponse finale
  sinon → ajouter résultat au contexte, recommencer
  • Tool use / function calling : le modèle produit un JSON structuré (nom + arguments) ; c'est ton code qui exécute. Le modèle ne « fait » rien, il demande.
  • Contexte : tout ce que le modèle voit à chaque tour. Le context engineering (quoi mettre, quoi résumer, quoi compacter) a remplacé le « prompt engineering » comme compétence centrale.
  • Mémoire : court terme (le contexte), long terme (fichiers, base vectorielle, notes), procédurale (skills, instructions type AGENTS.md).
  • Planification : décomposer la tâche (plan-then-execute), ou laisser le modèle replanifier à chaque tour (ReAct).
  • Réflexion / auto-critique : un second passage (ou un second agent) évalue et corrige le résultat.

Les briques périphériques

RAG (Retrieval-Augmented Generation)

Chercher des passages pertinents (vectoriel + mots-clés, hybride) et les injecter dans le contexte. Indispensable sur la doc métier interne. Les pièges : chunking, fraîcheur, permissions, hallucination si le retrieval est pauvre.

Structured outputs

Forcer le modèle à respecter un schéma JSON (Pydantic / records Java). Transforme la sortie LLM en contrat d'API fiable, condition pour l'intégrer dans un flux déterministe.

Guardrails

Contrôles avant (validation des entrées, filtrage) et après (schéma, règles métier, modération) chaque appel. Et surtout : permissions d'outils (lecture seule, allow-list, confirmation humaine pour les actions irréversibles).

Evals

Jeux de tests pour agents : cas de référence, métriques (succès de tâche, coût, latence), LLM-as-judge pour la qualité. Sans evals, on fait du « vibe-based » : interdit en prod.

Observabilité

Traces de chaque tour (prompt, outils, tokens, latence), via OpenTelemetry (conventions sémantiques GenAI), Langfuse, LangSmith, Arize Phoenix. C'est le « logging » des agents.

Human-in-the-loop

Points de contrôle humains : validation d'un plan, approbation d'une action à risque, revue d'une PR. Le niveau d'autonomie se règle par étape, il ne s'impose pas.

Les notions économiques à avoir en tête

  • Tokens : unité de facturation. Un agent qui boucle 20 fois avec 50k tokens de contexte coûte 1M tokens. D'où : compaction, caching de prompt, choix de modèle par étape (petit modèle pour router, gros pour raisonner).
  • Latence : chaque tour = un appel réseau. Les agents conviennent aux tâches asynchrones (batch nocturne, PR, rapport), moins aux interfaces temps réel sans streaming.
  • Non-déterminisme : même entrée, sorties variables. On ne teste pas « égal à », on teste des propriétés et des seuils statistiques.

Les 6 patterns canoniques

Référence la plus citée en entretien : le guide « Building effective agents » (Anthropic, déc. 2024), repris depuis par toute l'industrie. Classés du plus simple au plus autonome. Pour toi qui viens de Camunda, chaque pattern a un équivalent BPMN : utilise-le pour montrer que tu comprends.

1. Prompt chaining workflow · séquence

Décomposer une tâche en étapes LLM fixes, avec des vérifications programmatiques entre elles (« gates »). Ex. : générer le plan d'un document → vérifier qu'il couvre les critères → rédiger → traduire.

BPMN : tâches en séquence avec gateways exclusives. Quand : la tâche se découpe proprement et chaque étape est plus simple qu'un prompt unique.

2. Routing workflow · classification

Un premier appel classe l'entrée et l'envoie vers le prompt/modèle/outil spécialisé. Ex. : un ticket support → « remboursement », « technique », « commercial ». Permet d'utiliser un petit modèle pour les cas simples.

BPMN : gateway exclusive pilotée par une règle (DMN). Quand : catégories distinctes et classification fiable.

3. Parallelization workflow · fan-out / fan-in

Deux variantes : sectioning (sous-tâches indépendantes en parallèle, puis agrégation) et voting (même tâche plusieurs fois, vote ou consensus). Ex. : un agent revoit la sécurité, un autre la perf, un autre la lisibilité d'une PR.

BPMN : gateway parallèle. Quand : vitesse, ou besoin de plusieurs points de vue.

4. Orchestrator-workers agent · dynamique

Un orchestrateur découpe dynamiquement la tâche, délègue à des workers, puis synthétise. Différence avec la parallélisation : les sous-tâches ne sont pas connues à l'avance. Ex. : « implémente cette feature » → l'orchestrateur identifie les fichiers à modifier et lance un worker par fichier.

BPMN : sous-process multi-instance dont la cardinalité est calculée au runtime. Quand : tâches complexes dont la structure émerge en cours de route. C'est le pattern de Claude Code et des « sub-agents ».

5. Evaluator-optimizer agent · boucle

Un LLM produit, un autre évalue selon des critères explicites, et on itère jusqu'à acceptation. Ex. : traduction littéraire, génération de tests jusqu'à couverture cible, génération de code jusqu'à build vert.

BPMN : boucle avec condition de sortie. Quand : on sait écrire des critères d'évaluation clairs et l'itération apporte de la valeur mesurable.

6. Agent autonome agent · boucle ouverte

Le modèle planifie, agit via des outils, lit l'environnement (résultats de tests, erreurs, réponses d'API) et continue jusqu'à la fin ou un plafond. Nécessite : des outils bien conçus, des garde-fous (budget de tours, sandbox), des points d'arrêt humains, des evals sérieux.

BPMN : il n'y en a pas, et c'est le point : l'agent remplace le diagramme par un objectif. Quand : problèmes ouverts, environnement riche en feedback (le code en est le meilleur exemple : compilateur + tests = feedback gratuit).

Systèmes multi-agents : quand et comment

  • Spécialisation par rôle (PM-agent, dev-agent, QA-agent) : seulement si chaque rôle a des outils, un contexte ou des instructions vraiment différents. Sinon un seul agent avec de bons outils fait mieux.
  • Topologies : hiérarchique (orchestrateur), pipeline (hand-off), réseau (A2A). Préfère hiérarchique : plus simple à observer et à déboguer.
  • Problèmes classiques : explosion de coût, perte de contexte entre agents, conflits d'écriture (deux agents modifient le même fichier), boucles sans fin. Solutions : contexte partagé explicite (fichier de plan, tâches), verrous sur les ressources, budget global.

Design des outils : le travail invisible qui fait la qualité

ACI : agent-computer interface

On passe autant de temps à concevoir l'interface agent-outil que l'interface humain-écran. Un bon outil : nom et description sans ambiguïté, paramètres peu nombreux et typés, exemples dans la description, erreurs explicites et actionnables (« montant négatif interdit ; passe un entier positif en centimes »), formats proches de ce que le modèle voit sur internet (Markdown plutôt que XML exotique), idempotence quand c'est possible.

Pour un Tech Lead Java : chaque outil est un service avec un contrat. La même rigueur qu'un endpoint REST (validation, timeouts, retries, observabilité), plus une description lisible par le modèle.

Le cycle discovery → delivery, version agentique

Ce que Carrefour appelle « transformation agentique du cycle » correspond à ce que Forrester nomme agentic software development : des agents présents à chaque étape, orchestrés, avec des humains qui fixent le cadre et valident. En 2026, la vraie valeur n'est pas « coder plus vite » mais réduire les temps morts entre les étapes (attente de specs, de review, de tests, de release notes).

Les pratiques qui structurent une équipe agentique

Spec-driven development build

La spec devient le livrable principal : un document structuré (objectif, contraintes, interfaces, critères d'acceptation, cas limites) que l'agent transforme en plan puis en code. Outils : GitHub Spec Kit, Kiro (AWS), ou simplement un SPEC.md + PLAN.md dans le dépôt. Pour le Tech Lead : la qualité de la spec est la nouvelle qualité du code. Une spec floue produit du code plausible mais faux.

Fichiers d'instructions de dépôt (AGENTS.md, CLAUDE.md) build

Un fichier à la racine qui explique à n'importe quel agent : comment builder, lancer les tests, les conventions, l'architecture, ce qu'il ne faut pas toucher. Le standard ouvert AGENTS.md est lu par la plupart des outils (Codex, Cursor, Gemini CLI, Copilot) ; CLAUDE.md par Claude Code. C'est de la documentation vivante, versionnée, et c'est au Tech Lead de la maintenir.

Review en deux couches vérification

Couche 1 : agents (lint sémantique, sécurité, cohérence avec la spec, tests manquants). Couche 2 : humain, qui se concentre sur l'intention, l'architecture et les trade-offs. Règle : tout code généré est traité avec la même rigueur ou plus qu'un code humain (Forrester 2026). Les commits d'agents sont signés avec une identité et un périmètre.

Niveaux d'autonomie par étape gouvernance

Définir explicitement, par type de tâche, le niveau : suggère (l'humain fait), prépare (l'humain valide), exécute et notifie, exécute en silence. Les équipes performantes ne démarrent pas en « full autonome » : elles montent d'un cran quand les evals et le track record le justifient.

Evals et métriques d'équipe gouvernance

Mesurer avant d'industrialiser : lead time par étape, taux d'acceptation des PR générées, taux de rework, défauts en prod, coût tokens par feature. Et des evals pour chaque agent interne (ex. : « sur 50 tickets historiques, l'agent de spec retrouve-t-il les critères d'acceptation qu'on avait écrits ? »).

Sécurité & conformité gouvernance
  • OWASP Top 10 for LLM Applications : prompt injection (n°1), fuite de données sensibles, supply-chain des modèles/plugins, excès d'agentivité (« excessive agency »).
  • Prompt injection via outils : un agent qui lit un ticket, un mail ou une page web peut recevoir des instructions malveillantes. Parade : séparer données et instructions, allow-list d'outils, confirmation humaine pour les actions sensibles, sandbox.
  • Secrets et données : jamais de PII client dans un prompt sans base légale ; data-residency ; journalisation.
  • AI Act européen : obligations progressives entre 2025 et 2027 ; calendrier en discussion (« digital omnibus ») fin 2025. Un outil interne d'aide au dev est généralement à risque limité, mais il faut documenter. Dis que tu suis le sujet, pas que tu es juriste.

Exemple concret à raconter : une feature de bout en bout

Scénario à dérouler en entretien

Un responsable franchise demande « une alerte quand la marge d'une catégorie décroche sur un magasin ». (1) Un agent de discovery interroge BigQuery, sort les distributions de marge, propose 3 définitions de « décrochage » avec leurs faux positifs. (2) Le PM choisit ; un agent rédige la story et ses critères d'acceptation, en pointant deux cas limites (magasin nouvellement ouvert, catégorie saisonnière). (3) L'agent de code lit AGENTS.md, implémente le service Java + l'écran Angular, génère les tests, ouvre la PR. (4) Trois agents reviewers (sécurité, perf SQL, cohérence spec) commentent ; le Tech Lead arbitre et merge. (5) Release notes générées, déploiement progressif, un agent surveille les alertes la première semaine et résume. Partout : l'humain décide, l'agent prépare.

Squelette Spring AI d'un agent avec outils

@Service
public class MarginAlertAgent {
  private final ChatClient chat;

  MarginAlertAgent(ChatClient.Builder b, MarginTools tools) {
    this.chat = b.defaultSystem("""
        Tu es un analyste performance franchise. Utilise les outils
        pour vérifier chaque chiffre avant de conclure. Réponds en JSON.
        """)
      .defaultTools(tools)                       // méthodes @Tool exposées au modèle
      .defaultAdvisors(new SimpleLoggerAdvisor()) // traces
      .build();
  }

  public AlertReport analyse(String storeId, String category) {
    return chat.prompt()
      .user(u -> u.text("Magasin {s}, catégorie {c} : la marge décroche-t-elle ?")
                   .param("s", storeId).param("c", category))
      .call()
      .entity(AlertReport.class);               // structured output
  }
}

@Component
class MarginTools {
  @Tool(description = "Marge brute hebdo d'une catégorie pour un magasin, 12 dernières semaines")
  List<WeeklyMargin> marginHistory(String storeId, String category) { /* BigQuery */ }

  @Tool(description = "Médiane de marge de la catégorie sur les magasins comparables")
  double peerMedian(String category, String storeCluster) { /* ... */ }
}

Le modèle décide d'appeler marginHistory puis peerMedian ; Spring AI exécute, réinjecte les résultats, et désérialise la réponse finale dans AlertReport. Trois notions d'entretien en 30 lignes : tool calling, structured output, observabilité.

Ce qu'on attend d'un Tech Lead « agentique »

  • Architecte du système humain + agents : décide où un agent apporte de la valeur, où il n'en apporte pas, et à quel niveau d'autonomie.
  • Gardien de la qualité : specs, AGENTS.md, evals, revue à deux couches, définition de « done » qui inclut les tests générés.
  • Platform builder : outils internes (serveurs MCP vers le SI Carrefour, skills d'équipe, templates de prompts versionnés), pipelines CI avec gates IA.
  • Coach et conduite du changement : l'équipe passe de « j'écris du code » à « je spécifie, je délègue, je vérifie ». Il faut gérer l'anxiété, les sceptiques et les enthousiastes qui mergent sans lire.
  • FinOps IA : suivre coût tokens, latence, et prouver le ROI (lead time, défauts, throughput) à la hiérarchie.
  • Interface avec le PM : la discovery devient collaborative avec des agents ; le Tech Lead aide à cadrer les hypothèses techniques tôt.

Postures qui rassurent un Tech Manager

Pragmatique

« Je commence par un workflow simple, mesurable, puis j'augmente l'autonomie quand les evals le justifient. »

Lucide sur les limites

« Les agents sont excellents là où le feedback est automatique (tests, compilateur, données). Ils sont médiocres sans spec claire. Mon travail, c'est de créer ces boucles de feedback. »

Orienté équipe

« La transformation réussit si chaque dev gagne du temps dès la semaine 1 sur une tâche concrète qu'il déteste. On commence par là. »

Les erreurs à ne pas faire en entretien

  • Dire « l'IA va remplacer les devs » ou l'inverse (« c'est un gadget »). La bonne réponse : le rôle se déplace vers spécification, vérification, architecture.
  • Citer 15 frameworks sans en avoir touché un. Mieux : un framework Java pratiqué (Spring AI) + un mental model (LangGraph/ADK) + les protocoles.
  • Oublier la gouvernance (sécurité, coût, conformité). Chez un distributeur coté avec des données fournisseurs, c'est éliminatoire.
  • Parler de « prompt magique ». Parle de context engineering, d'outils, d'evals.

Technique

Quelle différence entre un agent et un workflow LLM ? Quand choisir l'un ou l'autre ?

Un workflow encode le chemin à l'avance ; l'agent choisit ses actions à chaque tour. Je choisis le workflow par défaut (prévisible, testable, moins cher) et l'agent quand le chemin dépend de ce qu'on découvre en route : debugging, implémentation d'une feature sur un dépôt inconnu, investigation d'incident. Et je mélange : un orchestrateur BPMN/LangGraph déterministe avec des nœuds agentiques bornés.

Comment garantir la fiabilité d'un système non déterministe ?

Trois leviers : (1) structured outputs et validation de schéma à chaque frontière ; (2) evals : jeu de cas de référence rejoué en CI avec métriques de succès, coût, latence, et LLM-as-judge pour la qualité ; (3) conception des outils pour que le feedback soit automatique (tests, compilateur, requêtes vérifiables). Plus de l'observabilité par trace pour analyser chaque échec. On ne vise pas 100 % mais un taux mesuré, avec un humain sur les actions irréversibles.

Comment gérez-vous la prompt injection dans un agent qui lit des tickets ou des mails ?

Je considère tout contenu lu par l'agent comme non fiable. Mesures : séparer instructions système et données (balisage, mention explicite), allow-list d'outils par tâche, lecture seule par défaut, confirmation humaine pour les écritures sensibles, sandbox pour l'exécution de code, détection de patterns d'injection, et journalisation complète. C'est le n°1 de l'OWASP LLM Top 10, je le traite comme une injection SQL : jamais de confiance dans l'entrée.

Expliquez MCP. Pourquoi est-ce important pour une équipe comme la nôtre ?

MCP standardise la façon dont un agent découvre et appelle des outils et des données : un serveur expose tools, resources et prompts ; n'importe quel client compatible (Claude Code, Copilot, Gemini CLI, un agent Spring AI) les utilise. Pour une Digital Factory, ça veut dire qu'on écrit une fois un serveur MCP « référentiel produits » ou « BigQuery Marchandise » et que tous les agents de l'équipe en profitent, avec des permissions centralisées. En Java, Spring AI et LangChain4j fournissent client et serveur.

Comment feriez-vous un agent text-to-SQL fiable sur BigQuery pour la discovery ?

Pas de SQL libre sur le schéma brut. Je construis une couche sémantique (vues métier documentées, métriques définies), un outil « describe_table » et « run_query » en lecture seule avec quota, des exemples de requêtes validées en few-shot ou en RAG, une étape de vérification (dry-run, contrôle des coûts BigQuery, bornes de dates) et des evals sur un jeu de questions-réponses connues. Le résultat est présenté avec la requête exécutée, pour que le PM puisse vérifier.

Comment contrôler les coûts ?

Budget de tours et de tokens par tâche, prompt caching sur les gros contextes stables, routage par complexité (petit modèle pour classer, gros pour raisonner), compaction de contexte, batch asynchrone pour le non-urgent, et un tableau de bord coût par feature / par agent. Le coût est une métrique de l'eval, pas une surprise de fin de mois.

Que mettez-vous dans un AGENTS.md ?

Commandes de build, test, lint ; structure du dépôt et où mettre quoi ; conventions (nommage, style, patterns imposés) ; ce qu'il ne faut jamais toucher ou faire (migrations, secrets, dépendances) ; comment écrire un test et un commit ; liens vers specs et ADR. Court, à jour, versionné, et revu comme du code.

Leadership & transformation

Comment embarquez-vous une équipe sceptique sur les agents ?

Je ne commence pas par la vision, je commence par une tâche détestée (tests de non-régression, release notes, migration de lib) que l'agent prend dès la semaine 1, mesurée. Je garde l'humain propriétaire du merge. J'organise des sessions de pairing avec agent et un canal pour partager prompts et skills. Les sceptiques deviennent les meilleurs reviewers : je leur confie la couche 2.

Comment mesurez-vous le succès de la transformation ?

Lead time par étape (idée → spec, spec → PR, PR → prod), taux d'acceptation des PR générées, taux de rework, défauts en prod, satisfaction équipe, et coût IA par feature. Avec une baseline mesurée avant. Si le lead time baisse mais le rework explose, on a déplacé le problème.

Un dev a mergé du code généré qui a cassé la prod. Que faites-vous ?

Post-mortem sans blâme : quel test manquait, quel gate CI aurait dû bloquer, pourquoi la revue humaine n'a pas vu. Puis règle : code généré = même exigence qu'humain ou plus ; agent reviewer obligatoire sur les chemins critiques ; déploiement progressif. L'incident sert à calibrer le niveau d'autonomie, pas à revenir en arrière.

Pourquoi vous, venant de la banque ?

Parce que j'ai orchestré des processus complexes sous contrainte (Camunda, microservices, réglementaire) et que l'agentique, c'est de l'orchestration avec une brique non déterministe : il faut quelqu'un qui sait gouverner. Et parce que le Marchandise ressemble à la finance : des flux, des règles, des données critiques, des partenaires externes. J'apporte la rigueur, et j'ai déjà mis des pipelines LLM en production à titre personnel.

Glossaire

Agent
Système où un LLM choisit dynamiquement ses actions et outils pour atteindre un objectif, en boucle.
Agentic commerce
Achat réalisé par un agent IA pour le compte d'un client (sélection, comparaison, commande, paiement). Axe du plan Carrefour 2030 avec Google.
Agentic SDLC / ASDLC
Cycle de développement où des agents interviennent à chaque étape (discovery, spec, build, test, delivery), orchestrés sous supervision humaine.
AGENTS.md
Fichier standard à la racine d'un dépôt décrivant à un agent de code comment builder, tester et respecter les conventions.
A2A
Agent-to-Agent protocol (Google, 2025) : communication entre agents via Agent Cards, tâches et artefacts.
Context engineering
Art de composer ce que le modèle voit : instructions, outils, mémoire, documents, résumés, dans la limite de la fenêtre de contexte.
Context window
Quantité maximale de tokens que le modèle peut traiter en un appel (de 128k à 1M+ selon les modèles en 2026).
Compaction
Résumer l'historique d'un agent pour libérer de la place dans le contexte sans perdre l'essentiel.
Discovery
Phase produit : comprendre le problème, valider la valeur, l'utilisabilité, la faisabilité et la viabilité avant de construire.
Delivery
Phase produit : construire, tester, livrer, opérer.
Dual-track agile
Discovery et delivery menés en parallèle par la même équipe, en continu.
Embedding
Vecteur numérique représentant le sens d'un texte, utilisé pour la recherche sémantique (RAG).
Eval
Évaluation systématique d'un système IA sur un jeu de cas avec métriques ; l'équivalent des tests pour le non-déterministe.
Excessive agency
Risque OWASP : un agent avec trop de permissions ou d'autonomie par rapport à son besoin réel.
Function calling / tool use
Capacité du modèle à produire un appel structuré vers une fonction définie par le développeur.
Guardrails
Contrôles automatiques en entrée/sortie d'un LLM : validation, filtrage, règles métier, permissions.
Hallucination
Réponse plausible mais fausse. Se combat par retrieval, outils vérifiables, structured outputs et evals.
Hand-off
Transfert de la conversation ou de la tâche d'un agent à un autre agent spécialisé.
Human-in-the-loop (HITL)
Point de validation humaine inséré dans une boucle agentique.
LLM-as-judge
Utiliser un modèle pour noter la sortie d'un autre selon une grille ; sert aux evals de qualité.
MCP
Model Context Protocol : standard ouvert pour connecter agents et outils/données (tools, resources, prompts).
Multi-agent
Système composé de plusieurs agents coopérants (orchestrateur-workers, pipeline, réseau).
Orchestrateur
Composant (code, graphe ou agent) qui décompose, délègue et synthétise. Rôle que jouait Camunda dans tes projets.
Prompt caching
Réutiliser le préfixe de prompt déjà traité par le fournisseur pour réduire coût et latence.
Prompt injection
Attaque où des instructions malveillantes sont glissées dans les données lues par le modèle. N°1 de l'OWASP LLM Top 10.
RAG
Retrieval-Augmented Generation : récupérer des documents pertinents et les fournir au modèle pour répondre.
ReAct
Reason + Act : schéma de boucle où le modèle alterne raisonnement et appel d'outil.
Sandbox
Environnement isolé où un agent exécute du code ou des commandes sans risque pour la prod.
Skill
Paquet d'instructions (et parfois de scripts) qu'un agent charge à la demande pour une tâche donnée. Spécialisation sans fine-tuning.
Spec-driven development
Approche où une spécification structurée pilote la génération de plan puis de code par un agent.
Structured output
Sortie du modèle contrainte à un schéma (JSON Schema), désérialisable en objet typé.
Sub-agent
Agent lancé par un autre agent pour une sous-tâche, avec son propre contexte.
Token
Unité de texte traitée et facturée par le modèle (~¾ de mot en anglais, moins en français).
Trace
Enregistrement complet d'une exécution agentique : prompts, outils, résultats, tokens, temps.
UCP / AP2 / ACP
Protocoles de commerce agentique (Google ; Google + partenaires paiement ; OpenAI + Stripe) : catalogue, panier, paiement avec mandat.
Vibe coding
Développement guidé par l'intuition et le prompt, sans spec ni revue. Acceptable pour un prototype jetable, pas pour un produit.
Astuce Tape un mot pour filtrer ; vide pour tout revoir.
