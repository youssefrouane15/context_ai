Checklist des éléments à me fournir — console QlickFlow

Tout ce dont j'ai besoin pour implémenter AER_LM-271 (BDD + API CRUD Agence, microservice utilisateurs) puis AER_LM-259 (Front Configuration des agences + intégration API, portail-ci/src/app/console), en respectant les conventions réelles de chaque projet — et en traversant correctement l'api-gateway.

3 projets concernésPriorité 🔴 = bloquantRien n'est codé — 271 conditionne 259

1La chaîne complète à couvrir

Navigateur (portail-ci) │ /console/agences → console-routing.module.ts → console-agence │ appel HTTP vers l'URL de environment.ts ▼ api-gateway-ci (com.bnpparibas.irb.qlickflow.apigateway) │ QfUrlsProperties → route /utilisateurs/** vers le microservice │ security/relay → propage le token OAuth au microservice ▼ microservice utilisateurs │ Controller → UseCase → Repository → PostgreSQL (table agence) ▼ Flyway (script de création + seed)
Trois projets, trois jeux de conventions différents. Le package de la gateway (com.bnpparibas.irb.*) diffère déjà de celui de fund-management (com.bmci.*) : je ne transposerai aucune convention d'un projet à l'autre sans l'avoir vue. D'où la longueur de cette liste — chaque élément demandé sert à éviter du code qui compile mais qui ne ressemble pas au projet.

3🔴 Microservice utilisateurs (pour 271)

☐ÉlémentPrioPourquoi
☐Arborescence complète : tree /f src\main\java depuis la racine du projet🔴Savoir si c'est hexagonal comme fund-management (5 modules) ou une structure classique en couches, et quel est le package racine.
☐Une tranche verticale existante complète : un Controller + son UseCase/Service + son Repository/Adapter + son entité JPA + son DTO + son mapper🔴L'élément le plus important de tout ce document. C'est lui qui me donne : conventions de nommage, style d'exceptions, format de réponse, usage ou non de Lombok/MapStruct, pagination, validation.
☐Le handler d'exceptions (@RestControllerAdvice) du projet🔴Quels codes HTTP, quel format d'erreur, quelles exceptions typées existent déjà. (Ne pas réinventer un trio Validation/NotFound/Conflict s'il existe autre chose.)
☐Le format de réponse : y a-t-il un ApiResponse<T> comme dans fund-management, ou un retour direct ?🔴Le front console dépendra de ce format pour désencapsuler.
☐Scripts Flyway existants (ou le mécanisme de migration utilisé) + nom du/des schéma(s)🔴Où poser la table agence, quelles conventions de nommage de colonnes, quelle stratégie d'id (UUID ? séquence ?), et si on est en phase « édition en place » comme fund-management ou en vraies migrations versionnées.
☐application.yml du microservice (celui du module container/racine)🟠Port, datasource, schémas, context-path éventuel — nécessaire pour les tests Postman et la déclaration côté gateway.
☐Une classe de test existante (unitaire et/ou intégration)🟠Pour livrer des tests dans le style du projet (JUnit 5 ? Mockito strict ? MockMvc standalone ou @SpringBootTest ?).
☐Le pom.xml (racine + module concerné)⚪Versions Spring Boot / Java, présence de MapStruct, Lombok, validation — pour ne pas utiliser une lib absente.
☐Existe-t-il déjà une notion d'agence/établissement dans ce microservice ?🔴Si oui, on étend l'existant au lieu de créer une table concurrente. À vérifier avant tout code.
Astuce pour l'arborescence sous Windows : depuis la racine du projet, tree /f src\main\java > arbo.txt puis tu m'envoies le fichier. Idem pour portail-ci\src\app.

5🔴 api-gateway-ci — la pièce que j'avais sous-estimée

Tant que la route n'existe pas dans la gateway, le front ne peut pas atteindre l'API : c'est aussi bloquant que le code lui-même. Et la propagation du token OAuth vers le microservice passe par security/relay — si elle n'est pas configurée pour utilisateurs, on aura des 401 inexpliqués.
☐ÉlémentPrioPourquoi
☐QfUrlsProperties + le application.yml de la gateway (bloc des routes)🔴Le cœur du sujet : voir comment un microservice existant (fund-management, dérogation) est déclaré et routé, pour déclarer utilisateurs à l'identique.
☐QfSecurityProperties et SecurityConfig🔴Quelles routes sont publiques/protégées, quels scopes/rôles sont exigés — pour savoir ce qu'il faut déclarer pour la console.
☐Contenu de security/relay/🟠Comment le token est relayé au microservice aval : le microservice utilisateurs devra le valider de la même façon.
☐Contenu de security/mock/🟠Probablement le mode dev local (bypass OAuth) — indispensable pour que tu puisses tester en local sans SSO complet.
☐Une route existante déjà fonctionnelle de bout en bout (front → gateway → microservice), n'importe laquelle🔴Le modèle complet à copier : URL côté front, entrée de routage, config sécurité. Une seule route vue = tout le pattern compris.
☐Le README de la gateway (visible ouvert sur ta capture)🟠S'il documente l'ajout d'un microservice, il répond peut-être à la moitié de cette section.
☐La gateway tourne-t-elle en local chez toi ? Sur quel port ?🟠Détermine le plan de test : via gateway (réaliste) ou en direct sur le microservice (plus simple pour démarrer).
