1Ce qui est demandé, en une phrase

Jusqu'ici, on a construit le QUOI : deux APIs qui créent, modifient et annulent des demandes d'espèces (retail et corpo). AER_LM-258 demande le COMMENT ÇA VIT : le parcours complet d'une demande — qui la crée, qui doit la valider selon son profil, quand la Caisse Centrale la voit, comment elle se termine — orchestré dans Camunda 7, avec des contraintes horaires strictes (10h, 16h) qui changent ce qui est permis selon l'heure de la journée.

La bonne nouvelle : ce ticket s'emboîte exactement sur ce qu'on a construit. Le diagramme du ticket parle de « deux entités, deux circuits » — ce sont TES deux périmètres. Le CRUD existant devient le socle ; le process Camunda vient piloter les transitions d'état par-dessus.

Le point subtil du diagramme : GELÉ est explicitement marqué « pas un statut Camunda ». Traduction technique : c'est un flag en base métier (ex : locked_by_cc = true) que l'API consulte pour refuser toute modification — pas une étape du BPMN. Le process Camunda reste posé sur SAISIE/À TRAITER pendant le gel. Même logique pour BROUILLON : tant que la demande n'est pas soumise, l'instance Camunda n'a probablement même pas besoin d'exister (à trancher, Q3).

5Les 3 règles d'horloge

RègleCe qu'elle ditTraduction technique
Cutoff 10h — urgence agencesUne agence normale (hors BP) ne peut plus soumettre d'URGENT après 10h : « techniquement interdit ».Une garde à la soumission : si isUrgent = YES et heure > 10h et agence non-BP → rejet (422 côté API / gateway côté process). PAS un timer Camunda : c'est une règle instantanée au moment de l'acte.
Exception Banque PrivéeUne agence BP PEUT soumettre un urgent après 10h, MAIS il passe obligatoirement par la validation du Responsable BP avant d'atteindre la Caisse Centrale.Un gateway dans le BPMN : urgent + après 10h + agence BP → user task « Validation Resp. BP » insérée dans le circuit. Il faut donc savoir qu'une agence est BP → attribut sur le référentiel establishment.
Cutoff 16h — clôture de journéeAvant 16h : l'agence crée/modifie/annule librement le non-urgent non-traité du jour. Après 16h : l'agence perd TOUTE main sur les demandes du jour (la CC prend le relais hors outil, statuts Terminé/Annulé) ; une saisie après 16h est rattachée automatiquement à J+1 ouvré.Deux mécanismes : (a) des gardes sur PUT/PATCH (si demande du jour et heure > 16h et appelant = agence → 422/403) ; (b) une notion de date de rattachement (businessDate) calculée à la création : avant 16h → aujourd'hui, après 16h → prochain jour OUVRÉ (il faut un calendrier des fériés, Q6). Le « verrouillage automatique + planification J+1 » de la légende peut aussi être un job planifié à 16h.
Piège classique à éviter : coder les cutoffs avec l'heure du poste client ou du navigateur. L'heure de référence est celle du SERVEUR (timezone Africa/Casablanca), sinon la règle « techniquement interdit » est contournable en changeant l'horloge d'un PC. À centraliser dans un seul composant (ex : CutoffPolicy) testable — on injectera l'horloge (Clock) pour les tests unitaires.

6L'architecture technique proposée (Camunda 7)

Le partage des rôles — qui porte quoi

ComposantResponsabilité
Camunda 7 (moteur BPMN)Le PARCOURS : enchaînement des étapes, user tasks de validation (assignées par rôle : DA, Resp. BP, Caisse Centrale), gateways d'aiguillage (auto-validant ? urgent après 10h BP ?), historique du qui-a-fait-quoi.
Ta base métier (schémas retail/corpo)La SOURCE DE VÉRITÉ de la demande : contenu, montants, ventilation, ET le statut affiché + le flag gelé + le motif d'annulation + la businessDate. Le process met à jour le statut via tes APIs/services à chaque transition (delegates/listeners).
Tes APIs existantesRestent le canal de création/modification. S'enrichissent des nouveaux verbes : soumettre, valider, rejeter, geler, traiter — qui déclenchent/complètent les étapes Camunda.

8Les questions à trancher avec Yassin AVANT de coder

Q1Où vit le moteur Camunda ? Embarqué dans microservice-fund-management (starter Spring Boot Camunda 7), ou dans l'orchestrateur BFF/socle Q360 qui appellerait nos APIs ? C'est LA question structurante — tout le design des delegates en dépend.
Q2Un BPMN paramétré ou deux BPMN (panier agence / corporate) ? Ma proposition : un seul, mais si le socle a une convention, on la suit.
Q3Le brouillon démarre-t-il une instance ? Ma proposition : non — l'instance naît à la soumission.
Q4Qui pose TRAITÉ hors outil ? Après 16h la CC « prend le relais hors outil » : le statut final est-il saisi a posteriori dans l'outil (écran CC), ou par un batch/import ?
Q5D'où viennent les rôles ? LDAP/SSO du socle, ou notre table user_profile enrichie (profile_type existe déjà : AGENT/RESP…) ? Et l'attribut « agence Banque Privée » : sur establishment ?
Q6Le calendrier des jours OUVRÉS pour le J+1 après 16h : existe-t-il un référentiel des fériés Maroc dans le socle ?
Q7« Une demande par client » (corporate) : contrainte d'unicité sur les demandes OUVERTES d'un même client ? Si oui → 409 à la création.
Q8Les demandes déjà en base (statuts INITIATED/VALIDATED actuels) : reprise de données vers les nouveaux statuts, ou base réinitialisée (fresh start, comme on sait faire) ?
