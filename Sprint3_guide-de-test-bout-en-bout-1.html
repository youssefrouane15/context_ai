SELECT u.uid, p.code AS profil, o.code AS agence,
       string_agg(DISTINCT rp.permission, ', ' ORDER BY rp.permission) AS permissions
FROM users u
JOIN hab_profiles p ON p.id = u.profile_id
LEFT JOIN orga_unit o ON o.id = u.organization_unit_id
JOIN hab_profile_role pr ON pr.profile_id = p.id
JOIN hab_role_permission rp ON rp.role_id = pr.role_id AND rp.permission LIKE 'GDF_%'
WHERE u.uid IN ('j43709', 'j08221', '{{UID_CC}}', 'h11111')
GROUP BY u.uid, p.code, o.code ORDER BY u.uid;
Si une permission manque sur une ligne, un bouton sera caché en démo : corrige les rôles avant de commencer. Colonnes profile_id / organization_unit_id comme en V10.

3. Se connecter et changer d'utilisateur

Le front autonome n'a pas de page de login (c'est le shell qui la porte). En mode mock, on pose le cookie directement sur la gateway :

  1. Ouvre http://localhost:9090/api/v1/public/users/me dans un onglet (un 401 est normal à ce stade).
  2. Dans la console DevTools de cet onglet, exécute la ligne ci-dessous avec l'uid voulu.
  3. Recharge l'onglet : le JSON de /me doit montrer le bon uid, orgaUnit.code = agence attendue, et des permissions GDF_* sous un rôle de plateforme GESTION_FONDS.
  4. Recharge le front (F5) : le contexte utilisateur est relu à chaque chargement de l'application.
fetch('/mock-auth/login?uid=j43709', { method: 'POST', credentials: 'include' }).then(r => console.log(r.status));

Changer d'utilisateur = relancer la ligne avec un autre uid, puis F5 sur le front. Pour tenir deux utilisateurs en même temps (S07), utilise une fenêtre de navigation privée pour B : les cookies y sont séparés.

Contrôle réseau à faire une fois

DevTools > Réseau, sur n'importe quel appel …/fund-management/cash… : cookie QF_MOCK_SESSION envoyé, et plus aucun en-tête X-Uid / X-Branch-Code (B2). Côté fund-management, aucun log WARN « Contexte appelant transitoire » : s'il apparaît, la chaîne de sécurité n'a pas posé l'authentification. Un log DEBUG « Auth >> uid=… agence=… toutesAgences=… » par premier appel de chaque persona (puis cache 5 min).

4.4 Hors démo — trois contrôles API optionnels (Postman)

Tout le fonctionnel se teste depuis les écrans (§5). Les trois cas ci-dessous vérifient que le back tient les règles même quand on contourne l'écran ; personne ne les verra en démo, ils sont là si tu veux te rassurer avant. Postman doit passer par la gateway avec le cookie mock : POST http://localhost:9090/mock-auth/login?uid=… (cookie gardé automatiquement), puis les appels sur http://localhost:9090/api/v1/public/fund-management/cash….
