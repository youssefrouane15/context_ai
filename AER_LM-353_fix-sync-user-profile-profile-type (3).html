AER_LM-353 + évolution PO — Synchronisation user_profile et colonne Vidage seul (export GAB)

fund-management · Flyway varchar(50) + uid unique · branche bugfix depuis release/v1.3.0 · 20/11/2026

Cause et correctifCommandes git (tout le déroulé)UserProfileEntityReport sur developVérificationÉvolution PO : colonne « Vidage seul » (export GAB)Console : création d'un chef de caisse (portail-ci)

0. Cause et correctif

Cause (log local) : [user-profile] synchronisation impossible pour g10008 : valeur trop longue pour le type character varying(10). utilisateurs-ci envoie profile_type = STANDARD_USER (13 car.), la colonne en accepte 10 → la synchronisation AER_LM-353 échoue en silence, le DA n'existe pas dans user_profile, la création de demande plante. La Caisse Centrale échoue aussi mais n'a pas besoin de user_profile pour traiter.
Correctif : un script Flyway (numéro calculé automatiquement par le script git) qui passe profile_type à 50 caractères et rend uid unique. La contrainte n'est posée que s'il n'y a aucun doublon : le démarrage ne peut pas échouer à cause des données. Aucun code Java ne change (sauf la longueur déclarée sur l'entité, section 2).

# 1. Créer le script Flyway au numéro suivant (calculé automatiquement)
cd fund-management-container/src/main/resources/db/migration
N=$(ls V*__*.sql | sed -E 's/^V([0-9]+)__.*/\1/' | sort -n | tail -1)
FICHIER="V$((N+1))__user_profile_profile_type_uid_unique.sql"

cat > "$FICHIER" <<'SQL'
-- AER_LM-353 : synchronisation des profils utilisateurs
-- 1) profile_type passe de 10 à 50 caractères : utilisateurs-ci envoie STANDARD_USER, PROFILE_ADMIN, SUPER_ADMIN (> 10)
--    -> la synchronisation échouait ("valeur trop longue pour le type character varying(10)") et le DA n'était jamais créé.
ALTER TABLE user_profile ALTER COLUMN profile_type TYPE VARCHAR(50);

-- 2) uid unique. Ajoutée seulement si aucun doublon n'existe (le déploiement ne peut pas échouer à cause des données) ;
--    sinon un WARNING est écrit dans le log de démarrage et les doublons sont à traiter avant un nouveau script.
DO $$
BEGIN
    IF EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'uk_user_profile_uid') THEN
        RAISE NOTICE 'uk_user_profile_uid existe déjà';
    ELSIF EXISTS (SELECT uid FROM user_profile WHERE uid IS NOT NULL GROUP BY uid HAVING count(*) > 1) THEN
        RAISE WARNING 'user_profile : uid en doublon, contrainte uk_user_profile_uid non créée';
    ELSE
        ALTER TABLE user_profile ADD CONSTRAINT uk_user_profile_uid UNIQUE (uid);
    END IF;
END $$;

5. Évolution PO : colonne « Vidage seul » (export GAB)

Demande PO : nouvelle colonne juste après Statut (L) → colonne M « Vidage seul » : Oui si le vidage est activé sur le GAB, sinon Non. Les cassettes passent de M-P à N-Q, le Total Alim. GAB de Q à R.
remplirGab / ecrireLigneGab servent aux deux exports (GAB hors site et onglet GAB de l'extraction Caisse Centrale, même structure par conception) : les deux templates reçoivent la colonne, sinon les cassettes de l'export Caisse Centrale seraient décalées.

Fichiers : Template_QlickFlow_GesFond_GAB-Hors-Site.xlsx et le template de l'extraction Caisse Centrale (onglet GAB Hors Sites), dans les ressources export/ de fund-management-application.
  1. Clic droit sur l'en-tête de colonne M → Insérer. Excel décale cassettes et Total, met à jour la formule du Total (ligne 4) et la fusion « Alimentation GAB (MAD) ».
  2. Pinceau (Reproduire la mise en forme) depuis L3 → clic sur M3 → saisir Vidage seul. Même pinceau L4 → M4 pour la ligne modèle.

  4. Enregistrer au format .xlsx (même nom).
