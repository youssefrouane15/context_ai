2Ce qu'est une external task, côté moteur

Quand le jeton d'une instance arrive sur une service task marquée camunda:type="external", le moteur n'exécute rien. Il crée une ligne dans sa table ACT_RU_EXT_TASK et le jeton attend. Cette ligne, c'est l'external task :

Colonne (simplifiée)ContenuRôle
TOPIC_NAMEgdf-initialiser-demandeLe nom de la file. Copié tel quel depuis l'attribut camunda:topic du BPMN.
TENANT_IDqlickflowLe tenant de l'instance (celui du déploiement).
WORKER_IDnull → fund-management-localQui a verrouillé la tâche. null = disponible.
LOCK_EXP_TIMEnull → maintenant + 30 sJusqu'à quand le verrou tient. Passé ce délai : redevient disponible.
RETRIESnull → 3 → 2 → 1 → 0null = jamais tentée. 0 = incident.
ERROR_MSGnotre message d'exceptionAffiché dans Cockpit.
PROC_INST_ID, BUSINESS_KEYid d'instance, UUID de la demandeCorrélation vers notre base.
La tâche est une donnée, pas un appel. Elle attend passivement que quelqu'un vienne la chercher. C'est ce qui rend le système robuste : si personne ne vient (notre app est down), rien ne se perd — la ligne attend.

4fetchAndLock : la requête qui fait tout

C'est LA requête à comprendre. Notre client l'envoie en boucle, et elle porte trois informations : qui je suis, quels topics je sais traiter, combien de temps je garde ce que je prends.

Ce que la lib envoie réellement au moteur (généré par ExternalTaskClient à partir de nos subscribe(...))

Long polling, expliqué simplement

Polling classique (naïf) : Long polling (ce qu'on utilise) : nous → "du travail ?" nous → "du travail ?" ─┐ moteur → "non" (0,1 s) moteur … attend … │ jusqu'à 20 s, nous → "du travail ?" moteur … attend … │ la connexion reste moteur → "non" (0,1 s) [une tâche apparaît] │ OUVERTE nous → "du travail ?" moteur → "OUI, tiens" ◄┘ réponse IMMÉDIATE → des milliers de requêtes à vide → quasi zéro requête à vide, latence ~0
La synchronisation, c'est ça : il n'y a ni file de messages, ni webhook, ni horloge partagée. Le moteur dépose ; nous demandons en continu avec une question qui reste ouverte 20 s. Si rien n'arrive en 20 s, réponse vide, on redemande aussitôt. Si une tâche arrive, on l'a dans la seconde. disableBackoffStrategy() dans notre config = « ne ralentis jamais le rythme, même quand c'est calme ».

6Dans la JVM : ce que fait vraiment ExternalTaskClient

GdfWorkerConfig.demarrerAbonnements() [thread principal Spring, au ApplicationReadyEvent] │ ├─ ExternalTaskClient.create()...build() → crée l'objet + UN thread dédié "TopicSubscriptionManager" │ ├─ client.subscribe("gdf-…").handler(h).open() × 9 → enregistre 9 (topic → handler) dans le manager │ └─ retour. Le thread principal continue sa vie (Tomcat sert les requêtes HTTP normalement). Thread "TopicSubscriptionManager" [1 seul thread, boucle infinie tant que client.stop() n'est pas appelé] while (running) { 1. construit UN fetchAndLock avec les 9 topics 2. envoie, attend (≤ 20 s) 3. pour chaque tâche reçue, DANS CE MÊME THREAD : handler.execute(task, service) ← notre code s'exécute ICI 4. recommence }
ConséquenceCe que ça implique pour nous
Les handlers s'exécutent séquentiellement, dans le thread de pollingUn handler lent bloque les autres topics. Les nôtres sont courts (calcul + 1 requête SQL). Si un jour un handler doit durer > 30 s : soit extendLock, soit déléguer à un executor.
Ce thread n'est PAS un thread web SpringPas de RequestContext, pas de session HTTP, pas d'utilisateur connecté. Un handler qui aurait besoin de « l'utilisateur courant » n'en a pas — normal, c'est le moteur qui agit.
Les handlers sont des beans SpringInjection normale (CashDemandUseCase…), @Transactional des use cases fonctionne (la transaction est ouverte dans le thread courant, quel qu'il soit).
Une exception non attrapée tuerait le threadD'où le try/catch générique dans abonner() : on convertit TOUTE exception en handleFailure. Le thread survit, la tâche part en retry.
Le verrou peut expirer avant la finSi un handler dépasse 30 s (ou si le pod meurt), un autre worker peut reprendre la tâche → exécution en double possible. Nos handlers doivent être idempotents (voir §8).

8Idempotence : la règle d'or des handlers

Parce qu'une tâche peut être exécutée deux fois (verrou expiré, crash après le traitement mais avant le complete), chaque handler doit donner le même résultat s'il est rejoué.

HandlerRejoué deux fois → ?Verdict
Initialiser / Reporter / Normaliser / ClôturerJournéeRecalcule les mêmes variables✔ idempotent par nature
CloturerDemande → changerStatut(VALIDATED)Ré-écrit VALIDATED sur VALIDATED✔ idempotent
AnnulerDemande → cancel(id)2ᵉ appel : notre use case refuse (« déjà annulée ») → exception → retries → incident✘ à durcir : dans le handler, si la demande est déjà CANCELLED, considérer comme OK et compléter
Durcissement recommandé — AnnulerDemandeHandler (retail, même chose corpo)
try {
    cashDemandUseCase.cancel(demandeId);
} catch (RetailConflictException dejaAnnulee) {
    log.warn("[gdf-annuler-demande] demande {} déjà annulée — rejeu toléré", demandeId);
}
service.complete(task);

9L'intégration Spring, pièce par pièce

PièceMécanisme SpringPourquoi comme ça
CamundaProperties@ConfigurationProperties(prefix="camunda") + @ComponentBinding du bloc camunda: du yaml (colonne 0 !). Une seule source de config pour les deux canaux.
CamundaRestClientConfig@Bean RestClient avec baseUrlCanal 1. Un RestClient pré-réglé, les appels n'écrivent que des chemins relatifs.
CamundaEngineClient@ComponentSeule classe qui connaît les URLs Camunda + le typage des variables.
CamundaWorkflowAdapter@Component implements ProcessusWorkflowPortLe domaine dépend du port (interface dans application-service) ; Spring injecte l'adapter. Inversion de dépendance.
Handlers@Component implements ExternalTaskHandlerBeans injectables, qui injectent eux-mêmes les use cases.
GdfWorkerConfig@Component + @EventListener(ApplicationReadyEvent) + @PreDestroyLe worker démarre quand TOUT est prêt (base, use cases) — pas pendant la construction du contexte. Pas de @Bean pour le client : il n'existe que si enabled=true.
Flag camunda.worker.enabledLu au ApplicationReadyEventtrue en run, false dans src/test/resources : les tests d'intégration démarrent sans moteur.
Arrêt@PreDestroy → client.stop()Le thread de polling s'arrête proprement au shutdown (sinon le pod met du temps à mourir sur OpenShift).
Pourquoi PAS le starter Spring Boot Camunda (external-task-client-spring-boot-starter) ? Il aurait fait la même chose avec des annotations @ExternalTaskSubscription, mais il impose un alignement de versions Spring Boot ↔ Camunda et une magie de configuration. La lib nue + 60 lignes de GdfWorkerConfig = même résultat, zéro surprise, tout visible.

11candidateGroups : ce que c'est, ce que ce n'est pas

Une user task est un point d'attente humain. Le BPMN dit qui a le droit de la prendre via camunda:candidateGroups="CAISSE_CENTRALE". Le moteur stocke ce groupe comme une simple chaîne de caractères dans sa table des tâches (ACT_RU_IDENTITYLINK). C'est tout.

User task "Traiter la demande" candidateGroups = CAISSE_CENTRALE │ "Qui peut la voir ?" ▼ "Qui l'a prise ?" GET /task?candidateGroup=CAISSE_CENTRALE POST /task/{id}/claim {userId} → assignee = j43709 → liste des tâches ouvertes pour ce groupe POST /task/{id}/complete {variables}
Ce que candidateGroups FAITCe qu'il NE FAIT PAS
Étiquette la tâche avec un ou plusieurs noms de groupeVérifier que l'utilisateur appartient au groupe (sur un moteur partagé, l'autorisation Camunda est en général désactivée pour les appels REST techniques)
Permet de FILTRER les tâches par groupe (corbeille)Connaître nos utilisateurs, nos profils, nos agences
Fonctionne sans aucune configuration d'identité côté moteurRemplacer notre propre gestion des habilitations
Conclusion structurante : le moteur ne sait pas qui est j43709. C'est notre backend qui doit dire « cet utilisateur a le profil X, donc il voit les tâches du groupe Y et a le droit de les compléter ». Le groupe Camunda n'est qu'un mot de passe de filtrage, pas un système d'habilitation.

12.3 Comment le micro-frontend reçoit l'identité (Module Federation)

OptionMécanismeAvis
A. Service partagé singleton (recommandé)Le shell expose une lib @qlickflow/session (ou équivalent) déclarée shared: { singleton: true } dans les deux webpack.config. Le MFE injecte SessionService et lit uid, profils, agence. Une seule instance en mémoire, partagée.Propre, typé, pas de duplication d'état. B. Intercepteur HTTP du shellLe shell fournit un HttpInterceptor partagé qui pose le JWT sur toutes les requêtes. Le MFE n'a rien à faire pour l'auth ; le backend lit le token.Indispensable de toute façon pour sécuriser nos endpoints. Complémentaire de A (A pour l'affichage/UX, B pour la sécurité).

Règle de sécurité : ce que le front connaît (profils, uid) sert à afficher (montrer ou cacher les corbeilles). La décision (« a-t-il le droit de compléter cette tâche ? ») est toujours prise par notre backend à partir du token, jamais d'un champ envoyé par le navigateur.
