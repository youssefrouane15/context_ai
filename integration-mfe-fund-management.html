1. Verdict

L'architecture est cohérente entre les deux côtés : même nom de remote, même port, même module exposé, même type de bibliothèque (ESM), même bootstrap différé. Le squelette est bon.
Mais ça ne marchera pas en l'état, et une régression métier s'est glissée dans la PR remote :
  • RÉGRESS. La PR #6 supprime le correctif des coupures (effect scindé + synchroniserCoupures()) : le bug « saisies effacées au switch historique ↔ création » revient. Ce fichier n'a rien à faire dans une PR d'intégration MFE.
  • BLOQUANT Remote : provideHttpClient() dans les providers de la route exposée → le remote crée son propre HttpClient, sans les intercepteurs du shell → aucun jeton d'auth sur les appels /cash.
  • BLOQUANT Shell : webpack.config.js référencé dans angular.json mais absent des 19 fichiers du MR.
  • BLOQUANT Remote : seuls core / common / common/http / router sont partagés → Material, CDK, forms, platform-browser, rxjs seront chargés deux fois (overlays CDK cassés, paginator/select/dialog, tokens dupliqués).
  • BLOQUANT Shell : la route /portail est hors de toute garde, et le remote a commenté son LoginGuard → fund-management accessible sans authentification.
