Un hexagone côté front aussi :
comment fund-management-front est construit — et où vivra ta « Liste des opérations »

Bonne nouvelle : cette app Angular est organisée exactement comme le microservice Java que tu as refactoré — mêmes mots, mêmes couches, même philosophie ports & adapters. Tu connais déjà cette architecture ; ce doc te donne la correspondance, le trajet d'une donnée, et le plan précis de ta feature.

1 · La grande idée

C'est ton hexagonal backend, traduit en Angular

Regarde l'arborescence de features/fund-management et compare avec le microservice Java :

Côté front (Angular)Équivalent backend (Java)Rôle
presenter/pages/application/rest (Controller)Le point de contact avec le monde extérieur — ici l'utilisateur au lieu du HTTP entrant
domain/domain-core/entities, value-objects, aggregatorsfund-management-domain-coreLe métier pur : modèles (operation.model.ts), règles, zéro dépendance technique
domain/domain-application-servicesfund-management-application-service (use cases)L'orchestration des cas d'usage (fundManagement.service.ts)
adapters/apiAdaptersfund-management-data-access (RepositoryImpl)L'adapter technique vers le monde extérieur — HTTP au lieu de JPA (fundManagement-http.service.ts)
adapters/localState (store/query/actions/facade)≈ la base de données… mais en mémoireL'état local de la feature : le cache réactif dans lequel les composants lisent
core/guards, privileges-managerSpring Security + filtresContrôle d'accès : qui entre sur quelle route, qui voit quel bouton (is-granted)
shared/presenter/components≈ un socle communLes briques UI réutilisables : header, drawer, input, feedback-state, icons
Analogie Même immeuble, autre ville. Au backend, l'hexagone protège le métier de la base de données ; au front, il protège le métier du framework et du HTTP. Dans les deux cas la règle est identique : le domaine ne connaît personne, tout le monde connaît le domaine. Si demain l'API change (agence → corpo, tiens tiens…), seul l'adapter HTTP bouge — et c'est précisément pour ça que l'équipe a choisi ce découpage, vu la migration en cours.
2 · Le trajet d'une donnée

De l'écran au backend, aller-retour

Voici ce qui se passera quand ta page « Liste » se chargera :

COMPOSANT
(presenter)
fund-management-list.component.ts« J'ai besoin des opérations » → il appelle la façade, et affiche ce que la query lui donne. Il ne sait ni d'où viennent les données, ni comment.
↓
FAÇADE
(localState)
fundMangement.facade.tsLe guichet unique de la feature : il expose loadOperations() et les observables. C'est LE seul fichier que le composant importe.
↓
SERVICE MÉTIER
(domain)
fundManagement.service.tsLe cas d'usage : il coordonne, applique les règles éventuelles (tri métier, mapping), et délègue la technique à l'adapter.
↓
ADAPTER HTTP
(apiAdapters)
fundManagement-http.service.tsLe seul qui connaît les URLs : GET /cash vers le microservice (via le proxy en dev). Il traduit le JSON de l'API en modèles du domaine.
↓  réponse  ↑
STORE + QUERY
(localState)
fundMangement.store.ts / query.tsLa réponse est rangée dans le store (l'état) ; la query expose des flux filtrés/triés ; le composant, abonné, se met à jour tout seul. Réactif de bout en bout.
La règle d'or Un composant n'appelle jamais l'adapter HTTP directement, et ne stocke jamais dans ses attributs des données qui appartiennent à la feature. Il demande à la façade, il lit la query. Toute la testabilité du front (comme celle du backend avec les ports mockés) repose là-dessus.
3 · Ta feature

La « Liste des opérations » : où elle vit, ce qu'on va créer

D'après le partage convenu (ton collègue : le formulaire de saisie vu dans les maquettes — caisse, GAB, ramassage, devises ; toi : la consultation), ta partie couvre : lister les demandes/opérations existantes avec leur statut, et probablement le point d'entrée vers le détail et l'annulation. Côté API, terrain connu — c'est le contrat de l'ancienne version agence que tu as toi-même refactorée : GET /cash (liste), GET /cash/{id}, PATCH /cash/{id}/cancel, PATCH /cash/{id}/operations/cancel.

Les fichiers à créer / modifier

FichierActionContenu
presenter/pages/fund-management-list/
(component .ts/.html/.scss/.spec)		CRÉERLa page liste : tableau des demandes, statuts, filtres, actions. S'appuie sur les composants shared (header, input, feedback-state pour vide/erreur/chargement)
fund-management.routes.tsMODIFIERAjouter la route list, protégée par les guards existants, selon le pattern du fichier
domain-core/entities/ (ex. cash-request.model.ts)CRÉERLe modèle de la demande (aligné sur le CashRequestDTO de l'API agence : id, statut, opérations…) — operation.model.ts existe déjà, on le complète
adapters/apiAdapters/fundManagement-http.service.tsMODIFIERAjouter getAll() → GET /cash (+ cancel si l'action est dans ta partie)
adapters/localState/ (store, query, actions, facade)MODIFIERÉtat operations[] + loading/error, action de chargement, sélecteurs, méthode loadOperations() dans la façade
domain-application-services/.../fundManagement.service.tsMODIFIERLe cas d'usage « charger la liste » entre façade et adapter
shared/.../feedback-stateRÉUTILISERPour les états liste vide / erreur réseau / chargement — ne pas réinventer
core/privileges-manager/is-granted.directiveRÉUTILISERMasquer l'action « Annuler » selon les droits, comme le reste de l'app

⚠️ Le point de coordination avec ton collègue : vous partagez le même localState

Lui écrit dans le store (création de demande), toi tu le lis (liste). Décidez ensemble maintenant de la forme de l'état (une seule collection cashRequests ? statuts normalisés ? qui déclenche le rechargement après une création ?) — sinon vous vous marcherez dessus au premier merge. Même logique que les décisions de merge corpo/retail côté backend : 10 minutes à deux, des heures économisées.
