Fix — Modification d'une demande : contrainte SQL sur IN_MODIFICATION et enregistrement d'un brouillon en 409

fund-management (Flyway V6) · fund-management-front (composant écran) · 23/09/2026 · 2 corrections, 10 min

1. Diagnostic

SymptômeCause
Demande En attente → Modifier la demande → « Impossible de passer en modification ». Console : SQLState 23514, la ligne viole chk_retail_request_status ; saga debut-modification ÉCHEC de « Pose du verrou de modification ».La contrainte CHECK de retail.cash_request.request_status date d'avant AER_LM-267 : elle liste INITIATED / SUBMITTED / VALIDATED / CANCELLED et pas IN_MODIFICATION. Le domaine et le BPMN v4.1 connaissent ce statut, la base non. La saga compense correctement (la demande reste SUBMITTED), mais aucune modification n'est possible.
Brouillon (Initiée) → Modifier → Enregistrer → « [409] La demande n'est pas en cours de modification (statut actuel : INITIATED) ». Le contenu est pourtant bien enregistré (le PUT passe).Le brouillon se modifie sans verrou (PUT direct), c'est voulu. Mais l'effet « retour d'enregistrement » du composant appelle ensuite PATCH /modification/end pour tout le monde ; sur un brouillon le back refuse à juste titre. Le PATCH de fin ne doit être appelé que si la demande était EN_MODIFICATION.

-- AER_LM-267 : IN_MODIFICATION (demande SUBMITTED verrouillée par un agent pendant sa modification)
-- Aligne la contrainte de statut sur l'enum RequestStatus du domaine et sur le BPMN v4.1.
ALTER TABLE retail.cash_request DROP CONSTRAINT IF EXISTS chk_retail_request_status;

ALTER TABLE retail.cash_request
    ADD CONSTRAINT chk_retail_request_status
    CHECK (request_status IN ('INITIATED', 'SUBMITTED', 'IN_MODIFICATION', 'VALIDATED', 'CANCELLED'));

Liste = RequestStatus { INITIATED, VALIDATED, CANCELLED, SUBMITTED, IN_MODIFICATION }, rien d'autre. Si le contrôle ci-dessus montre une valeur supplémentaire dans la contrainte actuelle (héritage corpo), garde-la dans la liste. Redémarre fund-management : Flyway applique V6 (log Migrating schema "retail" to version "6"). Rien à changer côté entité : request_status est déjà un varchar.

3. Front : fin de modification uniquement pour une demande verrouillée

fund-management.component.ts — effet « retour d'enregistrement » (bloc (6) du lot C) ÉDITION

fund-management-front\src\app\features\fund-management\presenter\pages\fund-management\fund-management.component.ts (Ctrl+F : terminerModification(this.idDemande, true))

      this.facade.acquitterModification();
      if (!this.idDemande) { return; }

      // Brouillon (INITIEE) : le PUT suffit, il n'y a pas de verrou à rendre.

Remplace, dans l'effet, les trois lignes qui vont de const fin = await this.actions.terminerModification(this.idDemande, true); jusqu'au this.router.navigate(...) inclus. Le reste de l'effet (lecture des signaux succès / erreur, acquitterModification()) ne change pas. abandonnerModification() fait déjà cette distinction, c'est le même test.
