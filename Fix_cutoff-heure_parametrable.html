Fix — heure de cut-off paramétrable : gdf.cutoff-heure

fund-management (application + external-services + container) · 23/09/2026 · 3 blocs, 5 min · permet de rejouer la modification agence après 16h00 pour la démo

1. Où le 16h00 est codé en dur

EndroitEffet
CutoffPolicy.HEURE_CUTOFF = LocalTime.of(16, 0) (application)Calcule journeeCloturee à chaque lecture : bandeau « Lecture seule » à l'écran, 409 « Journée clôturée » sur modification / annulation agence.
InitialiserDemandeHandler : LocalTime.of(16, 0) (external-services)Pose dateCutoff16h sur l'instance : le boundary timer déclenche gdf-cloturer-journee. Non interruptif : il ne bloque rien côté back, c'est la CutoffPolicy qui fait foi pour l'écran.

Une seule propriété pour les deux, valeur par défaut 16:00, surchargée en local pour la démo. Comme gdf.verrou-modification-duree.

2. Propriété

application.yml (container) — bloc gdf ÉDITION

fund-management-container\src\main\resources\application.yml (Ctrl+F : verrou-modification-duree)

gdf:
  verrou-modification-duree: PT30M   # ISO-8601, lu par CashDemandUseCaseImpl et transmis au timer BPMN
  cutoff-heure: "23:30"              # HH:mm, heure JVM. Valeur métier 16:00 — 23:30 uniquement pour la démo, à remettre ensuite

La JVM tourne en UTC+1 alors que Windows affiche UTC+0 (14:08 à l'écran = 15:08 dans les logs) : 23:30 côté JVM = 22:30 à ta montre, largement après la démo. Même valeur à mettre dans application-local.yml si le profil local surcharge le bloc gdf.

3. Back

CutoffPolicy.java FICHIER COMPLET

fund-management-application\src\main\java\com\bmci\workflow\fund\management\service\domain\retail\CutoffPolicy.java

package com.bmci.workflow.fund.management.service.domain.retail;

import com.bmci.q360.domain.retail.entity.CashRequest;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;

/**
 * Règle du cut-off (16h00 par défaut, gdf.cutoff-heure), calculée localement — même règle que dateCutoff16h côté worker.
 * Jour d'effet = jour de soumission, ou J+1 si soumise après l'heure de cut-off.
 * Une demande jamais soumise (brouillon) n'est pas concernée.
 */
@Component
public class CutoffPolicy {

    private final LocalTime heureCutoff;

    public CutoffPolicy(@Value("${gdf.cutoff-heure:16:00}") String heureCutoff) {
        this.heureCutoff = LocalTime.parse(heureCutoff);
    }

    public LocalTime heureCutoff() {
        return heureCutoff;
    }

    public boolean journeeCloturee(CashRequest demande) {
        LocalDateTime soumission = demande.getSubmittedAt();
        if (soumission == null) {
            return false;
        }
        return LocalDateTime.now().isAfter(dateCutoff16h(soumission));
    }

    public LocalDateTime dateCutoff16h(LocalDateTime soumission) {
        LocalDate jourEffet = soumission.toLocalTime().isAfter(heureCutoff)
                ? soumission.toLocalDate().plusDays(1)
                : soumission.toLocalDate();
        return jourEffet.atTime(heureCutoff);
    }
}

La constante HEURE_CUTOFF disparaît. Si un test construit new CutoffPolicy() sans argument, passe-lui new CutoffPolicy("16:00"). Si un autre code référence CutoffPolicy.HEURE_CUTOFF (Ctrl+Shift+F), remplace par cutoffPolicy.heureCutoff().

        LocalTime cutoff = LocalTime.parse(heureCutoff);

        LocalDate jourEffet = apresCutoff16 ? LocalDate.now().plusDays(1) : LocalDate.now();

Si le handler est construit avec @RequiredArgsConstructor et des champs final, garde le champ non final avec @Value : Lombok l'ignore et Spring l'injecte après construction. Redémarre fund-management.

5. Vérification

  • Une demande soumise plus tôt aujourd'hui, ouverte en consultation : plus de bandeau « Lecture seule », boutons Modifier / Annuler de retour (la règle est recalculée à la lecture, pas besoin de recréer la demande).
  • Modifier la demande → écran de modification (après le fix V6 / ALTER de la contrainte).
  • Nouvelle demande soumise : Postman GET {moteur}/process-instance/<id instance>/variables/dateCutoff16h → aujourd'hui à 23:30 (JVM).
  • Les trois demandes déjà passées par gdf-cloturer-journee à 16:00 restent utilisables : ce worker ne verrouille rien en base, seule la CutoffPolicy compte pour l'écran.
Après la démo : remettre cutoff-heure: "16:00" (ou supprimer la ligne, la valeur par défaut est 16:00). Le décalage JVM/Windows se règle à part avec -Duser.timezone=Africa/Casablanca sur fund-management et sur le moteur.
