0. Diagnostic (tes deux captures suffisent)

InstantQui écritCe qu'on voit
08:35:01.419completerTacheCaisseCentrale → figerDecisionRéponse du PATCH /complete-task : decisionAt/Par/Profil renseignés, requestStatus = SUBMITTED.
08:35:01.503worker gdf-cloturer-demande → changerStatutGET /cash/{id} : requestStatus = VALIDATED, updatedAt = …503, decision* = null.
Le worker a relu la demande avant que la photo du décideur soit commitée, puis l'a réécrite entière : decision_* repassent à NULL. Pourquoi « avant » : completerTacheCaisseCentrale est @Transactional — figerDecision est exécuté mais pas commité tant que la méthode n'est pas terminée ; or la méthode appelle ensuite Camunda (completerTache), qui crée immédiatement la tâche externe ; le worker (même JVM, autre thread, autre connexion, READ COMMITTED) la prend en quelques ms, charge la demande telle qu'elle est en base (décision NULL), pose VALIDATED et sauve ; la transaction REST commite ensuite, puis le worker termine… la dernière écriture gagne : VALIDATED sans décision. Même mécanique en annulation (worker gdf-annuler-demande, annuler()).

Contre-preuve qui valide le diagnostic : le déclassement (333) écrit les mêmes types de colonnes avec la même chaîne mapper → DTO → écran et s'affiche — parce qu'il ne déclenche aucun appel Camunda, donc aucun worker ne réécrit la ligne. La chaîne de mapping est saine ; c'est l'ordre commit / Camunda qui est faux.

fund-management-microservice\fund-management-domain\fund-management-application-service\src\main\java\com\bmci\workflow\fund\management\service\domain\retail\CashDemandUseCaseImpl.java

Seule l'annotation change, le corps de la méthode est inchangé. figerDecision est une méthode de CashDemandRepositoryImpl : elle commite dans sa propre transaction (comme figerPhotoAgence dans soumettre(), qui n'est pas transactionnelle non plus et n'a jamais eu ce bug). Si l'import org.springframework.transaction.annotation.Transactional n'est plus utilisé dans la classe, le retirer.

    /*
     * Volontairement SANS @Transactional : figerDecision doit être COMMITÉ avant l'appel Camunda.
     * completerTache() déclenche le worker (gdf-cloturer / gdf-annuler) qui relit la demande dans sa propre transaction
     * et la réécrit (statut VALIDATED/CANCELLED). Si la photo du décideur n'est pas encore commitée, il relit decision_* à NULL
     * et les réécrit à NULL : perte silencieuse (bug QA 10/11). Même ordre que soumettre() : écriture locale commitée, puis Camunda.
     */
    @Override
    public CashRequestDTO completerTacheCaisseCentrale(UUID id, DecisionCaisseCentraleDTO decision, ContexteAppelant contexte) {
Pourquoi pas l'inverse (Camunda d'abord, décision ensuite) : le worker pourrait alors commiter VALIDATED entre le find et le save de figerDecision, et c'est le statut qu'on perdrait. Écriture locale commitée → puis Camunda est l'ordre déjà retenu dans soumettre() (saga) ; on l'applique ici.
Effet de bord accepté : si Camunda échoue après figerDecision (409 tâche introuvable, 502), la photo du décideur reste posée sur une demande encore SUBMITTED ; le prochain complete-task la réécrit. Avant, le rollback l'effaçait — pour une donnée de traçabilité c'est le bon compromis face à une perte silencieuse systématique.
