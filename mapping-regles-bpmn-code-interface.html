2Concepts décodés (les 4 questions que tout le monde pose)

② Comment une external task se déclenche, techniquement ?

Le moteur ne nous appelle jamais. C'est nous qui frappons à sa porte, en permanence.

LE JETON LA BOÎTE AUX LETTRES NOTRE WORKER (thread démarré (instance BPMN) (table du moteur) à ApplicationReadyEvent) jeton arrive sur ──► le moteur DÉPOSE une tâche la service task topic = gdf-initialiser-demande état = disponible ▲ │ fetchAndLock (long polling) │ « du travail pour moi sur gdf-* ? » │ la question RESTE OUVERTE 20 s │ → réponse immédiate dès qu'une tâche arrive │ le moteur VERROUILLE la tâche ◄── notre worker la reçoit (lock 30 s, réservée pour nous) exécute le handler puis complete(variables) jeton AVANCE ◄── tâche terminée, variables posées Si le handler explose : handleFailure → retry (3× / 10 s) → INCIDENT rouge en Cockpit. Si notre pod meurt : le lock expire (30 s) → la tâche redevient disponible. Rien de perdu.
Le déclencheur, en une phrase : le trigger n'est pas un appel entrant — c'est l'arrivée du jeton sur la tâche côté moteur, combinée à notre boucle de polling (ouverte au démarrage de l'app par GdfWorkerConfig) qui ramasse la tâche dans la seconde.

② « Timer armé au démarrage » — version simple

Le timer 16h, c'est un réveil. On règle le réveil au moment où l'instance naît — pas plus tard.

PATCH /submit │ ▼ Instance créée ─────────────► le moteur RÈGLE LE RÉVEIL immédiatement │ heure de sonnerie = ${dateCutoff16h} │ ⚠ si la variable n'existe pas À CET INSTANT → crash │ │ ... la demande avance dans le circuit ... │ ▼ 16h00 : DRING ──► gdf-cloturer-journee ──► journeeCloturee = true ──► portes agence fermées
Conséquence de design : dateCutoff16h ne peut pas être calculée par une tâche du process (trop tard : le réveil est déjà en train d'être réglé). C'est pour ça que notre saga la fournit dans les variables de démarrage. Idem journeeCloturee=false : la condition des portes doit exister dès la naissance.

③ Pourquoi « TRAITEE » ? D'où sort cette valeur ?

C'est un contrat de valeurs écrit dans le BPMN. Le code Java ne la connaît pas — la gateway, si.

User task « Traiter la demande » complétée AVEC la variable decisionCaisseCentrale │ ▼ Gateway XOR du BPMN (c'est ELLE qui compare) : ${decisionCaisseCentrale == 'TRAITEE'} ──► gdf-cloturer-demande ──► VALIDATED ${decisionCaisseCentrale == 'ANNULEE'} ──► gdf-annuler-demande ──► CANCELLED autre valeur / faute de frappe ──► AUCUNE branche ne matche → le jeton se FIGE (incident gateway)
Qui pose la valeur ?Aujourd'huiDemain
decisionCaisseCentraleToi, à la main, dans Cockpit (c'est ce que tu as fait — comportement nominal, pas un contournement)Notre écran Caisse Centrale : bouton « Traiter » envoie POST /task/{id}/complete avec TRAITEE, bouton « Annuler » envoie ANNULEE + motif contrôlé (≥ 10 car.). L'utilisateur ne tape jamais la valeur.
À trancher avec le PO/Yassin : la gateway n'a pas de branche par défaut. Une valeur inattendue fige l'instance. Deux protections possibles : (a) default flow vers l'annulation dans le BPMN, (b) l'écran est la seule porte d'entrée et n'envoie que les 2 valeurs. Recommandation : les deux.

④ C'est quoi, exactement, nos compensations aujourd'hui ?

Une seule saga existe : la soumission (retail + corpo). Deux étapes, deux compensations.

Étapeexecuter()compenser() — joué SEULEMENT si une étape SUIVANTE échoue
① ChangerStatutDemandeStepGarde (INITIATED sinon conflit) puis statut → SUBMITTEDRestaure l'ancien statut (retour INITIATED)
② DemarrerProcessusStepStart de l'instance (businessKey = UUID)Supprime l'instance (DELETE /process-instance/{id})
Cas réel vécu : ① OK (SUBMITTED écrit) ② ÉCHEC (moteur KO) → l'orchestrateur rejoue ① À L'ENVERS : statut ré-écrit INITIATED → réponse 502 « la demande est restée dans son état initial » Ordre inverse toujours : exec ① ② ③ … | échec ③ → comp ② puis ① Compensation qui échoue elle-même → loggée ERROR, on continue les autres (trace pour intervention).
Et les workers ? Pas de compensation côté handlers — ce n'est pas le même outil : eux ont retries + incident (la tâche reste au moteur, rien à « défaire »). Compensation = sagas (écritures multi-systèmes). Retry = external tasks (travail rejouable).
