2GitLab CI — l'usine

L'idée en une phrase
À chaque push, un robot suit une recette écrite dans un fichier de ton repo (.gitlab-ci.yml) : il compile, lance TES tests, et emballe le tout. Si UNE étape échoue, la chaîne s'arrête — le code cassé ne va jamais plus loin.
Un pipeline = des étapes qui se suivent (et s'arrêtent au premier rouge)
build ✓→ test ✓→ package ✓
build ✓→ test ✗→ package (jamais lancé)

En haut : tout est vert, l'image part vers l'entrepôt. En bas : un test rouge = rien n'est déployé. C'est ta ceinture de sécurité — et c'est pour ça que le mvn clean verify qu'on soigne depuis des semaines compte autant.

FICHIER.gitlab-ci.yml — à la racine du repo de CODELis les commentaires : chaque ligne est expliquée
# .gitlab-ci.yml — la "recette" que le robot GitLab suit A CHAQUE push.
# 3 etapes (stages), executees dans l'ordre. Une etape rouge = tout s'arrete.

stages:
  - build        # 1. compiler
  - test         # 2. verifier
  - package      # 3. emballer (image Docker)

build-job:
  stage: build
  image: maven:3.9-eclipse-temurin-17     # l'outil dont ce job a besoin
  script:
    - mvn clean compile                   # les commandes, comme dans ton terminal

test-job:
  stage: test
  image: maven:3.9-eclipse-temurin-17
  script:
    - mvn clean verify                    # tes tests ! rouge ici = pas de deploiement

package-job:
  stage: package
  image: docker:24
  script:
    - docker build -t $REGISTRY/fund-management:$CI_COMMIT_SHORT_SHA .
    - docker push $REGISTRY/fund-management:$CI_COMMIT_SHORT_SHA
  # $CI_COMMIT_SHORT_SHA = le numero du commit (ex: a1b2c3d) :
  # chaque version a son etiquette unique, on sait toujours QUOI tourne OU.

Et « l'image Docker », c'est quoi ? Un plat préparé sous vide : ton application + tout ce qu'il lui faut pour tourner (Java, les libs...), emballés ensemble avec une étiquette (le numéro du commit : a1b2c3d). Le serveur n'a plus rien à installer — il réchauffe le plat, c'est tout. Ces plats sont stockés dans un entrepôt : le registry.

3Argo CD — le magasinier (et l'idée GitOps)

L'idée en une phrase (c'est LA grande idée : GitOps)
On ne pousse plus rien vers le serveur à la main. À la place, un repo Git de config décrit « ce qui DOIT tourner » (quelle version, combien d'exemplaires). Et Argo CD compare EN BOUCLE ce que dit Git avec ce qui tourne vraiment — dès qu'il y a un écart, il corrige. Git devient la télécommande du serveur.
La boucle d'Argo CD — comme un thermostat
Repo config« Je VEUX la version a1b2c3d, en 2 exemplaires »
→compare
Argo CD« écart détecté ! »
→corrige
Kubernetes« ce qui TOURNE vraiment »
🔁 …et il recommence, toutes les ~3 minutes, pour toujours. Un thermostat : température VOULUE (Git) vs température RÉELLE (serveur) → il chauffe ou il coupe jusqu'à égalité. Écart = OutOfSync (jaune), égalité = Synced (vert).

Conséquence géniale n°1 : déployer = modifier UNE ligne dans Git (l'étiquette de version) — avec une merge request, une revue, un historique. Conséquence n°2 : quelqu'un bidouille le serveur à la main ? Argo remet comme dans Git (selfHeal). Conséquence n°3 : revenir en arrière = git revert. Le déploiement devient aussi traçable que ton code.

FICHIERdeployment.yml — dans le repo de CONFIG (environnements/dev/)La « ligne magique » : l'étiquette de l'image = la version déployée
# deployment.yml — vit dans le REPO DE CONFIG (pas le repo du code !)
# C'est la fiche qui decrit CE QUI DOIT TOURNER. Argo CD la lit en boucle.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: fund-management
spec:
  replicas: 2                              # "je veux 2 exemplaires de l'app"
  template:
    spec:
      containers:
        - name: fund-management
          image: registry.bmci/fund-management:a1b2c3d   # <-- LA ligne magique :
          ports:                                          # changer cette etiquette
            - containerPort: 8300                         # = deployer une version
FICHIERapplication.yml — on présente le repo de config à Argo, une seule fois
# application.yml — on presente le repo de config a Argo CD, UNE fois.
# Ensuite il surveille tout seul, pour toujours.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: fund-management
spec:
  source:
    repoURL: https://gitlab.bmci/squad/fund-management-config.git   # OU regarder
    path: environnements/dev                                        # quel dossier
  destination:
    server: https://kubernetes.default.svc                          # OU deployer
    namespace: fund-management
  syncPolicy:
    automated:
      selfHeal: true      # quelqu'un bidouille le cluster a la main ? Argo REMET comme dans Git
      prune: true         # un fichier supprime de Git ? Argo supprime aussi dans le cluster
Deux repos, à ne pas confondre : le repo de CODE (ton Java + le .gitlab-ci.yml — l'usine) et le repo de CONFIG (les fichiers « je veux » — le catalogue qu'Argo surveille). Le pont entre les deux : la dernière étape du pipeline CI met à jour l'étiquette de version dans le repo de config. L'usine fabrique, met à jour le catalogue... et le magasinier fait le reste.

4Le film complet — ta journée de dev, image par image

Tu corriges un bug sur fund-management. Voici TOUT ce qui se passe :
1git push — ta correction part sur GitLab.
2GitLab voit le push → lance le pipeline : build ✓ puis test (ton mvn clean verify) ✓ puis package ✓.
3L'image fund-management:f4e5d6 est poussée à l'entrepôt (registry).
4Le pipeline met à jour le repo de config : l'étiquette passe de a1b2c3d à f4e5d6.
5Argo CD compare (dans les ~3 min) : « Git dit f4e5d6, le serveur fait tourner a1b2c3d → OutOfSync ».
6Argo synchronise : Kubernetes télécharge la nouvelle image et bascule les 2 exemplaires l'un après l'autre — jamais zéro app disponible (rolling update).
7Synced ✓ Healthy ✓ dans l'écran Argo. Ta correction est en ligne. Tu n'as touché AUCUN serveur.
8La version déployée pose problème ? git revert sur le repo de config → Argo redéploie l'ancienne. Retour arrière en 1 commit.

5Le mini-lexique (7 mots et tu suis toutes les réunions)

MotTraduction simple
PipelineLa chaîne de montage lancée à chaque push (build → test → package).
Job / StageUne machine de la chaîne / un groupe de machines qui tournent au même moment.

RegistryL'entrepôt qui stocke les images.
GitOps« Git décrit ce qui doit tourner ; un robot fait en sorte que ce soit vrai. »
Synced / OutOfSyncServeur conforme à Git / écart détecté (Argo va corriger).
Ce qu'il faut retenir en 3 phrases : GitLab CI fabrique et vérifie (l'usine — un test rouge et rien ne part). Argo CD garde le serveur conforme à ce que Git décrit (le thermostat — écart → correction, en boucle). Et toi, tu ne déploies plus jamais « sur » un serveur : tu modifies Git, le reste suit — traçable, révisable, réversible.
