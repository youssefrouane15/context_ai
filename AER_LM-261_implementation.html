1. Cadrage

AER_LM-261 — Authentification et rôles utilisateurs (Story, 13 pts, Sprint 3). « ETQ application, je veux authentifier l'utilisateur et récupérer son rôle parmi : Directeur d'agence, Chef de caisse, Caisse Centrale, Support. » Critères : l'authentification ramène identité + rôle + agence ; l'application s'en sert pour les droits sur les écrans et le parcours.

Ce qui existe déjà et qu'on ne réécrit pas

  • Identité : gateway BFF (mode oauth = CASSO, mode mock = POST /mock-auth/login?uid=) → JWT relayé en Bearer vers utilisateurs-ci → QfJwtAuthenticationConverter / QfSimplifiedAuthFilter chargent l'utilisateur en base depuis sub et construisent les authorities depuis ses permissions. Le token ne porte aucun rôle : rien à changer.
  • Modèle d'habilitations : Platform → RoleEntity (Set<Permission>) → ProfileEntity → UserEntity (+ organizationUnit). Gestion des Fonds devient simplement la 4e plateforme.
  • Profil DA (id 2, niveau AGENCE, manager) existe déjà : on lui ajoute le rôle GDF, on ne le duplique pas.
  • Canal service-à-service : GET /api/v1/internal/users/{uid} → InternalUserDTO {profile, orgaUnit}, non routé par la gateway (inaccessible de l'extérieur). C'est ce que fund-management consommera.

Ce que le front lit dans le contexte
profileCode = le rôle métier du ticket (DA, CHEF_CAISSE, CAISSE_CENTRALE, SUPPORT) · permissions = les GDF_* pour activer/masquer les actions · toutesAgences = true pour Caisse Centrale et Support · agence = null quand le profil n'est pas rattaché à une agence. Un utilisateur sans profil GDF (ex. le super admin h11111) reçoit permissions = [] : c'est au front d'afficher l'accès refusé.

3. Modèle d'habilitations (Java)

Trois éditions d'enums. Le nom des constantes est le contrat avec la base (V16) et avec le front (permissions du contexte) : ne pas le modifier après merge sans nouveau script Flyway.

Pourquoi GDF_TOUTES_AGENCES est une permission et pas une règle sur le profil
Le périmètre « toutes agences » doit être lisible par fund-management sans connaître la liste des profils. Une permission voyage dans InternalUserDTO.profile.roles[].permissions et dans le contexte ; un test ProfileEnum == CAISSE_CENTRALE dispersé dans deux repos serait le piège classique. Le filtrage par agence côté fund-management se réduit à : GDF_TOUTES_AGENCES absent ⇒ branch_code = agence.code.

4. Migration Flyway V16

Suite de V15 (colonnes agence de 271). Le script est idempotent sur les contraintes (bloc DO qui ne suppose pas les noms générés par Hibernate) et suit la convention de seed INSERT + setval.

Avant d'exécuter : deux vérifications d'une minute
  1. Comparer la liste des colonnes des deux INSERT (hab_roles, hab_profiles) avec V6 et V8 : si une colonne diffère (ex. libelle au lieu de name), aligner sur le script existant — ddl-auto: validate ne signalera pas une colonne absente d'un INSERT, Postgres le fera au démarrage de Flyway.
  2. Lancer la première requête ci-dessous : elle affiche exactement les CHECK que le bloc DO va supprimer. On attend au plus 4 lignes (2 platform, 2 permission).
Envers
Les seeds V6→V9 n'écrivent pas dans les tables _aud ; V16 non plus. Les révisions démarreront à la première modification par l'application.

5. API GET /me/context

Base : /api/v1/public/users (classe UserController, routée par la gateway via qf-admin). Un seul endpoint, lecture seule, sans @PreAuthorize.

MéthodeCheminRôle
GET/api/v1/public/users/me/contextContexte GDF de l'utilisateur du token (sub). 200 ; 404 si le uid n'existe plus en base ; 401 en amont (filtre) si absent ou inactif.

Ordre d'ajout

  1. AgenceContextDTO puis UserContextGdfDTO (nouveaux fichiers)
  2. UserMapper.toContextGdfDto
  3. UserFacade + UserFacadeImpl
  4. UserController

Contrats JSON

Pourquoi la facade passe par userService.findByUid et pas par /me
UserService.findByUid renvoie déjà Optional<UserEntity> avec profil et unité d'organisation (EAGER) : aucune requête supplémentaire. /me lève EntityNotFoundException (500 aujourd'hui, 404 avec le GlobalExceptionHandler de 271) et renvoie un UserDTO nu ; on ne reproduit pas cette incohérence, on suit le pattern getUserByUid (Optional → 200 / 404 en ApiResponse).
Rôles inactifs
Le mapper ne filtre pas RoleEntity.actif pour rester aligné avec la construction des authorities de QfJwtAuthenticationConverter (non filtrée non plus, d'après les captures). Si le tech lead veut que la désactivation d'un rôle retire ses permissions, il faut le faire aux deux endroits en même temps.
