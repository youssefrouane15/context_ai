0. Mode d'emploi

Scripts pgAdmin (base fund-management, schéma retail), local uniquement. Chaque script commence par un bloc WITH p AS (…) : tu ne saisis que là (référence, décalage en jours, statut) et tu lances tel quel ; le RETURNING affiche immédiatement les lignes touchées. Les décalages gardent la chronologie (création → soumission → décision → effet bougent ensemble) pour que les gardes du back (cut-off, « déjà traitée ») restent cohérentes.

1. Lire les colonnes

FICHIER NOUVEAUÉtape 0
dates-00-colonnes.sql
-- Étape 0 — Les colonnes de dates réellement présentes sur cash_request (noms exacts à reporter dans les scripts suivants).
-- Attendu : creation_date / submitted_at (ou submission_date) / modification_date / decision_at / date_effet (+ éventuellement validation_date, cancellation_date).
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'retail' AND table_name = 'cash_request'
  AND (data_type LIKE 'timestamp%' OR data_type = 'date')
ORDER BY ordinal_position;

2. Une demande, par référence

FICHIER NOUVEAUÉtape 1 — décaler toutes les dates de n jours
dates-01-par-ref.sql
-- Étape 1 — UNE demande, par référence : décaler TOUTES ses dates du même nombre de jours (la chronologie création → soumission → décision reste cohérente).
-- Saisis la référence et le décalage (négatif = vers le passé) dans le bloc p, rien d'autre à toucher.
-- Colonnes : adapte les noms à ceux de l'étape 0 ; supprime une ligne SET si la colonne n'existe pas chez toi.
WITH p AS (
  SELECT '20261005-1422-14'::text AS ref,
         -3                        AS jours        -- ex. -3 : la demande semble avoir été créée il y a 3 jours
)
UPDATE retail.cash_request c
SET creation_date     = c.creation_date     + make_interval(days => p.jours),
    submitted_at      = c.submitted_at      + make_interval(days => p.jours),
    modification_date = c.modification_date + make_interval(days => p.jours),
    decision_at       = c.decision_at       + make_interval(days => p.jours),
    date_effet        = c.date_effet        + make_interval(days => p.jours)
FROM p
WHERE c.unique_request_ref = p.ref
RETURNING c.unique_request_ref, c.request_status, c.creation_date, c.submitted_at, c.decision_at, c.date_effet;
FICHIER NOUVEAUÉtape 2 — poser des dates précises
dates-02-par-ref-valeurs.sql
-- Étape 2 — UNE demande, par référence : poser des dates PRÉCISES (NULL = ne pas toucher cette colonne).
-- Utile pour fabriquer un cas exact : « soumise hier 17h30 (après cut-off), date d'effet aujourd'hui, pas encore décidée ».
WITH p AS (
  SELECT '20261005-1422-14'::text                     AS ref,
         (current_date - 1 + time '09:00')::timestamp AS creation,     -- NULL pour ne pas changer
         (current_date - 1 + time '17:30')::timestamp AS soumission,   -- NULL pour ne pas changer
         NULL::timestamp                              AS decision,     -- NULL pour ne pas changer
         current_date::date                           AS effet         -- NULL pour ne pas changer
)
UPDATE retail.cash_request c
SET creation_date = COALESCE(p.creation,   c.creation_date),
    submitted_at  = COALESCE(p.soumission, c.submitted_at),
    decision_at   = COALESCE(p.decision,   c.decision_at),
    date_effet    = COALESCE(p.effet,      c.date_effet)
FROM p
WHERE c.unique_request_ref = p.ref
RETURNING c.unique_request_ref, c.request_status, c.creation_date, c.submitted_at, c.decision_at, c.date_effet;

3. En masse, par filtre

FICHIER NOUVEAUÉtape 3 — par date d'effet (aujourd'hui / hier / demain)
dates-03-par-filtre.sql

cible désigne les demandes à prendre (0 = date d'effet aujourd'hui, -1 = hier), jours le décalage à leur appliquer. Relance avec d'autres valeurs pour construire un jeu « hier / aujourd'hui / demain » en trois exécutions.

-- Étape 3 — EN MASSE, par filtre sur la date d'effet : « toutes les demandes dont la date d'effet est J → les passer à J + n ».
-- Exemples : (0, -1) = celles d'aujourd'hui passent à hier ; (-1, -1) = celles d'hier passent à avant-hier ; (0, +1) = celles d'aujourd'hui passent à demain.
-- Les autres dates suivent du même décalage pour rester cohérentes ; statut optionnel (NULL = tous).
WITH p AS (
  SELECT  0                     AS cible,     -- 0 = aujourd'hui, -1 = hier, 1 = demain (par rapport à la date d'effet)
         -1                     AS jours,     -- décalage à appliquer
         NULL::text             AS statut     -- 'SUBMITTED' | 'VALIDATED' | 'CANCELLED' | NULL (tous)
)
UPDATE retail.cash_request c
SET creation_date     = c.creation_date     + make_interval(days => p.jours),
    submitted_at      = c.submitted_at      + make_interval(days => p.jours),
    modification_date = c.modification_date + make_interval(days => p.jours),
    decision_at       = c.decision_at       + make_interval(days => p.jours),
    date_effet        = c.date_effet        + make_interval(days => p.jours)
FROM p
WHERE c.date_effet = current_date + p.cible
  AND (p.statut IS NULL OR c.request_status = p.statut)
RETURNING c.unique_request_ref, c.request_status, c.date_effet, c.submitted_at, c.decision_at;
FICHIER NOUVEAUÉtape 4 — par date de décision (KPI traitées)
dates-04-par-filtre-decision.sql
-- Étape 4 — EN MASSE, par date de décision (KPI « traitées aujourd'hui ») : « toutes les traitées décidées J → décidées J + n ».
-- Ne touche QUE decision_at (les autres dates restent) : sert à vider / remplir le KPI traitées du jour.
WITH p AS (
  SELECT  0  AS cible,   -- 0 = décidées aujourd'hui, -1 = hier
         -1  AS jours    -- décalage
)
UPDATE retail.cash_request c
SET decision_at = c.decision_at + make_interval(days => p.jours)
FROM p
WHERE c.decision_at::date = current_date + p.cible
  AND c.request_status IN ('VALIDATED', 'CANCELLED')
RETURNING c.unique_request_ref, c.request_status, c.decision_at, c.date_effet;

4. Contrôle

FICHIER NOUVEAUÉtape 5 — vue d'ensemble et comptages attendus
dates-05-controle.sql

Le second SELECT applique la règle de demain (date d'effet ≤ aujourd'hui pour en attente / urgentes). Tant que le back n'est pas modifié, les cartes affichent encore la règle actuelle (date de création) : compare les deux pour préparer le dev.

-- Contrôle — ce que les KPI et les filtres vont voir (à lancer après chaque manipulation).
SELECT unique_request_ref AS ref,
       request_status     AS statut,
       urgent,
       date_effet,
       CASE WHEN date_effet  < current_date THEN 'antérieure'
            WHEN date_effet  = current_date THEN 'aujourd''hui'
            ELSE 'future' END                    AS effet_vs_jour,
       creation_date::date  AS cree_le,
       submitted_at         AS soumise_le,
       decision_at          AS decidee_le,
       decision_par
FROM retail.cash_request
ORDER BY date_effet DESC NULLS LAST, submitted_at DESC;

-- Comptages attendus par les cartes (règle en vigueur demain : en attente / urgentes = date_effet <= aujourd'hui ; traitées = décidées aujourd'hui)
SELECT
  count(*) FILTER (WHERE request_status IN ('SUBMITTED','IN_MODIFICATION') AND date_effet <= current_date)                 AS en_attente,
  count(*) FILTER (WHERE request_status IN ('SUBMITTED','IN_MODIFICATION') AND date_effet <= current_date AND urgent)      AS urgentes,
  count(*) FILTER (WHERE request_status = 'VALIDATED' AND decision_at::date = current_date)                                 AS traitees_jour
FROM retail.cash_request;
