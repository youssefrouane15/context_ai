2. Adaptation des scripts omega

2.1 V19__create_gdf_habilitations.sql (ex-V16) — les deux CHECK

ÉDITIONBloc CHECK à remplacer dans V19
utilisateurs-ci\src\main\resources\db\migration\V19__create_gdf_habilitations.sql

Remplace le bloc « CHECK platform » existant du script (4 valeurs) par celui-ci (5 valeurs), et vérifie que les deux DROP CONSTRAINT … permission_check sont bien présents avant le premier INSERT dans hab_role_permission. Les DROP sont idempotents (IF EXISTS).

-- V19__create_gdf_habilitations.sql (ex-V16) — bloc CHECK platform : ajouter 'DC' (rôles Agent / Team Lead créés par develop V14,
-- sinon ADD CONSTRAINT échoue : « check constraint hab_roles_platform_check is violated by some row »)
ALTER TABLE hab_roles DROP CONSTRAINT IF EXISTS hab_roles_platform_check;
ALTER TABLE hab_roles
    ADD CONSTRAINT hab_roles_platform_check
        CHECK (platform IN ('CONSOLE_ADMIN', 'DTRP', 'ML_CHAB', 'DC', 'GESTION_FONDS'));

ALTER TABLE hab_roles_aud DROP CONSTRAINT IF EXISTS hab_roles_aud_platform_check;
ALTER TABLE hab_roles_aud
    ADD CONSTRAINT hab_roles_aud_platform_check
        CHECK (platform IN ('CONSOLE_ADMIN', 'DTRP', 'ML_CHAB', 'DC', 'GESTION_FONDS'));

-- CHECK permission : develop (V14/V15/V16) le recrée 3 fois avec sa liste (DTRP/MLCHAB/DC/CONSOLE_ADMIN), sans aucun GDF_*.
-- Notre V19 doit donc le SUPPRIMER (les deux tables) AVANT le premier INSERT de permission GDF_* ; l'enum Java reste la seule source de vérité.
ALTER TABLE hab_role_permission     DROP CONSTRAINT IF EXISTS hab_role_permission_permission_check;
ALTER TABLE hab_role_permission_aud DROP CONSTRAINT IF EXISTS hab_role_permission_aud_permission_check;
Pourquoi pas l'inverse (ajouter les GDF_* au CHECK) ? Develop réécrit ce CHECK à chaque nouvelle plateforme sans connaître nos permissions ; chaque merge futur casserait. Sans CHECK, l'enum Permission (validée au chargement par JPA / Envers) reste la seule liste — décision prise en 261, on la maintient. À signaler au tech lead pour que develop arrête de recréer ce CHECK.

2.2 Collision d'ids — mesure avant action

FICHIER NOUVEAUVérification des séquences (pgAdmin, base locale AVANT reset)
pgAdmin — qf_admin

La 2ᵉ requête simule les ids que develop V14-V16 prendront. Compare-les aux ids en dur de V19, V21, V25, V26.

-- pgAdmin, schéma qf_admin — AVANT de toucher nos scripts : develop insère rôles et profils par nextval(), nous par id en dur.
-- Si une séquence est à increment 1, les ids que develop va prendre (V14: 2 rôles DC + 2 profils ; V15: 1 rôle + 1 profil ; V16: 3 rôles)
-- entrent en collision avec nos ids en dur (rôles 10-12…, profils 9-11…) → duplicate key au boot.
SET search_path TO qf_admin;
SELECT sequencename, increment_by, last_value FROM pg_sequences WHERE schemaname = 'qf_admin';

-- Simulation des ids que develop obtiendra (sans consommer la séquence) :
SELECT 'hab_roles'    AS t, last_value + increment_by * g AS id_develop FROM pg_sequences, generate_series(1, 6) g WHERE sequencename = 'hab_roles_seq'
UNION ALL
SELECT 'hab_profiles', last_value + increment_by * g FROM pg_sequences, generate_series(1, 3) g WHERE sequencename = 'hab_profiles_seq'
ORDER BY 1, 2;
-- → comparer avec les ids en dur de V19 / V21 / V25 / V26. Toute égalité = script à adapter (voir §2.3).

2.3 Si collision

Deux options, je tranche pour la A :
  • A — nos scripts passent par les codes, plus par les ids : INSERT … SELECT nextval('hab_roles_seq'), … et rattachements hab_profile_role / hab_role_permission par JOIN hab_roles r ON r.name = '…' / hab_profiles p ON p.code = '…' — exactement le style de develop V15/V16, idempotent (NOT EXISTS). Plus de setval. Robuste à tous les merges suivants.
  • B — décaler nos ids en dur (ex. 100+) : rapide mais fragile (prochaine plateforme sur develop = même problème).
Les rattachements inter-scripts (V20 ajoute au rôle 8, V21 rattache l'export aux profils CC/Support, V25/V26 monétique et CC admin) suivent la même règle : par name / code. Envoie-moi V19, V21, V25, V26 (ex-V16, V18, V22, V23) en entier : je rends les 4 versions adaptées (A) dans la partie 2, avec le CHECK de 2.1 déjà intégré.
