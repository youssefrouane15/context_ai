Support multi-tenant du moteur partagé (aligné sur dérogation-tarifaire) · déroulé complet du test : démarrage → soumission → workflow → décision Caisse Centrale → compensation moteur éteint

27/08/2026 · clean install vert — on passe au test réel

1Pourquoi le tenant id

Le moteur Camunda est partagé entre plusieurs applications BMCI : chacune déploie ses processus sous un tenant (dérogation-tarifaire le fait déjà, le Modeler le demande au déploiement). Concrètement, le tenant est une étiquette d'isolation : sans elle chez nous,

OpérationRisque sans tenant
Démarrage d'instance (start by key)La définition déployée sous un tenant n'est pas trouvée par un appel sans tenant (404), ou ambiguïté si deux tenants ont la même key gestion-des-fonds.
Worker (fetchAndLock)Sans filtre, notre worker peut verrouiller des tâches d'autres applications qui utiliseraient les mêmes noms de topics — et inversement.
Corrélation de messagesLe message peut corréler une instance d'un autre tenant.
Le code ci-dessous est rétro-compatible : si camunda.tenant-id est absent ou vide, tout fonctionne comme avant (utile si ton moteur local n'a pas de tenants alors que staging en a).

2.3 CamundaEngineClient — démarrage et message tenant-aware

// REMPLACER demarrerProcessus par :
    /** POST /process-definition/key/{key}/tenant-id/{tenant}/start si tenant configuré, sinon la route sans tenant. */
    public String demarrerProcessus(String businessKey, Map<String, Object> variables) {
        Map<String, Object> corps = Map.of(
                "businessKey", businessKey,
                "variables", typerVariables(variables));

        var requete = avecTenant()
                ? camundaRestClient.post().uri("/process-definition/key/{key}/tenant-id/{tenant}/start",
                        properties.getProcessDefinitionKey(), properties.getTenantId())
                : camundaRestClient.post().uri("/process-definition/key/{key}/start",
                        properties.getProcessDefinitionKey());

        Map<?, ?> reponse = requete.contentType(MediaType.APPLICATION_JSON)
                .body(corps)
                .retrieve()
                .body(Map.class);
        return reponse == null ? null : (String) reponse.get("id");
    }

// REMPLACER correlerMessage par :
    public void correlerMessage(String nomMessage, String businessKey, Map<String, Object> variables) {
        Map<String, Object> corps = new HashMap<>();
        corps.put("messageName", nomMessage);
        corps.put("businessKey", businessKey);
        corps.put("processVariables", typerVariables(variables));
        if (avecTenant()) {
            corps.put("tenantId", properties.getTenantId());
        }
        camundaRestClient.post()
                .uri("/message")
                .contentType(MediaType.APPLICATION_JSON)
                .body(corps)
                .retrieve()
                .toBodilessEntity();
    }

// AJOUTER le helper :
    private boolean avecTenant() {
        return properties.getTenantId() != null && !properties.getTenantId().isBlank();
    }

2.4 GdfWorkerConfig — abonnements filtrés sur notre tenant

...\external\camunda\worker\GdfWorkerConfig.java — méthode abonnerÉDITION
    private void abonner(String topic, ExternalTaskHandler handler) {
        var subscription = client.subscribe(topic);
        if (properties.getTenantId() != null && !properties.getTenantId().isBlank()) {
            subscription.tenantIdIn(properties.getTenantId());
        }
        subscription
                .handler((task, service) -> {
                    try {
                        handler.execute(task, service);
                    } catch (Exception erreur) {
                        log.error("[{}] échec pour la demande {} : {}", topic, task.getBusinessKey(), erreur.getMessage(), erreur);
                        int restants = task.getRetries() == null ? RETRIES : task.getRetries() - 1;
                        service.handleFailure(task, erreur.getMessage(), erreur.toString(), restants, RETRY_TIMEOUT_MS);
                    }
                })
                .open();
    }

2.5 Déploiement du BPMN

Dans le Modeler, au moment du deploy de gestion-des-fonds.bpmn : renseigner le même Tenant ID que le yaml. C'est ce champ qui relie les deux mondes — un BPMN déployé sans tenant n'est pas visible par un appel avec tenant, et inversement.

3Plan de test de bout en bout

Chaque étape : quoi faire, pourquoi (ce qu'elle prouve), comment vérifier. Ordre strict — chaque étape suppose la précédente verte.

Étape 0 — Prérequis

Fonctionnel : rien. Technique : l'environnement complet doit être là avant tout test.

  • PostgreSQL up, schémas retail/corpo migrés (Flyway les rejoue au démarrage de l'app).
  • Moteur Camunda partagé up sur http://localhost:3030 → ouvre http://localhost:3030/camunda (Cockpit) dans le navigateur pour le confirmer.
  • mvn clean install vert (fait ✔).
  • La valeur du tenant-id est renseignée dans les deux yaml (ou vide si ton moteur local n'a pas de tenants — dans ce cas ne mets pas de tenant au deploy non plus : les deux côtés doivent être cohérents).

Étape 1 — Déployer le BPMN converti

Fonctionnel : publier le processus métier validé par le PO. Technique : rendre la définition gestion-des-fonds disponible au start-by-key, sous notre tenant.

  • Ouvre gestion-des-fonds.bpmn (la version convertie : external tasks gdf-*, zéro formData) dans le Modeler → bouton Deploy → REST endpoint http://localhost:3030/engine-rest, Tenant ID = celui du yaml.
  • Vérif : Cockpit → Processes → gestion-des-fonds apparaît, colonne tenant renseignée. Zéro instance.

Étape 2 — Démarrer le microservice et vérifier le worker

Fonctionnel : l'application est prête à traiter les étapes automatiques du workflow. Technique : le long polling du worker est ouvert sur les 9 topics, filtré sur notre tenant.

  • Run de WorkFlowFundManagementApplication (config IntelliJ habituelle avec ton yaml local).
  • Vérif logs : « Worker Camunda abonné aux 9 topics gdf-* sur http://localhost:3030/engine-rest ». Pas d'exception TASK/CLIENT.
  • Vérif négative : aucun log d'erreur répétitif de fetchAndLock (si tu en vois, l'URL ou le tenant est faux).

Étape 3 — Créer une demande retail (comme d'habitude)

Fonctionnel : l'agence saisit son brouillon — la création ne déclenche PAS le workflow, c'est voulu (le BPMN démarre à « demande saisie et soumise »). Technique : la demande naît INITIATED, aucune instance Camunda.

  • Depuis le front (formulaire) ou Postman : POST http://localhost:8300/cash avec une alimentation GAB classique (coupures MAD, totaux cohérents).
  • Vérif : 200/201, requestStatus = INITIATED, uniqueRequestRef généré. Cockpit : toujours zéro instance. Note l'id (UUID) de la réponse.

Étape 4 — Soumettre la demande (le cœur du test)

Fonctionnel : l'agence engage sa demande dans le circuit — c'est l'acte métier « soumission ». Technique : saga 2 étapes — (1) garde INITIATED puis statut SUBMITTED en base, (2) start-by-key avec businessKey = UUID et les 8 variables du contrat (dont dateCutoff16h pour le timer et journeeCloturee=false).

  • PATCH http://localhost:8300/cash/{id}/submit (remplace {id} par l'UUID noté).
  • Vérif API : 200, data.requestStatus = "SUBMITTED".
  • Vérif base : select request_status from retail.cash_request where id = '...' → SUBMITTED.
  • Vérif Cockpit : une instance de gestion-des-fonds, businessKey = l'UUID.
  • Vérif worker : log [gdf-initialiser-demande] demande {uuid} : {heureSoumission=..., apresCutoff10=..., apresCutoff16=...} — la première external task a été tirée, traitée, complétée par NOTRE service.
  • Vérif routage : dans Cockpit, le jeton est arrêté sur la user task « Traiter la demande (Caisse Centrale) » — si tu as soumis avant 16h sans urgence, il a traversé les gateways cutoff/urgence sans s'arrêter. (Soumets après 16h pour voir passer gdf-reporter-jour-suivant et la variable dateEffet.)

Étape 5 — Rejouer la soumission sur la même demande

Fonctionnel : on ne soumet pas deux fois la même demande. Technique : la garde de ChangerStatutDemandeStep (statut ≠ INITIATED → conflit), AVANT tout appel au moteur.

  • Renvoie le même PATCH /cash/{id}/submit.
  • Vérif : erreur (le code porté par ton RetailConflictException — 409/422 selon ton handler), message « Seule une demande INITIATED peut être soumise » ; Cockpit : toujours UNE seule instance.

Étape 6 — Décision Caisse Centrale : TRAITÉE

Fonctionnel : la Caisse Centrale traite la demande → statut métier final « validée ». Technique : complétion de la user task (via Cockpit, en attendant notre écran) → le process route vers gdf-cloturer-demande → notre handler rappelle changerStatut(VALIDATED) en routant retail/corpo par la variable typeDemande.

  • Cockpit → l'instance → user task « Traiter la demande » → compléter avec la variable decisionCaisseCentrale = TRAITEE (String).
  • Vérif logs : [gdf-cloturer-demande] demande {uuid} traitée par la Caisse Centrale.
  • Vérif base : request_status = VALIDATED. Vérif front : la liste affiche la chip « Validée ».
  • Vérif Cockpit : l'instance est terminée (plus dans les running instances).

Étape 7 — Décision Caisse Centrale : ANNULÉE (sur une 2ᵉ demande)

Fonctionnel : le refus Caisse Centrale annule la demande avec motif. Technique : branche opposée de la gateway décision → gdf-annuler-demande (avec origineAnnulation=CAISSE_CENTRALE en variable locale) → notre cancel(id) existant.

  • Refaire étapes 3-4 avec une nouvelle demande, puis compléter la user task avec decisionCaisseCentrale = ANNULEE et motifAnnulation = "Stock insuffisant en caisse centrale" (≥ 10 caractères, la règle du PO).
  • Vérif : log [gdf-annuler-demande] ... (origine=CAISSE_CENTRALE, motif=...), base → CANCELLED (demande + opérations), instance terminée.

Étape 8 — LE test qui compte : moteur éteint → compensation

Fonctionnel : si le workflow est indisponible, la demande de l'agence n'est PAS perdue ni bloquée dans un faux état « soumise ». Technique : l'étape 2 de la saga échoue → l'orchestrateur compense l'étape 1 en ordre inverse → le statut revient INITIATED ; le handler HTTP traduit en 502 avec message stable.

  • Arrête le moteur Camunda (ou coupe son port). Crée une 3ᵉ demande, puis PATCH /cash/{id}/submit.
  • Vérif API : 502, « La soumission a échoué (workflow indisponible) ; la demande est restée dans son état initial. »
  • Vérif logs : Saga [soumission-demande] > ÉCHEC de 'Démarrage du processus...' → compensation de 1 étape(s) → compensation de : Passage du statut à SUBMITTED.
  • Vérif base : request_status = INITIATED — l'utilisateur peut re-soumettre plus tard.
  • Redémarre le moteur, re-soumets la même demande → 200, instance créée : la reprise marche.

Étape 9 — Corpo

Fonctionnel : le circuit corporate (natures 5/6) va directement à la Caisse Centrale, sans circuit urgence. Technique : mêmes sagas côté corpo, variables typeDemande=CORPORATE / typeAgence=CENTRE_AFFAIRES → la gateway type route directement.

  • POST /corpo/cash puis PATCH /corpo/cash/{id}/submit.
  • Vérif : SUBMITTED, instance Cockpit dont le jeton est DIRECTEMENT sur la user task Caisse Centrale (pas de passage par les nœuds urgence/cutoff10) ; compléter TRAITEE → VALIDATED corpo en base.

Étape 10 — Timer 16h (optionnel mais instructif)

Fonctionnel : à 16h, les agences perdent la main. Technique : le timer ${dateCutoff16h} (variable fournie AU DÉMARRAGE par notre saga) déclenche le sous-processus → gdf-cloturer-journee → notre handler pose journeeCloturee=true, ce qui verrouille les conditions ${!journeeCloturee} des sous-processus annulation/modification.

  • Pour ne pas attendre 16h : dans DemarrerProcessusStep, remplace temporairement LocalDate.now().atTime(16, 0) par LocalDateTime.now().plusMinutes(2), redémarre, soumets, attends 2 minutes.
  • Vérif : log [gdf-cloturer-journee] ... verrouillage des actions agence et, dans Cockpit, variable journeeCloturee=true sur l'instance. Remets le code d'origine ensuite.
Grille de lecture des incidents : si une external task échoue 3 fois (bug dans un handler), elle devient un incident visible en rouge dans Cockpit sur le nœud concerné — le message d'erreur y est celui de notre exception. Corriger, puis « Retry » sur l'incident : la tâche repart. C'est le comportement voulu (pas de perte, pas de blocage silencieux).
