1. Diagnostic (ce que disent les logs)

SymptômeCause
Saga initier-demande : « Démarrage du processus » OK, puis ÉCHEC de « Complétion de la user task Task_InitierDemande », puis compensation avec OptimisticLockingException sur DELETE ExternalTaskEntity.Le moteur exécute encore le BPMN v3.0 : en v3 le processus part directement sur l'external task Task_InitialiserDemande, et la user task Task_InitierDemande n'existe pas. En v4.1 la première étape est cette user task. Le v4.1 n'a jamais été déployé (point PENDING du doc v4).
Worker gdf-initialiser-demande : TASK/CLIENT-01025 Cannot serialize variable 'dateCutoff16h', cause Java 8 date/time type java.time.OffsetDateTime not supported.Le client external-task (camunda-external-task-client 7.21) sérialise une Map<String,Object> avec son propre Jackson, sans module JSR-310. Mon bloc livré le 22/09 passait un OffsetDateTime ; la note disait que le client le typait en Date comme DemarrerProcessusStep — faux, DemarrerProcessusStep passe par notre typerVariables REST. À corriger avant tout : sinon toute demande soumise reste bloquée sur ce worker même après le déploiement v4.1.

Les deux se cumulent : les instances v3 bloquées font tourner le worker en échec en boucle (une erreur par cycle d'acquisition), ce qui a aussi produit le conflit optimiste pendant la compensation.

2. Étape 1 — corriger le worker

InitialiserDemandeHandler.java — dateCutoff16h en java.util.Date ÉDITION

fund-management-external-services\src\main\java\com\bmci\workflow\fund\management\external\camunda\worker\InitialiserDemandeHandler.java (Ctrl+F : dateCutoff16h)

        // AER_LM-273 : le chemin cutoff 10h / Banque Privée est hors MVP → jamais emprunté.
        boolean apresCutoff10 = false;
        boolean apresCutoff16 = LocalTime.now().isAfter(LocalTime.of(16, 0));
        // AER_LM-267 : le boundary timer 16h00 s'arme à l'entrée de SubProcess_Traitement avec cette date
        // (jour d'effet = aujourd'hui, ou demain si soumise après 16h00 — même règle que CutoffPolicy).
        // java.util.Date : seul type date que le client external-task sérialise nativement (DateValue).
        LocalDate jourEffet = apresCutoff16 ? LocalDate.now().plusDays(1) : LocalDate.now();
        Date dateCutoff16h = Date.from(jourEffet.atTime(16, 0).atZone(ZoneId.systemDefault()).toInstant());

        Map<String, Object> variables = new HashMap<>();
        variables.put("heureSoumission", OffsetDateTime.now().toString());
        variables.put("apresCutoff10", apresCutoff10);
        variables.put("apresCutoff16", apresCutoff16);
        variables.put("dateCutoff16h", dateCutoff16h);
        service.complete(task, variables);

Remplace le bloc de calcul existant (même périmètre que l'édition du 22/09). Import à ajouter : import java.util.Date;. Le timer ${dateCutoff16h} du BPMN accepte une Date. Puis redémarre fund-management.

Regarde versionTag dans la réponse : "4.1" → passe à l'étape 4 ; "3.0" (ton cas) → étape 3.

4. Étape 3 — déployer le BPMN v4.1

Postman, POST :

http://localhost:3030/engine-rest/deployment/create

Onglet Body → form-data, quatre lignes :

KeyTypeValue

enable-duplicate-filteringTexttrue
tenant-idTextle tenant que fund-management envoie au moteur (même valeur que la propriété tenant du bloc camunda de son application.yml). Si fund-management n'envoie pas de tenant, supprime cette ligne.

Réponse 200 : deployedProcessDefinitions contient une définition avec "versionTag": "4.1". Rejoue le GET de l'étape 2 pour confirmer que c'est elle la dernière.

Le tenant doit être identique à celui de fund-management, sinon le démarrage de processus retombe sur la v3 (ou en 404 « no process definition »). Le moteur est en H2 fichier (./camunda-h2-database) : le déploiement est persistant entre deux redémarrages.

5. Étape 4 — purger les instances v3 et les demandes

Postman, GET :

http://localhost:3030/engine-rest/process-instance?processDefinitionKey=gestion-des-fonds

Pour chaque id de la réponse, DELETE :

http://localhost:3030/engine-rest/process-instance/<id>?skipCustomListeners=true

S'il y en a beaucoup, une seule requête POST http://localhost:3030/engine-rest/process-instance/delete avec le corps :

{ "processInstanceIds": ["<id1>", "<id2>"], "deleteReason": "purge v3", "skipCustomListeners": true }

Puis pgAdmin :

DELETE FROM retail.cash_operation;
DELETE FROM retail.cash_request;

Sans cette purge, le worker continue d'échouer en boucle sur les anciennes external tasks et la console reste rouge même quand tout est corrigé.
