Fix — statut jamais mis à jour après Traiter / Annuler (moteur Camunda partagé)

camunda.worker.instance · DemarrerProcessusStep (variable instanceFundManagement) · GdfWorkerConfig (processVariableEquals) · 16/11/2026

0. Cause

Le moteur Camunda DEV (derrière Apigee) est partagé : tous les fund-management qui s'y branchent (pod DMZR + le poste local de chaque développeur, car application-local.yaml pointe sur Apigee DEV) s'abonnent aux mêmes topics gdf-*, même tenant QLICKFLOW, et aucun filtre ne dit à qui appartient une tâche (GdfWorkerConfig.abonner : seul tenantIdIn).
Quand la Caisse Centrale traite / annule, la tâche externe gdf-cloturer-demande / gdf-annuler-demande est prise par le premier worker qui interroge le moteur. Si ce n'est pas le pod DMZR, ce worker ne trouve pas la demande dans sa base → exception → handleFailure (3 essais, 10 s) → au 3ᵉ échec : incident, la tâche n'est plus proposée à personne. Résultat : l'écran reste « En attente » pour toujours, et le re-clic donne 409 (la tâche Caisse Centrale est déjà complétée) ou 502 (l'annulation est déjà partie).
Ton log de 11:05:26 (statut écrit 85 s après le clic, par ton poste local) en est la trace ; arrêter ton poste ne suffit pas, n'importe quel autre fund-management branché sur le moteur DEV fait pareil. Comme worker-id est figé à fund-management-local dans application.yaml, tous les workers ont le même nom : impossible de les distinguer dans le moteur.

Fix : chaque fund-management a une instance (camunda.worker.instance) ; DemarrerProcessusStep la pose sur le processus (variable instanceFundManagement) et le worker ne s'abonne qu'aux tâches dont le processus porte sa valeur (processVariableEquals du client Camunda). Aucun changement BPMN, front, base ni Apigee.

4. Déploiement et recette

FICHIER NOUVEAUParcours
recette\worker-camunda-instance.txt
0. PREUVE DE LA CAUSE (avant le déploiement, 1 min)
   Cockpit DMZR (https://webapp.socle-bpm-ma.ac.dev.echonet/) → Processes → gestion-des-fonds → instance de la demande monétique bloquée.
   Attendu : un INCIDENT sur « gdf-cloturer-demande » (ou gdf-annuler-demande) avec le message
   « La demande <id> est introuvable » → un AUTRE fund-management (base différente) a pris la tâche, a échoué 3 fois, la tâche est morte.

1. DÉPLOIEMENT
   - Variable Helm du pod DMZR dev : QF_CAMUNDA_INSTANCE=fund-management-dev   (staging : fund-management-staging, prod : fund-management-prod)
     Ne JAMAIS changer cette valeur ensuite : les processus démarrés avec l'ancienne valeur ne seraient plus pris par personne.
   - En local : rien à faire (valeur par défaut local-<ton uid Windows>, donc distincte pour chaque développeur).
   - Toute l'équipe doit récupérer ce commit : un fund-management local SANS ce correctif (Hamza, Yassine…) continue de voler
     toutes les tâches du moteur DEV (application-local.yaml pointe sur Apigee DEV).

2. VÉRIFICATION AU DÉMARRAGE (log fund-management)
   « Worker Camunda abonné aux 9 topics gdf-* sur … (workerId fund-management-dev, instance fund-management-dev) »

3. RECETTE ÉCRAN (DMZR) — sur des demandes CRÉÉES APRÈS le déploiement
   a. Agence : créer + soumettre une demande ; Caisse Centrale : Traiter → statut « Traitée » en 1 à 2 s.
   b. Une 2e demande : Caisse Centrale Annuler (motif) → « Annulée » en 1 à 2 s.
   c. Agence : annuler une demande soumise → « Annulée » en 1 à 2 s.
   d. Monétique : même chose (Traiter puis Annuler).
   e. Cockpit : variable « instanceFundManagement = fund-management-dev » sur les nouvelles instances, aucun incident.

4. DÉBLOQUER LES DEMANDES DÉJÀ EN COURS SUR DEV (Postman, collection Apigee, base https://morocco.apigee.dev.echonet/bpm/v1)
   Pour chaque demande bloquée :
   - GET  {base}/process-instance?businessKey=<id demande>                       → id de l'instance
   - PUT  {base}/process-instance/<id instance>/variables/instanceFundManagement
          body : {"value":"fund-management-dev","type":"String"}
   - si incident : GET {base}/external-task?processInstanceId=<id instance>       → id de la tâche externe
                   PUT {base}/external-task/<id tâche>/retries   body : {"retries":3}
   → le worker DMZR la reprend dans la seconde et le statut se met à jour à l'écran.
