0. Cause

Aucune requête et aucun message au clic : la navigation est refusée en silence par une garde de fund-management-front (un canActivate qui renvoie false ou redirige vers le dashboard ne laisse aucune trace). Le portail, lui, laisse passer : AuthGuard ne teste que currentUser, et la carte s'affiche parce que *appSiPlateforme se base sur les permissions.
Pourquoi seulement pour h11111 : en V17 (21/09), les permissions GDF_CONSULTER_DEMANDE / GDF_TOUTES_AGENCES ont été ajoutées directement au rôle 8 « Super Admin », qui est de plateforme CONSOLE_ADMIN. Or fund-management-front dérive ses habilitations (deriverContexteGdf) en ne gardant que les rôles de plateforme GESTION_FONDS → pour le SA : aucune habilitation → exigePermission('consulter') refuse. Les autres profils (DA, Chef de caisse, CC, Support) ont un vrai rôle GESTION_FONDS, d'où un bug propre au SA.

Fix : rattacher au profil SA le rôle existant « GDF Support » (consultation + toutes agences, plateforme GESTION_FONDS). Aucun code front ni back à changer. Les permissions déjà posées sur le rôle 8 restent (sans effet).

-- Le Super Admin (profil SA) n'avait les permissions GDF que via le rôle 8 « Super Admin » (plateforme CONSOLE_ADMIN, V17).
-- Le portail affiche la carte (contrôle sur les permissions) mais fund-management-front ne retient que les rôles de la
-- plateforme GESTION_FONDS : le SA y arrive sans aucune habilitation et la navigation est refusée en silence.
-- Correctif : rattacher au profil SA le rôle existant « GDF Support » (consultation + toutes agences, plateforme GESTION_FONDS).
-- Idempotent, sans id en dur.
INSERT INTO hab_profile_role (profile_id, role_id)
SELECT p.id, r.id
FROM hab_profiles p, hab_roles r
WHERE p.code = 'SA'
  AND r.name = 'GDF Support'
  AND NOT EXISTS (SELECT 1 FROM hab_profile_role pr WHERE pr.profile_id = p.id AND pr.role_id = r.id);

3. Évolution — ÉDITER réservé aux utilisateurs habilités Gestion des fonds

Règle : sur chaque ligne, ÉDITER n'est actif que si l'utilisateur de la ligne a au moins une permission GDF_ dans les rôles de son profil. On réutilise extractUserPermissions (déjà utilisé par AuthService.hasPermission, même type UserDTO) : aucun nouveau type, aucun appel en plus. Le bouton reste affiché, grisé avec une infobulle ; editUser refuse aussi par sécurité.
