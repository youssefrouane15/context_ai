0. Cause

Symptôme : GET /gab/hors-site → 400 « No enum constant …Ville.CASA » (poste local) ; chez le tech lead, V21 en échec « violates check constraint chk_gab_hors_site_ville » (ligne CASABLANCA).

Cause : l'enum Ville et le seed V21 ont été passés à CASABLANCA, mais Flyway ne rejoue jamais une migration appliquée — une base où la V20/V21 d'origine (CASA) a tourné garde ses 14 lignes CASA et son ancien CHECK. Supprimer les lignes de flyway_schema_history ne suffit pas : la V20 est en create table if not exists et la V21 en NOT EXISTS, le rejeu ne touche à rien.

-- AER_LM-311 : la ville Casablanca est codée CASABLANCA (enum Ville). Aligne les bases où la V20/V21 d'origine

3. Tech lead — déblocage du déploiement

FICHIER COMPLETÀ exécuter avant de redéployer
pgAdmin / psql — base de l'environnement de déploiement

Le jar redéployé doit contenir la V21 corrigée (CASABLANCA) et la V24.

-- Environnement du tech lead : V20 appliquée avec l'ancien CHECK, V21 en échec (success = false) → la table est vide.
-- 1. Aligner le CHECK à la main (la V24 n'est atteinte qu'après V21)
alter table qf_admin.gab_hors_site drop constraint if exists chk_gab_hors_site_ville;
alter table qf_admin.gab_hors_site add constraint chk_gab_hors_site_ville
    check (ville in ('AGADIR','BERRECHID','CASABLANCA','ESSAOUIRA','FES','KENITRA','MARRAKECH','MEKNES','RABAT','SETTAT','TANGER'));
-- 2. Retirer la trace de l'échec, sinon Flyway refuse de démarrer
delete from qf_admin.flyway_schema_history where version = '21' and success = false;
-- 3. Redéployer : V21 (CASABLANCA) passe, puis V22, V23, V24 (sans effet).
