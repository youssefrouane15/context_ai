1. Les acteurs, et qui parle à qui

Six pièces, un seul principe : le navigateur ne voit jamais de JWT. Il a un cookie de session ; tout ce qui est « token » vit derrière la gateway.

2. « Session id » ou JWT ? — les deux existent, à des endroits différents

C'est le point qui embrouille, parce que le tech lead a raison et les microservices attendent un JWT. Il y a deux objets distincts :

Cookie de sessionJWT (access token)
NomQF_SESSION (mode oauth) · QF_MOCK_SESSION (mode mock)token OIDC signé (CASSO / dev-sso) ou token RS256 fabriqué par MockJwtService
Qui le détientle navigateur (cookie httpOnly : le JavaScript du portail ne peut même pas le lire)la gateway, en mémoire et dans la table oauth_session d'utilisateurs-ci
Qui l'envoiele navigateur, automatiquement, sur chaque appel vers la gatewayla gateway, dans l'en-tête Authorization: Bearer …, vers utilisateurs-ci et fund-management
Contenuun identifiant opaque de sessionsub = uid (ex. h11111), émetteur, expiration — aucun rôle
Ce que voit le micro-frontendrien à faire : withCredentials: true sur HttpClient et c'est toutjamais
Ce que voit fund-managementjamaistoujours : c'est son moyen de savoir qui appelle
La phrase à retenir
Le micro-frontend Gestion des Fonds ne « récupère » pas de token : il fait des appels HTTP vers la gateway avec le cookie, comme la Console. La gateway échange le cookie contre le JWT et le relaie. Fund-management reçoit donc bien un JWT, mais jamais depuis le navigateur — toujours depuis la gateway. Le « sessionId » dont parle le tech lead, c'est le cookie ; il est géré par le portail hôte, pas par ton micro-frontend.

3. Le parcours de connexion, pas à pas

Mode oauth (recette, prod — CASSO ; en local avec dev-sso)

1 navigateur ──► gateway GET /oauth2/authorization/qlickflow (le portail redirige ici si pas de session) 2 gateway ──► CASSO 302 vers la page de login CASSO 3 personne ──► CASSO saisit ses identifiants 4 CASSO ──► gateway 302 /login/oauth2/code/qlickflow?code=… (redirect-uri = QF_OAUTH_REDIRECT_URI) 5 gateway ──► CASSO échange le code contre access token + refresh token (client_secret_basic) 6 gateway ──► utilisateurs-ci PUT /api/v1/internal/oauth-sessions (MsUsersReactiveOauth2AuthorizedClientService {uid, accessToken, expiries, refreshToken} → table oauth_session) 7 gateway ──► navigateur Set-Cookie: QF_SESSION=… + 302 frontendBaseUrl (QfOAuth2LoginSuccessHandler) 8 navigateur ──► portail affiche l'application ; la session existe

Mode mock (poste de dev)

1 navigateur / Postman ──► gateway POST /mock-auth/login?uid=g10002 2 gateway MockJwtService.generateToken("g10002") → JWT RS256 { sub: g10002, iss: mock-auth, exp: +1h } 3 gateway PUT utilisateurs-ci /api/v1/internal/oauth-sessions (même table que le vrai login) 4 gateway Set-Cookie: QF_MOCK_SESSION=<le JWT lui-même> (httpOnly, 1h) → 204
Pourquoi la gateway démarre-t-elle seulement avec dev-sso, même en mock ?
Le bloc spring.security.oauth2.client.registration.qlickflow est chargé quel que soit le mode, et son issuer-uri pointe sur http://localhost:9001. Spring interroge /.well-known/openid-configuration au démarrage pour construire le client OAuth2. Sans dev-sso : Connection refused. En mock, dev-sso ne sert qu'à ça ; en oauth local, il joue CASSO de bout en bout (étapes 1 à 8 ci-dessus sans VPN).

4. Le parcours d'un appel API, pas à pas

Exemple : le micro-frontend Gestion des Fonds charge le contexte de l'utilisateur.

navigateur GET https://gateway/api/v1/public/users/me/context Cookie: QF_SESSION=abc │ ▼ gateway ├─ SecurityConfig : la route n'est pas publique → il faut une session valide (sinon 401) ├─ mode oauth : QfTokenRelayFilter → charge l'OAuth2AuthorizedClient (cache, sinon oauth_session), │ rafraîchit si le JWT expire dans < 30 s │ mode mock : QfMockTokenRelayFilter → lit le JWT dans le cookie QF_MOCK_SESSION ├─ AuthUtils.relayBearerToken : ajoute Authorization: Bearer <JWT> └─ route qf-admin (Path=/api/v1/public/users/**) → http://utilisateurs-ci:8091 │ ▼ utilisateurs-ci ├─ mode oauth : QfJwtDecoder valide la signature (JWKS CASSO) → QfJwtAuthenticationConverter │ mode mock : QfSimplifiedAuthFilter lit `sub` sans vérifier la signature ├─ uid = sub → SELECT users … WHERE uid = ? (utilisateur absent ou inactif → 401) ├─ authorities = permissions des rôles du profil (ex. GDF_CREER_DEMANDE, CONSOLE_ADMIN_EDIT_USER) ├─ @PreAuthorize("hasAnyAuthority(…)") sur le contrôleur (403 si la permission manque) └─ UserController.getMyContext → 200 ApiResponse<UserContextGdfDTO> │ ▼ navigateur reçoit { uid, profileCode, agence, permissions, toutesAgences }
Deux conséquences pratiques
  • Un 401 vient toujours de l'identité (pas de session, JWT expiré, utilisateur inconnu ou désactivé) ; un 403 vient toujours d'une permission manquante. Le front doit les traiter différemment : 401 → relancer le login, 403 → « accès refusé ».
  • Désactiver un utilisateur ou lui retirer un rôle dans la Console est immédiat : chaque appel relit la base. C'est la raison pour laquelle le JWT ne transporte pas les rôles.

5. Comment les habilitations sont gérées

Le modèle est celui de la Console, inchangé par 261 ; Gestion des Fonds y entre comme quatrième plateforme.

QuestionRéponse
Où sont les noms de permissions ?Dans l'enum Java Permission — c'est la seule source de vérité (V16 a supprimé le CHECK SQL qui la dupliquait). Le même nom sert d'authority Spring et de chaîne dans /me/context.
Où sont les rôles et profils ?En base (hab_roles, hab_profiles, tables de liaison), seedés par Flyway (V6→V9, V16). Administrables ensuite depuis la Console (écrans rôles/profils existants).
Qui décide qu'un utilisateur est Chef de caisse ?L'administrateur, dans la Console : il crée l'utilisateur avec le profil CHEF_CAISSE et l'agence de rattachement. Rien à faire côté CASSO.
Comment un rôle devient-il un droit ?À chaque appel, utilisateurs-ci charge profil → rôles → permissions et les pose comme authorities Spring. Les contrôleurs sont gardés par @PreAuthorize("hasAnyAuthority('…')").
Ajouter une permission plus tard ?1) constante dans Permission ; 2) script Flyway qui l'affecte à un rôle (hab_role_permission) ; 3) garde @PreAuthorize là où elle s'applique ; 4) le front la lit dans permissions. Aucun CHECK SQL à toucher.
Pourquoi GDF_TOUTES_AGENCES est une permission ?Pour que fund-management sache filtrer « mon agence / toutes » sans connaître la liste des profils. Une permission voyage dans le contexte et dans InternalUserDTO ; un test profil == CAISSE_CENTRALE dispersé dans deux repos serait le piège classique.

6. Ce que le portail et le micro-frontend en font

Le portail hôte gère la session (login, cookie, déconnexion). Ton micro-frontend Gestion des Fonds n'a qu'une chose à faire au démarrage : appeler /me/context et garder la réponse en signals. Le reste (afficher, masquer, rediriger) découle de trois champs.

ChampSert àExemple
permissionsafficher / masquer les actions, garder les routesbouton « Nouvelle demande » si GDF_CREER_DEMANDE ; écran « Décision » si GDF_TRAITER_DEMANDE
toutesAgencesactiver le filtre agence dans les listingsCaisse Centrale voit un sélecteur d'agence ; un DA non
agencepré-remplir et afficher le rattachementen-tête « Agence 1422 » ; null pour Caisse Centrale / Support
profileCodelibellé du rôle, tableau de bord par rôle« Connecté en tant que Chef de caisse »
permissions = []accès refusé à tout le moduleh11111 (super admin) : page « Vous n'avez pas accès à Gestion des Fonds »
Ce que le front ne doit jamais faire
  • Décider seul du périmètre : masquer un bouton n'est pas une sécurité. Chaque règle affichée ici doit être aussi appliquée par fund-management (section 7).
  • Stocker ou manipuler un token : pas de localStorage, pas d'en-tête Authorization ajouté à la main. Le cookie suffit.
  • Appeler utilisateurs-ci ou fund-management directement : toujours via la gateway (/api/v1/public/…), sinon pas de Bearer.
Et la Console (écrans agence / zones de distribution) ?
Même mécanique, déjà en place : le portail appelle GET /me (le UserDTO complet) et les contrôleurs orga/referentiels sont gardés par CONSOLE_ADMIN_EDIT_USER / CONSOLE_ADMIN_CREATE_USER. Les écrans 259/268/260 n'ont rien à ajouter côté sécurité : un admin (SA, AU) y accède, les autres reçoivent 403.

7. Intégrer rôles, profils et permissions dans fund-management

État actuel : fund-management reçoit un Bearer de la gateway (dès que la route qf-fund-management est en place) mais, à ma connaissance, ne le lit pas. Il ne sait pas qui appelle, donc ne filtre rien. Trois briques, dans cet ordre.

gateway ──► fund-management GET /cash?page=0 Authorization: Bearer <JWT sub=g10002> │ ▼ (A) Filtre de sécurité — même contrat qu'utilisateurs-ci │ oauth : décoder + vérifier la signature (JWKS CASSO) · mock : lire `sub` sans vérifier │ uid = sub ▼ (B) Résolution de l'utilisateur — port hexagonal │ UserContextPort.resolve(uid) → GET http://utilisateurs-ci:8091/api/v1/internal/users/g10002 │ InternalUserDTO { profile{code, roles[].permissions[]}, orgaUnit{code, type}, enabled } │ cache 5 min (Caffeine) — un appel réseau par utilisateur et par 5 min, pas par requête │ utilisateur absent / enabled=false → 401 ; aucune permission GDF → 403 ▼ (C) Application des règles authorities = permissions GDF → @PreAuthorize sur les endpoints périmètre : si !GDF_TOUTES_AGENCES → branch_code = orgaUnit.code (listing, consultation, modification) création : branch_code = orgaUnit.code de l'utilisateur, jamais celui du corps de requête

Où ça se range dans l'architecture hexagonale

ModuleÉlémentRôle

application-serviceport UserContextPort + record CurrentUser {uid, agenceCode, permissions, toutesAgences}(B) : contrat ; les use cases reçoivent un CurrentUser, jamais un token
fund-management-external-servicesadapter UtilisateursCiUserContextAdapter (WebClient/RestTemplate + cache)(B) : appel interne à utilisateurs-ci, mapping InternalUserDTO → CurrentUser

Pourquoi un appel interne plutôt que des rôles dans le JWT
Trois raisons, toutes déjà tranchées par le socle : le JWT vient de CASSO, qui ne connaît pas les rôles QlickFlow ; en mock le JWT est fabriqué par la gateway sans regarder la base ; et une révocation doit être immédiate. Le coût est un appel HTTP interne par utilisateur toutes les 5 minutes, ce qui est négligeable.

9. Questions directes, réponses directes

QuestionRéponse
Fund-management attend-il un JWT ?Oui — mais il le reçoit de la gateway, jamais du navigateur. Aujourd'hui il ne le lit pas ; c'est la brique (A) de la section 7.
Le micro-frontend doit-il récupérer un « sessionId » ?Non, rien à récupérer : le cookie de session est posé par la gateway au login et repart automatiquement avec withCredentials: true. Il est httpOnly, ton code ne peut pas le lire, et c'est voulu.
Comment le micro-frontend connaît-il le rôle ?Un appel GET /api/v1/public/users/me/context au démarrage → profileCode, permissions, agence, toutesAgences.
Où sont générés les tokens ?En prod : CASSO, après le login OIDC piloté par la gateway. En local mock : MockJwtService dans la gateway, sur POST /mock-auth/login. En Postman : par le script de pré-requête (accepté uniquement en mock).
Comment les rôles passent-ils du portail à fund-management ?Ils ne passent pas par le portail. Fund-management reçoit un JWT avec sub = uid et demande lui-même à utilisateurs-ci (/api/v1/internal/users/{uid}) le profil, les permissions et l'agence.
Quelqu'un peut-il appeler /api/v1/internal/… depuis Internet ?Non : la gateway ne route pas ce préfixe. Ces endpoints ne sont joignables que sur le réseau interne du cluster.
Que se passe-t-il si l'admin retire le profil CHEF_CAISSE à quelqu'un ?Au prochain appel, utilisateurs-ci ne trouve plus la permission → 403 ; fund-management, avec son cache de 5 min, suit dans les 5 minutes (ou immédiatement si on invalide le cache sur l'événement).
Et le refresh du token ?Géré par la gateway (QfTokenRelayFilter rafraîchit si le JWT expire dans moins de 30 s, via le refresh token stocké dans oauth_session). Le front n'a rien à faire.
Pourquoi la gateway plante-t-elle sans dev-sso ?Découverte OIDC au démarrage (section 3). Lancer dev-sso avant.
Où en est-on ?utilisateurs-ci : fait (V16, /me/context, tests). Gateway : route à ajouter. Fund-management : à faire (doc séparé après tes captures). Front GDF : à faire (deux fichiers proposés en section 6).

10. Glossaire

TermeDéfinition
OIDC / OAuth2Protocole de délégation d'authentification : le portail ne voit jamais le mot de passe, CASSO le vérifie et délivre des tokens.
JWTToken signé (header.payload.signature) lisible mais infalsifiable. Le payload contient sub (uid), iss, exp.
Access token / refresh tokenLe premier est envoyé aux services (durée courte, 1 h) ; le second sert à en obtenir un nouveau sans re-login.
BFF (backend for frontend)La gateway : elle porte la session et les tokens à la place du navigateur.
BearerForme de l'en-tête Authorization: Bearer <token> : « porteur de ce token = authentifié ».
Resource serverUn microservice qui valide un Bearer avant de répondre. utilisateurs-ci en est un ; fund-management doit le devenir.
AuthorityChaîne Spring Security attachée à l'utilisateur courant ; ici, le nom d'une Permission.
@PreAuthorizeAnnotation qui refuse (403) l'appel si l'authority demandée manque.
Profil / rôle / permissionProfil = ce qu'est la personne (CHEF_CAISSE) ; rôle = paquet de permissions (GDF Agence) ; permission = un droit atomique (GDF_CREER_DEMANDE).
Mode mock / oauthDeux configurations de la même chaîne : mock = pas de signature vérifiée, pour le dev ; oauth = CASSO (ou dev-sso), pour tout le reste.
dev-ssoServeur OIDC local (9001) fourni par le tech lead, qui joue CASSO sur ton poste.
