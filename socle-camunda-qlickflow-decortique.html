1La vue d'ensemble : qui parle à qui

Tes captures montrent une décision d'architecture fondamentale du socle : le moteur Camunda n'est PAS embarqué dans le microservice métier. Ce sont deux applications Spring Boot séparées :

ProjetRôlePreuves dans tes captures
qlickflow-camunda-engineLe moteur Camunda, mutualisé. Une seule classe Application, il ne fait qu'héberger le moteur et son API REST (port 3030).Projet quasi vide (1 classe + yaml), fichiers camunda-h2-database.mv.db à la racine (base H2 locale du moteur), 2 BPMN d'autres processus dans ses resources.
derog-tar-retail-ciLe microservice métier (dérogation tarifaire retail). Il ne contient aucun moteur : il pilote le moteur à distance via son API REST.Package bpm.outbox complet, camunda-openapi-v7.24.json + template mustache (client REST généré), logs de POST vers localhost:3030/engine….
En clairLe moteur Camunda est comme une tour de contrôle mutualisée : chaque microservice métier (dérog tarifaire aujourd'hui, fund-management demain) lui envoie ses plans de vol (les BPMN), lui signale les événements (« la demande X est soumise »), et la tour décide de l'étape suivante. Le microservice garde ses données métier chez lui (PostgreSQL à lui, migrations Flyway V1→V6) ; le moteur garde l'état des processus chez lui (sa propre base — H2 en local).

Pourquoi ce choix « moteur externe » plutôt qu'embarqué ? C'était justement la question structurante Q1 de notre cadrage AER_LM-258 — le socle y a déjà répondu : externe et mutualisé. Conséquences : les microservices restent légers (pas de tables Camunda chez eux), le moteur est un point central administrable (Cockpit unique), mais chaque interaction avec le workflow est un appel réseau — d'où tout l'attirail de fiabilisation qu'on va voir (outbox, retry, recovery).

2Le déploiement BPMN depuis le Modeler et la process-definition-key

C'est le point que tu voulais éclaircir. Le mécanisme repose sur un seul identifiant, présent à trois endroits qui doivent correspondre exactement :

a) Dans le fichier BPMN : l'attribut id du process

Ouvre P_A104304_QF_DEROG_TARIF_RET_PACK.bpmn en XML (onglet XML du Modeler). La racine contient :

Extrait type du BPMN (onglet XML du Modeler)
<bpmn:process id="P_A104304_QF_DEROG_TARIF_RET_PACK" name="Dérogation tarifaire retail" isExecutable="true">

Cet id — modifiable dans le Modeler en cliquant sur le fond du diagramme, panneau de droite, champ « ID » — devient la process-definition-key côté moteur. Le nom du fichier ne compte pas ; seul cet attribut compte. Note aussi isExecutable="true" : sans lui, le moteur accepte le déploiement mais refuse de démarrer des instances.

b) Au déploiement : le Modeler pousse vers le moteur

Bouton « Deploy » du Modeler (l'icône fusée) → il demande l'URL du REST endpoint : http://localhost:3030/engine-rest (celui de qlickflow-camunda-engine) et un « deployment name ». Le Modeler fait alors un POST /engine-rest/deployment/create. Le moteur enregistre une nouvelle version de la définition : si une définition avec la même key existe déjà, il crée la version N+1 — les instances en cours continuent sur leur version d'origine, les nouvelles instances démarrent par défaut sur la dernière. C'est le versioning natif de Camunda.

c) Dans le yaml du microservice : la même key

Le microservice a besoin de connaître la key pour dire au moteur « démarre une instance de CE processus ». D'où la propriété que tu as vue dans l'application.yaml de la dérog tarifaire — schématiquement :

application.yaml (principe — vérifie les noms exacts dans le fichier)
camunda:
  base-url: http://localhost:3030/engine-rest
  process-definition-keys:
    derogation-tarifaire: P_A104304_QF_DEROG_TARIF_RET_PACK
    infos-complementaires: P_A104304_QF_DEROG_TARIF_RET_PACK_INFO_COMPL

Quand le service veut lancer le workflow, il appelle POST /engine-rest/process-definition/key/{key}/start avec cette valeur. Si la key du yaml ne correspond pas à l'id d'un BPMN déployé → erreur « no deployed process definition with key ». C'est LE point de fragilité du déploiement manuel : trois copies du même identifiant (XML, moteur, yaml) qu'aucun outil ne synchronise automatiquement.

La convention de nommage : P_A104304_QF_DEROG_TARIF_RET_PACK se lit probablement P = Process, A104304 = code applicatif/projet BMCI, QF = QlickFlow, puis le nom métier. Pour fund-management il faudra demander à Yassin le code à utiliser — ne l'invente pas.
En clairLa process-definition-key est le nom de la recette enregistrée chez le moteur. Le Modeler dépose la recette (avec son nom écrit dedans), le yaml du microservice note ce même nom dans son carnet, et à chaque nouvelle demande le service téléphone au moteur : « lance-moi la recette qui s'appelle P_A104304_… ». Un caractère de différence entre les deux, et le téléphone sonne dans le vide.

3Le pattern Outbox, décortiqué pièce par pièce

Le problème qu'il résout : le double-écrit (dual-write)

Imagine le code naïf : dans la même méthode, on sauvegarde la demande en base puis on appelle Camunda par REST. Deux systèmes, deux écritures, aucune transaction commune. Si la base commite mais que l'appel REST échoue (réseau, moteur redémarré…), tu as une demande « SOUMISE » en base sans processus démarré chez Camunda — état incohérent, invisible, découvert des jours plus tard. L'inverse est possible aussi (processus démarré, rollback en base).

En clairL'outbox, c'est la boîte d'envoi du courrier : au lieu de courir à la poste toi-même à chaque lettre (et risquer l'accident en route), tu poses la lettre dans la boîte d'envoi dans le même geste que ton travail. Un facteur passe toutes les X secondes, prend les lettres, et s'occupe de la poste — avec des retentatives si la poste est fermée. Ta lettre ne peut pas se perdre entre ton bureau et la boîte : c'est le même geste, la même transaction.

Comment le socle l'implémente — chaque package de bpm.outbox a un rôle

Package (tes captures)Rôle dans la mécanique
publisher (OutboxPublisher, DefaultOutboxPublisher)Le point d'entrée pour le code métier : « publie cet événement ». Concrètement : un INSERT dans la table outbox, dans la transaction métier en cours. C'est ça, la garantie d'atomicité.
contract (metatata, payload, transport)La forme d'une lettre : les métadonnées (type d'événement, clé de corrélation, id agrégat…), le contenu métier (payload JSON), et les infos de transport. (Note le typo « metatata » — il est dans le socle.)
persistence (entity, mapper, repository)La table outbox elle-même et son accès JPA. La migration V5__alter_outbox_event_text_columns.sql montre qu'ils ont dû élargir les colonnes texte — les payloads ont grossi en cours de route.
job (OutboxPollingJob, OutboxRecoveryJob)Le facteur : un job planifié (@Scheduled, thread scheduling-1 de tes logs) qui tourne en boucle. Le second job repêche les lettres bloquées (claimées par un pod qui a crashé avant de finir).
processing (claiming → dispatching → execution → finalization)Le pipeline du facteur, en 4 temps : claiming = réserver un lot d'événements en attente (les marquer « à moi » pour qu'un autre pod ne les prenne pas) ; dispatching = router chaque événement vers son handler selon son type ; execution = l'appel réel (POST REST vers Camunda) ; finalization = marquer traité, ou compter l'échec pour retry.
spring (autoconfigure, properties…)Le packaging en starter : le module s'auto-configure via des propriétés. Indice fort que ce bpm.outbox est conçu comme un socle réutilisable — exactement ce qu'on voudra brancher dans fund-management.
spiLes points d'extension : là où chaque microservice branche SES handlers d'événements sans modifier le socle.

Et ShedLock (migration V4) — le détail qui prouve la production

V4__create_shedlock_table.sql : sur OpenShift, le microservice tourne en plusieurs répliques. Sans précaution, chaque pod exécuterait le polling job → doubles envois vers Camunda. ShedLock pose un verrou en base : à chaque tick, un seul pod obtient le verrou et exécute le job, les autres passent leur tour. Le claiming par lot ajoute une seconde ceinture de sécurité au niveau des lignes elles-mêmes.

Deux choses distinctes cohabitent sur ce thread planifié :

  • Le polling outbox (les 4 dernières lignes) : tournée du facteur, boîte vide, il rentre. Ça tourne en permanence, que tu aies de l'activité ou non.
  • Les paires Start/End POST vers localhost:3030/engine… avant le job outbox : des appels REST récurrents vers le moteur qui ne viennent pas de la boîte vide. Hypothèse la plus probable : un polling de tâches — soit du fetchAndLock d'external tasks (le microservice demande au moteur « as-tu du travail pour moi ? »), soit une synchronisation périodique d'état (requêtes sur les user tasks ou les instances). L'URL est tronquée sur ta photo ; la partie après /engine trancherait immédiatement.
À vérifier (2 minutes) : clique sur un de ces liens bleus dans la console IntelliJ et regarde l'URL complète. Si c'est /engine-rest/external-task/fetchAndLock → le socle utilise des external tasks et ça répond à la question du chemin retour (section 5). Si c'est /engine-rest/task… ou /history/… → c'est de la synchronisation d'état par interrogation. Note-le, c'est structurant pour nous.

Le LoggerInterceptor (package c.b.i.q.w.c.l) est un intercepteur du client REST qui trace chaque appel sortant — couplé au package observability.correlation, il permet de suivre une demande de bout en bout dans les logs. Bonne pratique du socle à conserver.

5Le chemin retour des statuts — ce qu'on sait, ce qui manque

Tes captures prouvent solidement le sens aller : métier → outbox → REST → Camunda. Le sens retour (le processus avance chez Camunda → le statut métier change dans PostgreSQL de la dérog) n'est pas directement visible. Trois mécanismes possibles en Camunda 7, et le socle en utilise forcément au moins un :

MécanismePrincipeIndices pour/contre
External tasks (pull)Dans le BPMN, les service tasks sont de type « external » avec un topic. Le microservice interroge le moteur (fetchAndLock), exécute le travail (dont la mise à jour du statut), et complète la tâche.Compatible avec les POST récurrents de tes logs ; c'est le pattern recommandé avec moteur distant. Hypothèse favorite.
Callback HTTP (push)Le BPMN contient des connecteurs HTTP qui appellent l'API du microservice (« passe la demande X en VALIDATED »).Possible — le package wfdtrp.controller pourrait exposer ces endpoints — mais fragile (le moteur doit connaître l'URL de chaque service, gestion d'erreur côté BPMN).
Interrogation d'état (poll)Le service interroge périodiquement le moteur sur l'état des instances/tâches et synchronise sa base.Également compatible avec tes logs ; plus simple mais avec latence et charge d'interrogation.
En clairAller = le métier pousse ses événements vers le moteur via la boîte d'envoi. Retour = soit le métier tire le travail que le moteur lui a préparé (external tasks — le plus probable ici), soit le moteur rappelle le métier. Il nous faut cette réponse avant d'écrire notre BPMN, car elle détermine comment on écrira nos service tasks.

6Critique du socle : ce qui est bien, ce qui pique

Ce qui est solide (à reprendre tel quel)

  • Outbox transactionnel + ShedLock + recovery job : le trio complet de la fiabilité en multi-pods. Rien à redire, c'est l'état de l'art du pattern.
  • Client Camunda généré depuis l'OpenAPI officiel (camunda-openapi-v7.24.json + mustache) : pas de client écrit à la main, contrat typé, régénérable.
  • Packaging en starter auto-configuré (spring.autoconfigure + spi) : le socle outbox est réutilisable par les autres microservices — dont le nôtre.
  • Observabilité par corrélation : intercepteur de logs + correlation id, indispensable quand trois systèmes participent à une même demande.
  • Migrations Flyway propres incluant l'infra technique (shedlock, outbox, audit) versionnée comme le reste.

Ce qui pique (les nitpicks demandés)

  • Le déploiement BPMN est manuel et non versionné côté moteur. Le BPMN vit dans le repo de la dérog, mais c'est un humain avec le Modeler qui le pousse vers le moteur. Risque de dérive : le fichier committé ≠ la version réellement déployée. Aucun pipeline ne garantit la synchronisation (le .gitlab-ci.yml build l'app, pas les déploiements BPMN, sauf preuve contraire). En cible, un déploiement du BPMN par appel REST au démarrage du service ou par étape de pipeline serait plus sûr — question à poser.
  • Triple copie de la key sans garde-fou (XML, moteur, yaml) : une faute de frappe = erreur au runtime seulement. Un test d'intégration qui vérifie au démarrage que les keys du yaml existent chez le moteur serait peu coûteux.
  • Logs INFO sur boîte vide : « Start/claim/empty batch/End » à chaque tick, toutes les quelques secondes → du bruit permanent qui noie les vrais événements. Ces lignes devraient être en DEBUG ; seul un lot non vide mérite INFO.
  • Latence structurelle du polling : le statut ne bouge qu'au rythme du tick (aller) + tick de récupération (retour). Pour AER_LM-258 avec ses gardes horaires strictes (10h/16h), il faudra connaître ces intervalles et vérifier qu'ils sont compatibles avec l'expérience utilisateur attendue.
  • H2 en fichier pour le moteur local : parfait pour le poste de dev, mais à ne jamais extrapoler — en INT/PROD le moteur doit pointer une vraie base. À confirmer dans le yaml de l'engine.
  • Couplage de version : le client est généré depuis l'OpenAPI 7.24 ; une montée de version du moteur impose de régénérer. Pas grave, mais à documenter.
  • Le typo metatata : anecdotique, mais si ce package devient un socle partagé, il sera gravé partout. À signaler gentiment.

7La transposition sur fund-management (hexagonal)

La dérog tarifaire est en couches « classiques » (controller/service/repository/facade). Nous, on est en hexagonal strict — la transposition consiste à ranger chaque pièce du socle du bon côté des ports. La règle d'or : le domaine ne sait pas que Camunda existe ; il sait seulement qu'il « publie des événements de cycle de vie ».

Pièce du socle (dérog)Chez nous (fund-management)Module
Appel à OutboxPublisher dans le service métierUn port de sortie WorkflowEventPublisher dans service.domain.ports.output, appelé par les use cases (ex. à la soumission d'une demande). Le domaine publie un événement métier, point.fund-management-application-service (le port)
bpm.outbox.persistence + publisherL'adapter qui implémente le port : INSERT dans la table outbox dans la même transaction que le save(). Table créée par une migration Flyway chez nous (+ shedlock), comme leurs V4/V5.fund-management-data-access
OutboxPollingJob + pipeline + client Camunda généréL'infrastructure d'envoi : job planifié + client REST. C'est de la technique pure, côté adapters — jamais dans domain-core. Si le socle bpm.outbox est publié comme dépendance interne (starter), on l'importe au lieu de le réécrire.fund-management-container (ou un nouveau module fund-management-bpm si Yassin préfère isoler)
process-definition-keys du yamlMême principe dans notre application.yaml, avec la key de NOTRE processus (code à demander, convention P_Axxxxx_QF_…).container / resources
BPMN dans resources/bpmnNotre BPMN AER_LM-258 versionné dans le repo (source de vérité), déployé vers le moteur via Modeler comme eux — en signalant le risque de dérive (section 6).container / resources
Chemin retour (external tasks / callback)Dépend de la réponse de la section 5. Si external tasks : un worker côté adapters qui fetchAndLock, appelle un use case dédié (« appliquer la transition X »), et complète la tâche. Le use case reste la seule porte d'entrée du domaine — le worker n'est qu'un adapter entrant de plus, au même titre que le controller REST.adapters entrants

Et le lien avec notre cadrage AER_LM-258 se referme proprement : les statuts du cycle de vie (INITIATED → VALIDATED → … ) restent portés par notre base via requestStatus ; Camunda orchestre QUI peut faire QUOI et QUAND (les validations par profil, les gardes 10h/16h), et chaque transition franchie déclenche — par le chemin retour — la mise à jour du statut chez nous. GELÉ, comme on l'avait cadré, reste un verrou applicatif chez nous, pas un état Camunda.

Ordre de bataille inchangé : on ne code rien tant que (a) le BPMN n'est pas validé par Yassin et (b) les réponses ci-dessous ne sont pas connues. Le socle nous fait gagner énormément — à condition de le brancher, pas de le réinventer.
