3. Points que la compilation ou l'exécution peuvent révéler

  1. Codes d'erreur : les assertions $.error reprennent ceux du handler migré en ApiResponse (BAD_REQUEST, NOT_FOUND, CONFLICT, VALIDATION_ERROR, TECHNICAL_ERROR). Les tests 403 n'assertent que le statut et success=false.
  2. Si les 2 tests 403 sortent en 500 : la méthode @ExceptionHandler(RetailForbiddenException.class) du lot B1 n'a pas été ajoutée au handler — le test a raison, c'est le handler qu'il faut compléter.
  3. Handler : import application.rest.retail.error.RetailDemandExceptionHandler et constructeur (MessageSource), comme dans ta version actuelle. Si ton import diffère, garde le tien.
  4. Recherche : le test ne construit pas de PageResult (le use case mocké renvoie null, emballé par ApiResponse.success) pour ne dépendre que des accesseurs de DemandeSearchCriteria utilisés par le use case B1.
  5. Corps en JSON brut (text blocks Java 17) : le test vérifie le contrat réellement reçu par le front, sans dépendre des builders ni de l'enum RequestType.
