1Méthode

Ce qu'on mesure : la couverture de lignes (une ligne est « couverte » si un test l'exécute) et de branches (chaque côté d'un if/switch). Rappel de la limite qu'on a documentée dans le dossier de maîtrise : la couverture mesure l'exécuté, pas le vérifié — une ligne traversée sans assertion compte quand même. Nos tests assertent, donc le chiffre a du sens ici.

Comment j'estime : pour chaque classe de production, je liste les méthodes/branches que les tests existants traversent réellement (je connais les deux — je les ai écrits), je rapporte au volume de la classe, et j'arrondis par plage. Les classes générées (Impl MapStruct) et le boilerplate Lombok sont traités comme JaCoCo le fera avec notre lombok.config (addLombokGeneratedAnnotation=true : getters/setters/builders exclus du dénominateur). Les DTOs, entités JPA, enums, exceptions et interfaces sont hors périmètre de couverture utile (pas de logique) — les inclure gonflerait ou plomberait artificiellement le chiffre.

Les cibles qu'on s'est fixées : domaine ≥ 90 % · mappers ≥ 85 % · adapters ≥ 80 % · handlers 100 % des branches · use cases ≥ 85 %.

5Les trous — par ordre de gravité

Trou n°1 — Les web mappers MapStruct (les deux périmètres, ~5 %) : les contrats d'entrée (id/réf/statuts/dates IGNORÉS — c'est une frontière de SÉCURITÉ : un client qui envoie "requestStatus":"VALIDATED" ne doit pas passer) ne sont vérifiés par AUCUN test. C'est le plus grave car c'est du code de frontière, et il est invisible : tout marche en apparence.
Trou n°2 — Chemins heureux des use cases (~50 %) : create/update/getById/getAll/cancel ne sont exercés unitairement que côté rejet. L'orchestration (validation AVANT save, mapping aller-retour) n'est prouvée que par les campagnes API manuelles — la couverture ne la voit pas, et une régression ne serait attrapée qu'à la main.
Trou n°3 — 3 branches de handler jamais déclenchées : 422 (RetailValidation/CorpoValidation), 409 (Conflict), et le catch-all Exception. Le contrat d'erreur BFF est LA promesse faite au front — chaque branche doit avoir son test (cible 100 %).

6Les chiffres réels + le plan de comblement

Mesurer (IntelliJ, la procédure qu'on a validée)

  1. Vérifie lombok.config à la racine : lombok.addLombokGeneratedAnnotation = true (JaCoCo ignore alors le boilerplate généré).
  2. Settings → Build → Coverage : runner JaCoCo ; filtre d'inclusion com.bmci.*.
  3. Clic droit sur le dossier de tests racine → Run 'All Tests' with Coverage — sur les TESTS, pas sur l'application lancée.
  4. Le rapport s'affiche à l'ARRÊT du process ; exporte en HTML si tu veux le partager.
