2Les commits — deux stratégies

Recommandée : 5 commits thématiques — l'historique raconte le refactoring et Yassin peut reviewer commit par commit (common → packages → Flyway → modèle+handler → tests). Les git add par chemins font le tri même si tout est modifié en vrac dans ton working tree ; entre les commits 2 et 4, git ne reprend que ce qui reste modifié dans ces dossiers.

## [FEAT][AER_LM-257] Demandes Corpo — alignement 100% retail, module common, Flyway, handler pattern BFF

### Ce que fait cette PR
Implémente le périmètre **Demandes Corpo** en application des directives d'architecture :

| Directive | Application |
|---|---|
| Dupliquer le schéma tel qu'il est | Schéma PostgreSQL `corpo` = tables retail répliquées + colonnes Jira (identité client, `denomination_code`) — livré par **Flyway V2** |
| Flyway pour les migrations | Base existante baselinée V1 (non touchée), V2 versionnée, historique `public.flyway_schema_history` |
| Séparer les modèles et couches | Racines `retail/` et `corpo/` dans chaque module, couches à l'intérieur |
| Module common | `fund-management-common` : socles (BaseId, BaseEntity, AggregateRoot), 6 VOs d'identité, DTOs partagés (Currency, Denomination, Response, Responsible, Error) |
| Exceptions pattern BFF | Contrat `ErrorDTO {code, message}` + `MessageSource` + registre `CorpoHttpStatus`, résolution par type d'exception, messages préfixés `[code]` compatibles avec la regex du BFF |

Le modèle corpo est le **miroir exact du retail** (agrégat → opérations → détails devise → coupures, mêmes VOs, DTOs arborescents, même mécanique de persistance) + uniquement les ajouts Jira : réf demande CO-AAAA-NNNNNN (séquence), réf client, ville, complément d'adresse, n° de compte, code coupure stable.

### Règles métier
- Montant **calculé serveur** (Σ quantité × valeur faciale) ; montant fourni contrôlé → 422 si incohérent
- Défauts serveur : urgent NO, statut INITIATED, institution 1, caisse 001
- Référence unique immuable ; annulation propagée demande + opérations ; demande annulée figée (409)
- Résolution par référentiels : coupure par CODE, devise par ISO → 422 si inconnues

### Points d'attention reviewers
- **Seule modification de la main class** : scans `@EntityScan`/`@EnableJpaRepositories` élargis à la racine `dataaccess` (requis par la structure racine — élargir un scan est sans risque)
- **Divergences retail assumées** : create → **201** (retail : 200, sémantique HTTP explicite) ; FKs `user_profile_id`/`establishment_id` **nullables** (l'identité client remplace) ; `DenominationDTO` unifié au format corpo (retail expose `denominationCode`/`faceValue` à null — additif, non cassant)
- Mapper de persistance **MapStruct hybride** : structure générée, résolutions en `default`+`@Context`, liens parents en `@AfterMapping`
- Fetch join limité au 1er niveau (MultipleBagFetchException) — comme retail
- Handler d'erreurs : **pas de regex** (nous produisons nos erreurs, le type est la source du code) — argumentaire détaillé dispo

### Base de données
Pré-requis une fois avant le premier démarrage : `DROP SCHEMA IF EXISTS corpo CASCADE;` (ancien prototype). Flyway crée le schéma, applique V2 (8 tables + séquence + seed MAD/11 coupures). Le schéma `public` (retail) n'est pas modifié ; le futur V1 retail restera sous baseline sur cette base.

### Tests
7 classes (domaine, mapper web, use case, mapper persistance, adapter, web slice MockMvc, intégration `@SpringBootTest+@Transactional`) — `mvn clean verify` → rapports JaCoCo. Campagne API : 21 cas (nominaux, règles métier, edge cases) avec attendus en base, tous passés.

### Breaking change à signaler au front
Contrat corpo **arborescent** (aligné retail) + corps d'erreur **ErrorDTO** `{code, message}` (+ `fieldErrors` sur les 400). Exemples de payloads dans le cahier de tests.

### Reste ouvert (backlog assumé)
Coupure en double dans une ventilation (500 propre → à trancher : dédup ou 422) · pagination GET all · Testcontainers · migration retail vers le handler (guide fourni) · `ddl-auto: none` (décision d'équipe) · endpoint VALIDATED (attend le workflow Camunda).

# Fund Management — Périmètre Corpo (AER_LM-257)

Demandes d'**alimentation** / **ramassage** d'espèces pour les clients corporate,
implémentées en miroir du modèle retail (architecture hexagonale) + spécificités Jira.

## Architecture

| Module | Rôle |
|---|---|
| `fund-management-common` | Socle partagé retail/corpo : `BaseId`, `BaseEntity` (domaine & JPA), `AggregateRoot`, VOs d'identité, DTOs communs (`CurrencyDTO`, `DenominationDTO`, `ErrorDTO`…) |
| `fund-management-domain-core` | Métier pur — `domain.retail.*` / `domain.corpo.*` (agrégats, enums, exceptions typées) |
| `fund-management-application-service` | DTOs, mappers web MapStruct, ports & use cases — `service.domain.{retail,corpo}.*` |
| `fund-management-data-access` | Entités JPA, repositories, mappers de persistance, adaptateurs — `dataaccess.{retail,corpo}.*` |
| `fund-management-application` | REST — `rest.retail` / `rest.corpo` (+ handler d'erreurs) |
| `fund-management-container` | Main, configuration, migrations Flyway, tests d'intégration |

**Règle de placement** : partagé par les deux modèles → `common` · nominal → `retail` · corpo → `corpo` · indépendant → transverse.

## API Corpo — `/corpo/cash` (media type `application/vnd.api.v1+json`)

| Méthode | Endpoint | Succès | Erreurs |
|---|---|---|---|
| POST | `/corpo/cash` | **201** | 400, 422 |
| GET | `/corpo/cash/{id}` | 200 | 404 |
| GET | `/corpo/cash` | 200 | — |
| PUT | `/corpo/cash/{id}` | 200 | 400, 404, 409, 422 |
| PATCH | `/corpo/cash/{id}/cancel` | 200 | 404, 409 |

Payload **arborescent** (aligné retail) : `operations[] → currencyDetails[] → operationDenominations[]`,
coupures référencées par **code stable** (`BILLET_200`, `PIECE_10`, `CENTIME_50`…).
Erreurs au contrat BFF : `{"code":"422","message":"[422] …"}` (+ `fieldErrors` sur les 400).

Règles clés : montant **calculé serveur** et contrôlé · référence `CO-AAAA-NNNNNN`
générée par séquence, immuable · annulation propagée · demande annulée figée.

## Base de données & Flyway

- Schéma dédié **`corpo`** (duplication du schéma retail + colonnes Jira), livré par `V2__create_corpo_schema.sql`
- Historique : `public.flyway_schema_history` — base existante baselinée V1
- Un script appliqué ne se modifie **jamais** (checksum) : toute évolution = `V3`, `V4`…
- Reset des données de test : voir `docs/` (TRUNCATE des 4 tables transactionnelles + RESTART de la séquence)
