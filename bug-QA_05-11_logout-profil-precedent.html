0. Cause (v3 : pourquoi le fix v2 marche en local et pas en DMZR)

Oui, c'est lié à la Module Federation — pas au mécanisme, à l'état en mémoire. Shell et remote fund-management tournent dans la même page (même runtime JS). Le remote a ContexteUtilisateurService en providedIn: 'root' : /me est mis en cache dans un signal et charger() ne rappelle pas l'API tant que contexte() est rempli. Au logout, le shell vide cookie et storages (ta capture le confirme : cookies et storage vides) mais fait un router.navigate(['/login']) — navigation SPA, la page vit toujours, le singleton aussi → au login suivant, le remote sert l'ancien profil. Ctrl+F5 vide la mémoire JS, d'où le « fix ». Même cause que l'erreur attrapée par le catch actuel, qui fait déjà window.location.assign : on généralise.

v3 — DMZR : le portail y est en hash routing (/#/login). Le commit 38257ccd a mis assign('#/login') : changer seulement le fragment #… est une navigation intra-page, pas un rechargement — le singleton du remote survit, comme avant. En local (path routing, /login) assign recharge vraiment, d'où la différence. Fix : cible selon le mode de routing + reload() forcé.

  logout(): void {
    try {
      this.menuModule.reinitialiser();   // AER_LM-336 : plus d'entrées de menu de l'utilisateur précédent
      sessionStorage.clear();
      Object.keys(localStorage).filter(k => k.startsWith('qf.')).forEach(k => localStorage.removeItem(k));
    } finally {
      // Rechargement COMPLET obligatoire : le MFE fund-management vit dans la même page et garde /me en mémoire.
      // En hash routing (DMZR : /#/login), assign('#/login') ne change que le fragment → aucun rechargement, l'ancien
      // profil survit. On pose la cible puis on force reload() : sans effet si assign a déjà rechargé (path routing local).
      window.location.assign(environment.useHash ? '#/login' : '/login');
      window.location.reload();
    }
  }
