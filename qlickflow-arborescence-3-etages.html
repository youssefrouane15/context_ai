Pourquoi « api-gateway » et « api-gateway-ci » ?
Les 3 étages de QlickFlow, expliqués simplement

Ta question exacte : « ils ont projet et projet-ci, dans le projet ils utilisent Argo CD et il n'y a pas les sources — sauf qlick-flow-ac-dev qui fait du Terraform ». Réponse : ce ne sont pas des doublons. Ce sont trois familles de repos avec trois métiers différents, empilées comme les étages d'un immeuble.

0 · Le principe

Une seule idée à comprendre : « ce qui est déployé, c'est ce qui est écrit dans Git »

Toute l'architecture que tu as photographiée repose sur un principe unique appelé GitOps : à chaque étage, un repo Git décrit un état souhaité, et un robot se charge de rendre la réalité conforme à ce qui est écrit.

  • Étage 2 : « voici le code de l'application » → le robot (pipeline GitLab CI) fabrique l'image Docker.
  • Étage 1 : « voici la version et la configuration à faire tourner » → le robot (Argo CD) déploie sur le cluster.
  • Étage 0 : « voici l'infrastructure qui doit exister » → le robot (Terraform) crée la base, le stockage, le réseau sur IBM Cloud.
Analogie Imagine un restaurant. L'étage 2, c'est la cuisine : on y prépare les plats (le code devient une image Docker). L'étage 1, c'est le carnet de commandes affiché en salle : il dit quel plat servir à quelle table, en quelle quantité — et le serveur (Argo CD) le lit en permanence et sert exactement ce qui y est écrit. L'étage 0, c'est le bâtiment lui-même : les murs, l'électricité, la plomberie (Terraform). Personne ne cuisine en salle, personne ne sert depuis la cuisine : chaque étage a un métier, un seul.
Étage 2 · L'usine

Les repos X-ci : là où vivent les sources

Ta capture de api-gateway-ci montre exactement le contenu type de cette famille :

api-gateway-ci/ ├── pipeline/ ← scripts et étapes du pipeline CI ├── src/ ← ⭐ LE CODE SOURCE (Java, config…) ├── .gitignore ├── .gitlab-ci.yml ← la recette du pipeline : build → test → image ├── Dockerfile ← comment emballer l'app dans une image Docker ├── pom.xml ← Maven, comme sur fund-management └── sonar-project.properties ← analyse qualité SonarQube

Le métier de ce repo : fabriquer et contrôler. À chaque push, le pipeline GitLab :

  • compile le projet Maven (mvn package) et exécute les tests ;
  • passe le code au contrôle qualité SonarQube ;
  • construit l'image Docker à partir du Dockerfile ;
  • pousse cette image dans le registre d'images du groupe, avec une étiquette unique (le tag, souvent le hash du commit) ;
  • et enfin — c'est le pont vers l'étage 1 — écrit ce nouveau tag dans le repo X (dans le fichier values de l'environnement visé).
À retenir Le repo -ci ne déploie jamais rien lui-même sur le cluster. Il s'arrête à « l'image est prête et publiée, le carnet de commandes est mis à jour ». C'est la fin de la CI (Continuous Integration). La suite, c'est le métier de l'étage 1.
Étage 1 · Le plan de pose

Les repos X (sans -ci) : un chart Helm surveillé par Argo CD

C'est le repo qui t'a surpris : aucune source dedans — et c'est voulu. Ta capture de api-gateway montre :

api-gateway/ ├── .gitignore ├── .gitlab-ci.yml ← minuscule : quelques vérifications, pas de build ├── Chart.yaml ← la fiche d'identité du paquet Helm ├── README.md ← « Hi Legends 👋 » ├── values-dev.yaml ← config pour l'environnement DEV ├── values-qua.yaml ← config pour la QUALIFICATION ├── values-prod.yaml ← config pour la PRODUCTION └── values.schema.json ← le gendarme : valide le format des values

C'est quoi, Helm et un « chart » ?

Helm est l'installateur d'applications de Kubernetes/OpenShift — l'équivalent d'un « setup.exe » pour le cluster. Un chart est le paquet d'installation : il contient des modèles de configuration Kubernetes (déploiement, service, routes…) avec des trous à remplir. Les fichiers values remplissent les trous : même recette, doses différentes par environnement.

Extrait type — values-dev.yaml vs values-prod.yaml 
# ---- values-dev.yaml ----
image:
  repository: registry.groupe/qlick-flow/api-gateway
  tag: "a1b2c3d"      # ← LA ligne que la CI met à jour à chaque build
replicaCount: 1       # dev : 1 exemplaire suffit

# ---- values-prod.yaml (même structure, autres doses) ----
#   tag: "v1.4.2"      # prod : une version STABLE, pas le dernier commit
#   replicaCount: 3    # prod : 3 exemplaires (haute disponibilité)

Et Argo CD dans tout ça ?

Argo CD est un robot installé dans le cluster OpenShift. Son travail tient en une boucle infinie :

  1. Lire le repo api-gateway (le chart + le values de l'environnement) → c'est l'état souhaité.
  2. Regarder ce qui tourne réellement dans le cluster → c'est l'état réel.
  3. S'ils diffèrent (nouveau tag d'image, replicaCount changé…) → synchroniser : Argo CD applique le chart et le cluster redevient conforme à Git.

C'est le modèle « pull » : personne ne pousse un déploiement vers le cluster depuis un pipeline. C'est le cluster qui tire son état depuis Git. Conséquences très concrètes :

  • Rollback = git revert. Revenir en arrière, c'est annuler un commit dans le repo values. Argo CD redéploie l'ancienne version tout seul.
  • Audit gratuit. L'historique Git du repo X = l'historique exact de tout ce qui a été déployé, par qui, quand.
  • Sécurité. Avoir le droit d'écrire du code (repo -ci) ≠ avoir le droit de déployer en prod (repo X, fichier values-prod). Deux repos = deux serrures.
  • Anti-dérive. Si quelqu'un modifie à la main un réglage dans le cluster, Argo CD détecte l'écart avec Git et le remet en conformité.
Analogie Le repo X est le thermostat de la maison : tu écris « 21° » dans Git, et la chaudière (Argo CD) travaille en continu pour que la température réelle soit 21°. Tu ne « pousses » pas de la chaleur : tu déclares une consigne, le système converge vers elle.
Le pont entre les étages

Le voyage complet d'une ligne de code jusqu'à la prod

1
Le dev pousse du code dans api-gateway-ci

Une correction, une feature — un commit ordinaire sur le repo des sources.

2
Le pipeline CI se déclenche

Compilation Maven, tests, SonarQube. Si tout est vert, construction de l'image Docker.

3
L'image part au registre avec un tag unique

Exemple : api-gateway:a1b2c3d. L'image est prête, mais rien n'est encore déployé.

4
La CI commite le nouveau tag dans api-gateway

Une seule ligne change dans values-dev.yaml : tag: "a1b2c3d". C'est le passage de témoin CI → CD. (D'où les « Edit values-dev.yaml » que tu vois dans l'historique des commits.)

5
Argo CD détecte l'écart et synchronise

État souhaité (Git) ≠ état réel (cluster) → Argo CD applique le chart Helm avec les nouvelles values.

6
OpenShift fait tourner la nouvelle version

Le pod redémarre avec l'image a1b2c3d. Promotion en QUA puis PROD = modifier values-qua.yaml puis values-prod.yaml (souvent via merge request, avec validation humaine).

… et tout ceci tourne sur un terrain créé par l'étage 0

Le namespace OpenShift, la base PostgreSQL, le coffre à secrets : c'est qlick-flow-ac-dev qui les a fait exister. On y descend.

Étage 0 · Les fondations

qlick-flow-ac-dev : l'exception qui n'en est pas une — c'est de l'Infrastructure as Code

Tu as vu juste : ce repo utilise Terraform. Il ne déploie pas une application — il crée l'infrastructure elle-même sur IBM Cloud. « ac » = les Access / Cloud components de l'environnement dev.

qlick-flow-ac-dev/ ├── .templates/ ← modèles du pipeline mutualisé ├── examples/cos-module/ ← exemple d'utilisation d'un module ├── .gitlab-ci.yml ← 4 lignes ! (voir plus bas) ├── cft.tf ← chaque fichier .tf = UNE brique d'infra : ├── cos.tf ← le stockage d'objets (Cloud Object Storage) ├── database.tf ← la base PostgreSQL ├── kvstore.tf ← le coffre à secrets (key-value store) ├── roksns.tf ← le namespace OpenShift (ROKS) ├── vip.tf ← l'entrée réseau (Virtual IP) ├── provider.tf ← quel "fournisseur" parle à IBM Cloud ├── variables.tf ← les paramètres du projet ├── terraform.tfvars ← les valeurs de ces paramètres └── outputs.tf ← ce que Terraform restitue après création

Terraform en une phrase

Avec Terraform, tu décris ce qui doit exister (déclaratif), et l'outil calcule puis exécute les actions pour y arriver : terraform plan = « voici ce que je vais créer/modifier/détruire », terraform apply = « je le fais ». Exactement la même philosophie qu'Argo CD — mais appliquée aux ressources cloud au lieu des applications.

Extrait réel du README du repo — création d'un stockage COS 
# Un fichier .tf DÉCRIT une ressource à créer. Ici : un stockage
# d'objets (COS) sur IBM Cloud, via l'orchestrateur BP2I
# (la « centrale de commande » cloud du groupe BNP Paribas).

resource "orchestrator_subscription_cos_v1" "cos" {
  realm       = var.realm_id
  environment = "int"
  tier        = "P"
  description = "COS FOR TEST ITDS Pipeline"
  apcode      = var.apcode
  timeouts = {          # leçon durement apprise par l'équipe :
    create = "10m"      # sans timeout explicite, une création lente
    delete = "10m"      # rend la ressource « tainted » (état inconnu)
    update = "10m"
  }
  payload = {}
}

Le pipeline le plus court du monde

Le README du repo le dit lui-même : « Overall idea: do Terraform, not GitLab CI ». La squad n'écrit pas son pipeline — elle inclut le pipeline mutualisé du groupe (TCaaS), qui sait faire plan / apply / remédiation / Vault tout seul :

.gitlab-ci.yml — l'intégralité du fichier 
include:
  - project: 'Production-mutualisee/IPS/IDO/TCaaS/pipelines/templates/gitlab-cd-templates/iac'
    file: '.templates/gitlab-ci.yml'
    # ref: 1.5.1   ← optionnel : figer une version du template

Toi tu n'écris que les fichiers .tf — le pipeline fourni fait le reste. Même logique de mutualisation que le socle BFF côté Java.

Quatre concepts vus dans tes captures — décodés

① Le state file — la mémoire de Terraform

Le fichier terraform.tfstate est le carnet où Terraform note « voici ce que j'ai déjà créé, et avec quels identifiants ». Sans lui, Terraform ne sait pas si la base existe déjà ou s'il doit la recréer. Il est sensible (il peut contenir des secrets) et stocké dans un backend : GitLab par défaut, ou IBM COS. Ta capture précisait un piège de version : COS exige Terraform 1.11+, et seules 1.11.0 / 1.11.1 fonctionnent — 1.11.2 à 1.11.4 posent problème.

② Vault — le coffre-fort des clés

Pour parler à IBM Cloud, le pipeline a besoin d'une clé API. Elle n'est jamais écrite dans le repo : elle vit dans Vault (le coffre-fort du groupe), et le pipeline vient la chercher au démarrage grâce aux variables APIKEY_VAULT_NAMESPACE, APIKEY_VAULT_ROLE, APIKEY_VAULT_ADDR, etc. — celles de ta première capture, avec l'avertissement : en oublier une = pipeline en échec. Les captures suivantes montraient la migration en cours de l'ancienne méthode d'authentification (CI_JOB_JWT, dépréciée) vers les ID Tokens GitLab, via l'outil promote-cli.

③ Les ressources « tainted » — l'état inconnu

Une ressource est marquée tainted (« souillée ») quand une erreur pendant sa création empêche Terraform de savoir si elle est utilisable ou non — le plus souvent un timeout : l'apply s'est terminé avant que l'orchestrateur BP2I ait fini de créer la ressource. La procédure de ta capture : vérifier côté IBM Cloud via le job Refresh plan, puis selon le cas lancer Fix tainted (la ressource existe → on la « dé-souille ») ou Recreate (elle n'existe pas → on la recrée). D'où les timeouts explicites de 10 minutes dans tous les .tf.

④ Les variables TF_VAR_ — le pont CI ↔ Terraform

Toute variable Terraform peut être alimentée depuis GitLab en la préfixant TF_VAR_ : une variable my_var dans un fichier .tf se règle avec une variable CI/CD nommée TF_VAR_my_var. Exemple vu dans tes captures : TF_VAR_orchestrator_allow_replace_on_apply: "true" pour lever la sécurité qui interdit de détruire/remplacer une ressource. Et TF_LOG (trace/debug/info/warn/error) pour déboguer le provider.

Attention L'étage 0 est le plus dangereux des trois : un terraform apply mal paramétré peut détruire une base de données. C'est exactement pour ça que le provider BP2I bloque les destructions par défaut (orchestrator_allow_replace_on_apply), que le state est verrouillable, et que ce repo est en général réservé au tech lead / à l'équipe infra. En tant que dev applicatif, tu lis cet étage pour comprendre ton environnement — tu n'y écris pas sans accord de Yassin.

Et pour toi, concrètement

Le bon réflexe : « où est-ce que je regarde quand ça casse ? »

🔎 « L'application plante / un test échoue / le build est rouge »

→ Étage 2, repo X-ci : les logs du pipeline, le code, les tests. C'est ton terrain de jeu quotidien — le futur repo du microservice fund-management suivra ce même modèle.

🔎 « La bonne version ne tourne pas / mauvaise config en QUA / il faut revenir en arrière »

→ Étage 1, repo X : vérifie le tag dans le values de l'environnement, l'état de synchronisation dans l'interface Argo CD, et l'historique des commits (qui a promu quoi, quand).

🔎 « La base est injoignable / le namespace n'existe pas / un secret manque »

→ Étage 0, repo qlick-flow-ac-dev : c'est un sujet infra — regarde les .tf pour comprendre ce qui est censé exister, puis remonte à Yassin plutôt que d'y toucher.

La phrase à retenir « -ci fabrique, X décrit, Argo CD applique, Terraform fonde. » Quatre verbes, toute l'architecture. Et le fil rouge des trois étages est le même : Git est la source de vérité, un robot rend la réalité conforme à ce qui y est écrit.
Annexe

Glossaire express

GitOpsPratique où l'état souhaité (apps + infra) est décrit dans Git, et où des outils automatiques font converger la réalité vers ce qui est écrit.
CI / CDCI = intégrer et fabriquer (build, tests, image). CD = livrer et déployer. Ici : CI dans les repos -ci, CD via Argo CD.
Image DockerLe paquet exécutable de l'application : le .jar + Java + tout le nécessaire, prêt à tourner n'importe où.
Registre d'imagesLa bibliothèque où les images Docker sont publiées et versionnées par tag.
Helm / ChartHelm = l'installateur d'apps pour Kubernetes. Chart = le paquet d'installation, avec des modèles à trous.
values.yamlLe fichier qui remplit les trous du chart : version d'image, nombre de réplicas, URLs… Un par environnement.
values.schema.jsonLe gendarme : valide le format des values et bloque une faute de frappe avant le déploiement.
Argo CDRobot dans le cluster qui compare en continu Git (souhaité) et le cluster (réel), et synchronise. Modèle « pull ».
OpenShift / ROKSLa plateforme Kubernetes de Red Hat ; ROKS = sa version managée sur IBM Cloud. C'est là que tournent les pods.
NamespaceUn « appartement » isolé dans le cluster, dédié à une équipe/appli. Créé ici par roksns.tf.
TerraformOutil d'Infrastructure as Code : on décrit les ressources cloud dans des fichiers .tf, il les crée (plan puis apply).
ProviderLe traducteur entre Terraform et un cloud donné. Ici : le provider BP2I « orchestrator » du groupe.
BP2I OrchestratorLa centrale de commande cloud interne BNP Paribas : Terraform lui passe commande, elle crée les ressources IBM Cloud.
State fileterraform.tfstate : la mémoire de Terraform. Sensible ; stocké dans un backend (GitLab ou IBM COS).
COSCloud Object Storage : stockage de fichiers/objets IBM Cloud. Utilisé par l'appli et comme backend possible du state.
TaintedRessource en état inconnu après une erreur de création (souvent un timeout). Se répare via Fix tainted / Recreate / Import.
VaultCoffre-fort à secrets du groupe. Le pipeline y récupère la clé API IBM Cloud — jamais de secret dans le repo.
tfenvPetit outil qui installe automatiquement la bonne version de Terraform (via TFENV_VERSION ou required_version).
TCaaSL'équipe/offre mutualisée du groupe qui fournit le pipeline IaC « clé en main » que le .gitlab-ci.yml inclut en 4 lignes.
VIPVirtual IP : l'adresse d'entrée réseau stable par laquelle le trafic atteint l'application.
