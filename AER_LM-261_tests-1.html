Non couvert par des tests unitaires, et pourquoi : les enums (pas de logique), V16 (vérifiée par la requête « après V16 » du doc d'implémentation et par le démarrage en ddl-auto: validate), la route gateway (YAML, vérifiée par le parcours Postman bout en bout).

Fixtures alignées sur les entités réelles (captures du 16/09)
ProfileEntity.roles est une List alimentée par addRole(RoleEntity) ; RoleEntity.permissions par addPermission(Permission). Les tests n'utilisent que ces deux méthodes, aucun setter supposé. Seul point à ajuster à la main : les deux imports OrganizationService / ProfileService (packages non vus) — reprendre ceux de UserFacadeImplTest.

2. Contrôleur — UserControllerTest

Le contrôleur reçoit un Authentication ; on passe un UsernamePasswordAuthenticationToken réel plutôt qu'un mock : getName() renvoie le principal, aucun stub à déclarer, Mockito strict reste satisfait.

3. Facade — UserFacadeImplTest

Les fixtures userEntity / userDTO du setUp existant sont réutilisées. Le second test vérifie que le mapper n'est jamais sollicité quand l'utilisateur est absent.

4. Mapper — UserMapperTest

UserMapper est un @Component à quatre dépendances injectées par constructeur : contrairement à ZoneMapperTest (new ZoneMapper()), il faut @InjectMocks. Aucune dépendance n'est stubbée : toContextGdfDto ne les touche pas, et Mockito strict échouerait sinon.

Ce que ces six cas verrouillent
  • Le contrat JSON du doc d'implémentation (identité, profileCode, agence {id, code, nom}).
  • Le filtre plateforme : une permission CONSOLE_ADMIN_* présente sur le même profil ne fuit pas dans le contexte GDF.
  • Le tri (TreeSet) : le front peut comparer des listes stables.
  • Les quatre chemins null : unité non-agence, unité absente, rôles absents, profil absent — le cas h11111 réel et les utilisateurs créés via CreateAdminUserDTO (sans orga).
